## 第 1 页｜标题：把 Agent 带入实时交互世界

### 页面文案

# Omni-Anything

## 面向 Agent 双工交互的推理系统

**让任何 Agent 无需重新训练，就能持续感知、实时表达、随时响应打断，并在交互过程中调用工具、把结果写回对话。**

`training-free · agent-agnostic · real-time · stateful`

首个验证载体：全双工语音交互（历史稿表述；不是当前落地目标）

### 版式建议

- 深色背景，标题居中；`Omni-Anything` 为视觉主体。
- 中部用一条极简链路表达系统边界：

  `真实世界 ⇄ Omni 交互运行时 ⇄ 任意 Agent`

- 「全双工语音」只作为右下角首期载体，不放进主标题，避免把项目讲窄。

### 这一页怎么讲

今天的 Agent 已经会推理、会调用工具，但大多仍通过 request/response 接口接触用户。Omni-Anything 要补齐的是 Agent 面向真实世界的交互能力层：智能内核不必重新训练，就能进入持续、实时、可中断的交互闭环。

## 第 2 页｜项目目标：构建 Agent 的通用交互能力层

### 页面标题

# 从「会完成任务」到「能持续参与真实世界」

### 核心目标

**构建一套与 Agent 智能内核解耦的 Omni Interaction Runtime，把任意 Agent 的推理与工具能力，稳定投射为实时、连续、可中断、可持续的多模态交互。**

### 三项能力目标

#### 1. 通用接入｜任意 Agent

- 通过标准适配层连接异构 Agent、工具与 API
- 不修改 Agent 的核心推理逻辑，不依赖模型权重训练
- 前台交互模型与后台 Agent 可独立演进、灵活替换

#### 2. 原生双工｜始终可交互

- 输入与输出并行：边听、边说、边思考、边调用工具
- 以真实播放进度定义上下文，正确处理打断、撤回和结果 cancellation
- 后台任务异步返回后，可在不中断前台交互的情况下写回结果

#### 3. 可部署性能｜可上线

- 支撑长时间、多会话、低抖动运行，而不是单次演示
- 在有限 GPU 容量下保持实时时限，并控制可接受的单路成本
- 形成可迁移到 GPU、昇腾等平台的运行时、状态协议和执行机制

### 底部结论条

> **项目交付的不是一个新的语音模型，而是 Agent 操作系统时代可复用的实时交互基础设施。**

### 版式建议

- 上半页放「一句话目标」；下半页放三张能力卡片：通用接入 / 原生双工 / 可部署性能。
- 三张卡片上方可以画一条能力链：

  `Agent 智能 → Omni-Anything → 实时交互`

### 这一页怎么讲

项目把「智能能力」和「交互能力」解耦。Agent 负责想什么、做什么；Omni-Anything 负责何时听见、何时说出、何时撤回、状态如何持续，以及这些行为如何以可接受成本运行。语音双工是第一阶段的可测载体，架构面向更一般的多模态事件流。

## 第 3 页｜研究问题：传统推理系统为何支撑不了原生双工 Agent？

### 页面标题

# 从一次性 request，到持续存在的交互过程

### 场景图

```text
用户 / 环境
   ⇅  连续输入、实时输出、随时打断
前台 Omni 模型  ⇄  Omni 交互运行时  ⇄  后台 Agent / 工具 / API
   ⇅  固定 tick                         ⇅  异步、长时、结果可 cancel
```

### 核心研究问题

**如何在不重新训练 Agent 的前提下，把 request 式推理引擎改造成一个满足真实时间因果、承载长期状态、且成本可控的持续交互系统？**

### 三个结构性矛盾

#### ① 长期状态 vs. 有限显存

双工会话没有轮次间隙，KV cache 随输入持续增长，每个 tick 都要访问。系统往往不是先把 GPU 算满，而是先触及 capacity-bound。

> 真实软件栈实验中，KV 池满后出现 starvation，而多数 GPU 采样仍为 0% SM util（E1 一例约 85% 采样为 0%；勿单独以本稿为证）。

#### ② 微小周期工作 vs. 通用动态引擎

每个 tick（固定时长的一轮，例如 2 秒）的有效计算很小，却反复承担动态 batching、kernel launch、内存规划和 shape 适配成本；通用性开销反而成为主要成本。

#### ③ 并行交互语义 vs. 串行生成接口

用户输入、模型输出和 Agent 结果在真实时间中并行发生；传统引擎却按串行 token 顺序组织状态，既可能让模型「看到尚未播出的内容」，又会重复扫描同一份历史。

### 底部结论条

> **需要共同解决三个瓶颈：状态容量、执行控制、数据移动；任何单点模型优化都不足以构成完整的双工 Agent 运行时。**

### 版式建议

- 左侧占 40%：画「用户—前台—运行时—Agent」的闭环图。
- 右侧占 60%：用三条「结构性矛盾」解释为什么传统 LLM serving 不够。
- `KV cache` 首次出现时加小字解释：「模型为会话历史保留的 attention 工作状态」。

### 这一页怎么讲

评审不需要先理解所有底层术语，只需要抓住一个变化：普通聊天服务处理的是短暂 request，Omni-Anything 处理的是持续存在、事件驱动、带物理时间约束的交互过程。持续状态、固定 tick 和真实播放因果同时出现后，传统引擎的三项基本假设一起失效。

## 第 4 页｜三个研究点：面向 Agent 前台双工交互的推理系统

### 页面标题

# 从「能双工」到「能持续、稳定、高效地双工」

### 研究点 1｜状态容量（现行主线候选 ≈ KV conveyor）

## 持续双工会话的 KV 状态虚拟化与请求编排

**问题：** 多路会话的 KV cache 持续增长，GPU 算力远远未满就先触及显存瓶颈；Agent 结果写回和打断还会制造大量 stale resident KV。

**方法：** 利用交互 tick 的可预测性，把 tail KV 的母本放在主机内存，通过相位指派和 SLO-aware 的 DMA 时间表，在每 tick 前 H2D 搬入、算后释放；配合 uncommitted / commit / cancel 状态机管理 Agent 结果。

**目标：** 用算力和带宽换显存，将物理 KV 容量 `M` 扩展为等效容量 `M + P`，支撑更长、更高密度且无损的实时会话。

`state virtualization · scheduled tail-KV offloading · transactional writeback`

### 研究点 2｜执行控制（非现行主线；设想稿在 `context/ideas/`）

## 面向周期交互的静态执行计划特化

**问题：** 每 tick 计算很小，却不断落入通用动态路径，反复承担 batching、CPU launch、内存规划和 shape 适配开销。

**方法：** 由运行时主动把 tick 类型、会话相位和 batch 组成约束成有限 signature 族，对每类交互 tick 做 AOT graph capture、attention metadata 固化、KV action 编排和工作区预分配。

**目标：** 把「在线逐步规划」变成「预编译计划重放」，降低每 tick 的 latency 和抖动，提升跨 GPU / 昇腾平台的可预测执行能力。

`process compilation · AOT execution · finite signatures`

### 研究点 3｜数据移动（非现行主线；设想稿在 `context/ideas/`）

## 面向同请求共享上下文的 prefill–decode 融合

**问题：** 同一交互 tick 内，模型一边 prefill 新输入、一边 decode 输出，两条路径会重复扫描同一份会话历史；简单串行化还可能破坏真实播放因果。

**方法：** 以 playback frontier 定义时间对齐 mask，将共享同一历史快照的 prefill 与 decode 合并执行，并通过 fork / commit 生命周期保证打断和写回后的状态正确性。

**目标：** 在不改变模型语义的前提下减少重复 KV 访存，降低同 tick 关键路径和 first-token latency。

`causality-aware fusion · shared-history scan · playback frontier`

### 三点共同底座

> **双工时间轴协议 + revocable KV 状态机**：统一描述输入何时可见、输出实际播到哪里、Agent 结果何时返回，以及状态何时 commit 或 cancel。

```text
研究点 1：让状态装得下       研究点 2：让每一 tick 跑得轻       研究点 3：让历史少搬一次
        长时多路承载   +          稳定低抖动执行   +          低延迟同 tick 计算
```

### 版式建议

- 主体使用三列等宽卡片，分别标注状态 / 执行 / 数据移动。
- 每列严格保留「问题—方法—目标」三行；英文关键词作为小号技术标签。
- 底部用一条横向底座承托三列，写「双工时间轴协议 + revocable KV 状态机」，强调三点属于同一运行时，而不是三项零散优化。

### 这一页怎么讲

三个研究点对应三类系统开销：研究点 1 扩展状态容量，研究点 2 消除动态控制开销，研究点 3 消除同一 request 内部的重复数据移动。它们共享同一时间轴和状态机，最终共同支撑「任意 Agent 的 training-free、可持续、性能可接受的原生双工交互」。

## 全稿统一说法

- 主标题讲 **Agent 的通用实时交互基础设施**，不要讲「语音推理服务优化项目」。
- 语音双工是首期载体；`omni` 表示能力层可连接持续多模态事件，而不是承诺一期覆盖所有模态。
- 「training-free」明确指**无需为接入的 Agent 重新训练模型权重**，不等于系统无需配置、标定或适配。
- 研究点 1 约 20% 的 PCIe5 / 480ms 容量增益仍是可用公式直接算出的预测，尚未在真机完成验证；这四页不把它写成已完成结果。
- 对非领域评审，三个记忆点应保持一致：

  1. 不是重新造模型，而是给任意 Agent 补一层交互基础设施；
  2. 双工交互把 request 变成带真实时间的持续过程；
  3. 三个研究点分别解决状态、执行和数据移动问题。
