\paragraph{Initialization and input replay.}
The initial text is tokenized to the requested length and processed by the real model.
Managed initialization waits for valid host backing and releases eligible idle blocks before proceeding to the next session, avoiding a requirement to fit all initial histories on the GPU simultaneously.
The input clock starts only after setup; initialization generation does not count toward delivered work.
Recording streams concatenate each speaker's source utterances in lexical order without padding or looping, and each session uses its recorded offset.
The open-loop source does not delay future updates to wait for earlier completion.
Rejected sessions are not retried.

\paragraph{Hardware provenance.}
GPU identity, memory and driver version were captured in each run manifest.
The CPU, RAM and PCIe endpoint details in Table~\ref{tab:reproduction-settings} were collected afterward on the same host and GPU.
The endpoint's Gen5 reading does not establish the end-to-end host-link generation, effective H2D bandwidth, or physical NUMA placement.
No nominal PCIe bandwidth is substituted for an observed transfer time.

\section{KV Checks and Execution Costs}

\paragraph{State and lifecycle checks.}
Eight short replays compare resident execution with managed execution using 2,048-token initial histories and a 4\,GiB GPU KV pool.
The checks cover one session, four concurrent sessions, staggered termination, and demand, submission, and advance restoration triggers.
All 136 periodic updates complete, and every run returns to its initial one-block allocator reservation after session release.
The five managed runs check 267 session transfers byte for byte across the model's KV layers before publishing their completion.
An independent GPU round-trip test also checks noncontiguous blocks and unchanged unrelated destinations.

The single-session pair produces identical token hashes for all eight updates.
In the aligned four-session pair, ten of twenty output hashes differ, while context positions, generated-token counts, and physical copy checks agree.
The cause of these output differences remains unresolved.

\paragraph{Grouped execution costs.}
Six separate resident runs measure one, two, and four sessions released together, at initial histories of 2,048 and 8,192 tokens.
They use the same model, period, output budget, and eager backend settings, with a 50.80\,GiB automatically sized KV pool and seed 1729.
Each run supplies five measured groups after a common four-second startup exclusion.
Elapsed time runs from the first engine enqueue to the last generation completion in the group, including backend scheduling and execution.
A release group may execute through several backend batches.

\section{Backbone Cost Estimation}

The resource estimates in the main paper use public model configurations and device specifications.
They estimate backbone prefill and decode time at the largest batch that fits within each GPU's assumed memory budget.
The central estimates assume 80\% memory bandwidth efficiency and 25\% compute efficiency, without empirical calibration.

\paragraph{Memory reservations.}
MiniCPM-o 4.5's backbone uses 144\,KiB of BF16 KV per retained position, giving 5.625\,GiB at its configured limit of 40,960 positions~\cite{openbmb2026minicpmconfig}.
Its speech decoder adds a separate reservation of 0.234375\,GiB at its 4,096-position limit.
The combined reservation is therefore $K_{\mathrm{sess}}=5.859375$\,GiB per session.
We assume $R=20$\,GiB for weights and other allocations and approximate each GPU's nominal capacity as a GiB budget $M$.
The memory-only session limit is $N_{\mathrm{mem}}=\lfloor(M-R)/K_{\mathrm{sess}}\rfloor$.

\paragraph{Work and traffic accounting.}
The backbone's projection and MLP matrices contain about 6.95 billion parameters and its output head another 0.62 billion, occupying about 15.1\,GB in BF16~\cite{openbmb2026minicpmconfig}.
Each batched forward pass reads these matrix weights once, while attention reads each session's own historical KV.
The prefill stage processes ten encoded audio positions together, assumes reuse of historical KV across those queries, and computes logits only for the last position.
Four sequential decode forward passes follow, including a final state update when needed.
The update begins with enough unused context positions to accommodate these additions; attention cost is approximated at the configured context limit.
We apply the roofline estimate separately to the projection and MLP matrices, the output head, and attention, then sum their times over prefill and decode.
Input encoding, speech generation, and runtime overhead require separate measurement.

\paragraph{Compute reference and sensitivity.}
For the RTX PRO 6000 Blackwell Server, we use approximately 240\,TFLOP/s as the dense BF16 reference.
This value is inferred from its FP32 rating and the GB202 ratio of dense BF16 throughput with FP32 accumulation to FP32 throughput~\cite{nvidia2026rtxpro,nvidia2025blackwell}.
The efficiency ranges in the main paper vary bandwidth efficiency from 40\% to 80\% and compute efficiency from 15\% to 40\%, holding batch size and workload fixed.
The lower and upper execution-time endpoints use efficiency pairs $(0.80,0.40)$ and $(0.40,0.15)$, respectively.
These ranges describe sensitivity to assumptions, not measurement uncertainty.

\paragraph{Other model configurations.}
The cross-model estimates use the public configurations of the 3B and 7B Qwen2.5-Omni Thinkers and Moshi's temporal Transformer~\cite{qwen2025omni3bconfig,qwen2025omni7bconfig,defossez2024moshi,kyutai2026moshiconfig}.
For the Qwen models, a one-second incremental update contains 25 encoded audio positions and four text decode forward passes; the period and decode count are workload assumptions~\cite{xu2025qwenomni}.
Moshi advances its temporal backbone once per native 80\,ms frame.
We reserve each model's auxiliary KV separately and assume 16, 28, and 20\,GiB for weights and other allocations for Qwen 3B, Qwen 7B, and Moshi, respectively.
The per-session auxiliary KV reservations are 0.375, 1.5, and 0.0078125\,GiB, respectively.
The estimates exclude input encoders and speech-output modules, including Moshi's depth Transformer.

\section{Additional Results}
The main evaluation uses six single-run measurements, with two offered loads and three systems.
The high-load primary window contains 140 offered updates: residency admits and completes 110; each managed system admits and completes 140.
All admitted updates satisfy their planned-tick deadlines in this window.
Under the supplementary source-ready-plus-two-seconds criterion, on-demand restoration completes 104 on time and 36 late, while \systemname completes 138 on time and two late.
Across the full run, the corresponding on-time/late counts are 117/51 and 160/8.
There is no unfinished admitted work in any of these measurements.

\paragraph{Transfer and host costs.}
For the high-load primary window, submitted H2D payloads total 210.94\,GiB for on-demand restoration and 223.59\,GiB for \systemname; submitted incremental D2H payloads total 1.53 and 1.14\,GiB, respectively.
These counters include copy submissions within the common time interval, so different copy timing can change the number of transfers counted at its boundaries.
They are not per-update matched transfer volumes, nor do they measure exclusive link occupancy.
Both systems reach 62.85\,GiB of valid host backing, including reclaimable cached copies, with an 80\,GiB reserved host pool.
Source-end draining takes 5.16 seconds for on-demand restoration and 3.16 seconds for \systemname, compared with 1.42 seconds for residency.
The lower offered-load point reaches 54.43\,GiB of valid host backing in both managed systems.

\paragraph{Reproducibility and interpretation.}
Raw event logs, manifests, input schedules, source patches, terminal validation, and input hashes accompany the measurements.
The primary analysis excludes the initial six seconds; the deadline sensitivity recomputes the full sequence from the same immutable events.
The source-clock deadline is an explicitly supplementary analysis.
No update within a run is treated as an independent experimental repeat, and no confidence interval is inferred from the percentile samples.
