\section{Periodic Interactive Model Serving}
\label{sec:problem}

\subsection{From Finite Requests to Long-Lived Sessions}

A finite request usually consists of a prompt, a prefill, and an
autoregressive decode that eventually completes.  Its KV state can then be
released or retained as a cache entry.  Continuous batching, paged KV
allocation, and prefix caching improve this request stream, but the request's
completion remains a natural state-lifetime boundary.

A \emph{streaming interaction session} has a different serving shape.  The
session remains open, input and output arrive as incremental chunks, and the
model reuses earlier context on later updates.  A continuously listening
assistant, for example, may append a short audio chunk and produce an
incremental result while preserving the history needed to interpret the next
chunk.  The logical context and its KV working set therefore grow across
updates instead of disappearing after one response.  We use \emph{periodic
interaction session} for an analyzable instance of this shape; it is a serving
abstraction, not a claim that every application uses an identical timer or
media protocol.

The measured prototype instance uses audio input to a persistent
Qwen2.5-Omni request and reads Thinker text output.  It does not execute the
Talker or Code2Wav path and does not deliver PCM audio.  Consequently, the
paper uses this stack to study state residency and scheduling, not to infer
audio quality, playback stalls, or the behavior of every multimodal model.

\subsection{Workload Model}

Session $i$ has a target period $T$.  Its $k$th application-level update, or
\emph{tick}, is released at
\begin{equation}
  r_{i,k} = r_{i,0} + kT,
  \qquad
  \phi_i = r_{i,0} \bmod T,
\end{equation}
where $\phi_i$ is the session's release offset.  A tick submits one input
chunk and receives whatever output is currently deliverable.  It is distinct
from a gateway-to-worker service RPC and from an engine iteration; the latter
may execute prefill, decode, or neither for several requests.

For update $(i,k)$, let $m_{i,k}$ be the number of tokens generated by the
model.  The abstract workload bounds it by a per-period output token cap $M$,
so $0 \le m_{i,k} \le M$.  The cap is an upper bound, not a minimum delivery
requirement.  In particular, the amount consumed by a gateway at one release
need not belong to the input submitted at that release when output is buffered
asynchronously.  We associate each input chunk with a soft per-period latency
target $D$.  The final operational definition of latency and sustainable
service is part of the evaluation protocol; an RPC returning within $T$ is
not, by itself, evidence that the corresponding model output is fresh.

If an update occupies less than $T$, the workload itself supplies an
intrinsic reuse interval before the same session is used again.  Release
offsets do not create that interval.  They only determine where each session's
input, admission, computation, and possible restoration occur within the
shared period.

\subsection{Resource Frontier}

KV state competes with model weights, activations, and other runtime state for
GPU memory.  As session contexts grow, keeping all KV blocks resident makes
the aggregate working set grow with both session count and context length.
The relevant capacity is the GPU block pool actually available to KV, not the
device's nominal memory size.  We call an operating point
\emph{KV-cache-capacity limited} when this allocatable pool is exhausted
before the workload exhausts its per-period compute budget.  This is a
capacity statement and should not be confused with describing a kernel as
memory-bandwidth bound.

Eviction moves rather than eliminates cost.  A missing block with a host copy
consumes host-to-device bandwidth and transfer time; a block without such a
copy must be recomputed; retaining fewer GPU blocks can also change prefix
matching and cache pressure.  Release offsets introduce a further trade-off:
they can spread simultaneous demand, but can also replace a large batch with
several smaller ones.  The feasible region must therefore account for at
least GPU KV capacity, prefill and decode computation within $T$, HBM traffic,
and the PCIe restoration envelope.  We treat this multi-resource frontier as
an evaluation model to be calibrated, not as an already established
cross-hardware law.

\subsection{Design Goals and Non-Goals}

Conveyor follows four design goals.  First, it preserves the complete logical
context rather than using lossy truncation to manufacture capacity.  Second,
it keeps each session's period $T$ unchanged; scheduling may choose a stable
offset within the period but may not stretch the workload.  Third, eviction
occurs only after a resumable request becomes idle, and restoration must
remain correct when prefetching is late or unavailable.  Fourth, physical
block pools remain authoritative for residency and host coverage, and every
enabled mechanism emits independent events that can be checked in a run.

The current scope is a single-GPU serving system.  It does not include speech
synthesis, application cancellation, asynchronous external-result insertion,
multi-GPU prefill/decode disaggregation, or an admission controller for loads
beyond the total resource frontier.  Initial-context preloading is an
experimental state-construction procedure rather than a serving mechanism.
