\section{Background and Motivation}

\subsection{Periodic Execution and Retained State}
\label{sec:request-classes}
\label{sec:formulation}

An application's retention policy determines which history remains available to the model.
Full retention, a fixed window, and a summary therefore have different implications for both memory use and model behavior.
Residency management preserves the selected history while changing where its KV is stored.
Reclaiming GPU space requires an interval without access to that state; periodic input capture alone does not establish such an interval.

For timing analysis, consider sessions with a common period $T$ and reference time $t_0$.
Session $i$ has phase $\phi_i\in[0,T)$, so its micro-turn $k$ is released at the tick
\begin{equation}
  r(i,k)=t_0+\phi_i+kT.
  \label{eq:release}
\end{equation}
Let $c(i,k)$ denote completion of generation for that micro-turn.
Its soft deadline is the next tick, giving the service target
\begin{equation}
  c(i,k)\le r(i,k+1)=r(i,k)+T.
  \label{eq:deadline}
\end{equation}
Occasional misses are permitted under a specified deadline-miss rate limit.
Latency is $c(i,k)-r(i,k)$, so delays before submission remain part of the service latency and do not shift the deadline.
Initial phase alignment and delivery delay require separate accounting (Section~\ref{sec:methodology}).

Reclamation can begin only after computation stops accessing the selected KV.
Let $q(i,k)$ denote the last use of the KV selected for eviction in micro-turn $k$.
The server can release that state once outstanding references are gone and a valid host copy is available.
Restoration must complete before the next computation accesses the state; \systemname targets the next tick, $r(i,k+1)$, to avoid delaying that computation.
The planned reclamation and restoration window therefore extends from $q(i,k)$ to $r(i,k+1)$, provided no intervening accesses occur.
Late computation shortens this window and may eliminate it entirely.

\subsection{When KV Capacity Limits Concurrency}
\label{sec:capacity-problem}
\label{sec:slack-conditions}

The capacity argument compares the memory and execution time required by all admitted sessions.
One session's KV may be idle while other sessions keep the GPU busy, and periodic releases alone do not establish compute slack~\cite{liu1973scheduling}.
Execution time can also increase with context length, even when the amount of new input and generated output per micro-turn is fixed.
We must therefore assess the complete workload's execution time at the context length that fills GPU KV capacity.

Consider $N$ sessions whose inputs are available at the same tick, with a common period $T$ and no inter-session KV sharing.
Each session reaches a maximum retained length of $L$ positions within the period, with $\kappa$ KV bytes per position.
Let $G_{\mathrm{KV}}$ be the capacity available for KV after weights, activations, and other runtime allocations.
Ignoring allocation rounding, full residency fills this pool at
\begin{equation}
  L_{\mathrm{mem}}=\frac{G_{\mathrm{KV}}}{N\kappa}.
  \label{eq:memory-boundary}
\end{equation}
Let $C_N(L)$ be the elapsed time to execute all $N$ sessions' per-period work under a specified policy, with the required KV resident.
This includes input processing, model execution, and scheduling overhead; batching means it is not generally the sum of isolated session times.

The remaining compute budget at the memory limit is $T-C_N(L_{\mathrm{mem}})$.
A positive value means that the retained KV fills the pool before the complete workload uses up the period.
To obtain a sufficient condition in terms of resource and workload parameters, suppose execution time satisfies
\begin{equation}
  C_N(L)\le A_N+B_NL,\qquad A_N\ge0,\ B_N\ge0,
  \label{eq:compute-envelope}
\end{equation}
for fixed per-period input and generation work over the context range under analysis.
The intercept $A_N$ accounts for work independent of history length, while the slope $B_N$ allows cost to increase with that length.
This affine envelope must be established as an upper bound for the chosen workload, platform, and execution policy.
If $L_{\mathrm{mem}}$ lies within the same range, then
\begin{equation}
  T-C_N(L_{\mathrm{mem}})
  \ge T-A_N-\frac{B_NG_{\mathrm{KV}}}{N\kappa}.
  \label{eq:memory-before-compute}
\end{equation}
A positive right-hand side is sufficient to establish compute slack at the memory limit.
If it is at least $\eta T$, for $0<\eta<1$, the workload leaves at least a fraction $\eta$ of the period unused.

Fitting $A_N$ and $B_N$ to measurements does not establish an upper bound.
Such a fit predicts slack and requires validation on independent configurations.
Even a valid slack bound does not guarantee that additional sessions or recomputation meet their deadlines.
Their work must fit alongside recovery costs and interference while preserving every session's deadline.

\subsection{Restoration Needs Both Time and Space}
\label{sec:opportunity}

Eviction frees GPU capacity until the server allocates a destination for restoration.
The entire destination must be allocated before copying begins, even though its contents are not yet usable.
Let $\mathcal{P}(t)$ contain the physical GPU blocks allocated to KV at time $t$, including destinations of unfinished restorations.
For block sizes $b_p$, the capacity constraint is
\begin{equation}
  \sum_{p\in\mathcal{P}(t)} b_p \le G_{\mathrm{KV}}
  \quad\text{at every }t.
  \label{eq:memory}
\end{equation}
Each shared physical block is counted once; counting only valid KV would omit space already committed to ongoing restorations.

The destination must become available early enough to complete the transfer before the next tick.
For a restoration of $e$ bytes starting at $u$, let $\widehat B$ be the estimated effective host-to-device bandwidth.
With an allowance $\delta$ for scheduling and completion overhead, the estimated completion must satisfy
\begin{equation}
  u + e/\widehat B + \delta \le r(i,k+1).
  \label{eq:restore-time}
\end{equation}
The bandwidth estimate must reflect the shared transfer schedule, including interference from host backup traffic and concurrent GPU work.
The nominal link rate alone does not capture these effects.

Equations~\ref{eq:memory} and~\ref{eq:restore-time} constrain the same restoration decision.
Starting earlier leaves more time for copying but holds the destination longer; evicting more bytes releases more capacity but lengthens the transfer.
Session phases determine when memory is released relative to when other sessions need their KV restored.
A per-period transfer budget can therefore be satisfied even when individual restorations lack time or their destinations cannot coexist in GPU memory.
The server must check the transfer windows and GPU allocation over time, together with computation under the chosen phases.
