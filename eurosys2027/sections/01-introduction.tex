\section{Introduction}
\label{sec:introduction}

Full-duplex interaction is an emerging direction in human--AI communication, with recent models such as OpenAI's GPT-Live and ByteDance's Seeduplex~\cite{openai2026gptlive,bytedance2026seeduplex}.
By listening while speaking and adapting to interruptions, these models let users clarify or redirect a conversation without waiting for a response to finish.
At the serving layer, we treat each ongoing interaction as an \emph{interaction session}.

We study interaction sessions that advance through periodic updates, each processing new input and generating output as needed.
For example, Moshi operates on 80\,ms audio frames, while Thinking Machines Lab's TML-Interaction-Small organizes input and output into 200\,ms \emph{time-aligned micro-turns}~\cite{defossez2024moshi,thinkingmachines2026interactionmodels}.
The session's history persists across these updates.

To reuse history across updates, the server caches attention keys and values (KV), whose footprint grows with the retained context.
Using published parameters for MiniCPM-o 4.5, we estimate a BF16 KV footprint of about 1.2\,GiB in the language backbone for a ten-minute audio conversation~\cite{cui2026minicpmo45,openbmb2026minicpmconfig}.
This estimate assumes full retention of continuous input and output streams, contributing ten audio positions and four generated text tokens per second, respectively.
It excludes prompt and control tokens and state in other modules.
% 2 (K and V) * 36 layers * 8 KV heads * 128 dimensions * 2 bytes = 144 KiB/position.
% 600 s * (10 input audio positions/s + 4 output text tokens/s) * 144 KiB = 1.153564453125 GiB.
% This counts backbone KV for both streams, excluding control/prompt tokens and other modules.

Keeping all retained KV on the GPU, which we call \emph{full residency}, consumes memory even during intervals when the session does not access it (Figure~\ref{fig:motivation}).
As histories grow across concurrent sessions, this state can exhaust GPU KV capacity before their combined computation uses up the time available in each period.
We target this regime, where reusing the space occupied by idle KV could allow the server to accommodate more sessions.

Offloading idle KV to host memory makes its GPU space available to other sessions.
InferCept, for example, chooses among retaining, swapping, and recomputing KV for requests paused by external interactions~\cite{abhyankar2024infercept}.
In periodic service, the evicted state is needed again for the next update.
We use the start of the next period as each update's soft deadline.
If restoration begins only when an update is released, computation that needs the evicted state must wait for the transfer, potentially causing a deadline miss (Figure~\ref{fig:comparison}(a)).

Periodicity provides an opportunity to avoid this delay: the next update's scheduled release time is known in advance.
We call the start of each period a \emph{tick} and use it as the target for completing restoration.
By keeping idle KV in host memory and restoring it before the next tick, the server can reuse the same GPU space across sessions.
We refer to this reuse as \emph{memory multiplexing}.

Scheduling restoration requires both transfer time and GPU space.
Restorations compete for shared transfer bandwidth, and the full GPU destination for each restoration must be allocated before copying begins.
Restoring too early occupies space that other sessions could use; starting too late risks missing the next tick.
Larger evictions free more space but require more data to be transferred back.
The server must therefore coordinate how much KV to evict from each session, when to restore it, and when to schedule each session's computation.

We present \systemname, a serving system that multiplexes GPU memory across periodic interaction sessions through \emph{cyclic KV restoration}.
\systemname assigns each session a \emph{phase}, or release offset within the period, to spread execution and restoration demand over time.
After a session completes an update, \systemname evicts part of its idle KV and schedules restoration to complete before the next tick.
The plan coordinates phases, eviction amounts, and restoration times so that space released by one session can accommodate another's restoration (Figure~\ref{fig:comparison}(b)).
The goal is to serve more concurrent sessions while preserving their retained histories and meeting the same soft deadline targets.

\systemname plans KV demand at each session's configured maximum context length, which input and generation must respect.
The recurring schedule accounts for computation, transfers, and GPU allocation, while runtime operations cover only the history actually retained.
It reuses this plan as histories grow within their limits and revises it when sessions join or leave.
