\section{Introduction}
\label{sec:introduction}

A conversational assistant that can respond to interruptions must process new input even while it speaks.
MiniCPM-o 4.5 does so in one-second chunks: it incorporates the latest input, decides whether to speak, and generates output when needed~\cite{cui2026minicpmo45}.
We use Thinking Machines Lab's term \emph{micro-turns} for these short interaction intervals~\cite{thinkingmachines2026interactionmodels}.
Each micro-turn extends a history that the model uses in subsequent updates.
We study how to serve concurrent sessions that advance in this periodic manner.

Models cache attention keys and values (KV) for retained history so that later updates can reuse them.
This state has a memory cost even between updates: retaining ten minutes of MiniCPM-o 4.5 input audio, for example, requires approximately 0.82\,GiB per session in BF16.
This is a parameter-based estimate, not a serving measurement: the model produces 10 audio feature tokens per second, and its published backbone configuration requires 144\,KiB of KV per position~\cite{cui2026minicpmo45,openbmb2026minicpmconfig}.
The estimate assumes full retention and excludes text, visual inputs, control tokens, other model state, and allocation overhead.
When a micro-turn finishes before the end of its period, its KV is idle but remains allocated under full GPU residency (Figure~\ref{fig:motivation}).
Across sessions, this retained state can fill the available KV capacity while their combined computation still leaves time within the period.
Whether this occurs depends on the workload and execution policy; periodic execution alone does not imply spare GPU compute capacity.

One way to limit this memory cost is to retain less history.
Metronome bounds the KV window of periodic interaction sessions and uses deadline feedback to control admission~\cite{meng2026metronome}.
For applications that need a larger history, offloading idle KV preserves that history at the cost of recovering it later.
InferCept, for example, chooses among retaining, swapping, and recomputing state for requests paused by external interactions~\cite{abhyankar2024infercept}.
Periodic service makes recovery a recurring scheduling problem: whenever KV is evicted between micro-turns, it must be restored for the next one.
Waiting until that micro-turn arrives puts restoration on its execution path (Figure~\ref{fig:comparison}(a)).

The start of each period, or \emph{tick}, is known in advance, giving the server an opportunity to restore KV before it is needed.
When the application also permits the server to choose each session's phase, or start offset within the period, the server can stagger these updates.
One session's idle interval can then provide GPU space for another session's work.
This is the opportunity for \emph{memory multiplexing}: sessions reuse the same GPU KV space at different times while each retains its own history.

Using that space requires more than fitting the transfer bytes into a period.
A restoration must allocate its entire destination before copying begins, so an early transfer occupies memory that other sessions may still need.
A later transfer leaves that space free longer but has less time to complete before the next tick.
Likewise, evicting more KV reclaims more space but requires a longer transfer to restore it.
Session phases determine when these demands occur relative to one another.
The server must therefore coordinate when sessions run, how much KV they evict, and when they restore it, checking both shared bandwidth and GPU allocation throughout the period.

We present \systemname, a design that coordinates these decisions through \emph{cyclic KV restoration}.
After each micro-turn, it evicts part of the session's idle KV and schedules that state to return by the next tick.
By staggering sessions, it seeks to use space released by one session for another's restoration, as illustrated in Figure~\ref{fig:comparison}(b).
The aim is to serve more sessions while preserving their history and meeting a recurring soft deadline: each micro-turn should finish by the next tick.

History growth means that a schedule that fits now may no longer fit later.
At admission, \systemname plans over a finite lookahead interval, accounting for expected KV growth and the computation, transfers, and allocations needed during that interval.
It follows the plan across micro-turns, with infrequent revisions as histories grow or sessions enter and leave.
Planning ahead is intended to anticipate resource pressure without replanning every micro-turn; feasibility within one such interval does not guarantee capacity for the session's entire lifetime.
