\section{Introduction}
\label{sec:introduction}

Recent models such as OpenAI's GPT-Live and ByteDance's Seeduplex support full-duplex human--AI interaction~\cite{openai2026gptlive,bytedance2026seeduplex}.
By listening while speaking and adapting to interruptions, these models let users clarify or redirect a conversation without waiting for a response to finish.
We refer to each ongoing interaction as an \emph{interaction session}.

We study interaction sessions that advance through periodic updates, each processing new input and generating output as needed.
For example, Moshi operates on 80\,ms audio frames, while Thinking Machines Lab's TML-Interaction-Small organizes input and output into 200\,ms \emph{time-aligned micro-turns}~\cite{defossez2024moshi,thinkingmachines2026interactionmodels}.
A single response can span  updates, allowing new input to influence generation before the response ends.
The server must therefore preserve each session's history across updates, including intervals when that session is not executing.

To reuse history across updates, the server caches attention keys and values (KV), whose footprint grows with the retained context.
For MiniCPM-o 4.5, retaining ten minutes of continuous input and output at ten encoded audio positions and four generated text tokens per second requires an estimated 1.2\,GiB of BF16 backbone KV~\cite{cui2026minicpmo45,openbmb2026minicpmconfig}.
% 2 (K and V) * 36 layers * 8 KV heads * 128 dimensions * 2 bytes = 144 KiB/position.
% 600 s * (10 input audio positions/s + 4 output text tokens/s) * 144 KiB = 1.153564453125 GiB.
% This counts backbone KV for both streams, excluding control/prompt tokens and other modules.
Under \emph{full residency}, the KV for each session's retained history stays on the GPU, occupying memory even when the session is not accessing it (Figure~\ref{fig:motivation}).
As histories grow across concurrent sessions, their combined KV footprint can exhaust GPU KV capacity while their computation still fits within each period.
We target this regime, where reclaiming the GPU space occupied by idle KV could allow the server to accommodate more sessions.

Offloading idle KV to host memory makes its GPU space available to other sessions.
InferCept, for example, chooses among retaining, swapping, and recomputing KV for requests paused by external interactions~\cite{abhyankar2024infercept}.
For periodic interaction sessions, the next update's scheduled release time is known in advance.
Each update has a soft deadline at the start of the following period.
If restoration starts only when an update is released, computation that depends on the evicted state must wait for the transfer, which can cause a deadline miss (Figure~\ref{fig:comparison}(a)).
This timing information allows the server to restore KV before it is needed.
A \emph{tick} marks the start of each period; KV restoration is scheduled to finish before the next tick.
Keeping idle KV in host memory between updates allows the server to reuse the same GPU space across sessions.
We refer to this reuse as \emph{memory multiplexing}.

Restoration scheduling must account for both transfer time and GPU space.
Restorations share transfer bandwidth and require GPU memory for their destination buffers.
Restoring too early occupies space that other sessions could use; starting too late risks leaving KV unavailable at the next tick.
Larger evictions free more space but require more data to be transferred back.
The server must therefore coordinate how much KV to evict from each session, when to restore it, and when to schedule each session's computation.
The schematic in Figure~\ref{fig:comparison} assumes that each restoration's full destination is allocated before copying begins and counts that space in the memory curves from allocation onward.

We present \systemname, a serving system that multiplexes GPU memory across periodic interaction sessions through \emph{cyclic KV restoration}.
Within the timing flexibility allowed by the application, \systemname assigns each session a \emph{phase}, or release offset within the period, to spread H2D restoration demand over time.
This keeps the link busy over more of the period, allowing more KV to be restored per period and supporting larger evictions.
After a session completes an update, \systemname evicts part of its idle KV and schedules restoration to complete before the next tick.
The plan coordinates phases, eviction amounts, and restoration times so that space released by one session can accommodate another's restoration (Figure~\ref{fig:comparison}(b)).
This coordination expands effective KV capacity to serve more concurrent sessions under the same history and soft deadline requirements.

To reuse a schedule as histories grow, \systemname plans for the KV required at each session's configured maximum context length.
The total retained context, including new input and generated output, must stay within this limit.
The recurring schedule accounts for computation, transfers, and GPU allocation, while runtime operations act on the history actually retained.
\systemname revises the plan when sessions join or leave.
