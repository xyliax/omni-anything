\section{Evaluation}
\label{sec:evaluation}

The evaluation tests whether lower peak GPU KV residency translates into more periodic work completed on time, and quantifies the latency and transfer costs.
Three experiments examine capacity, service under session arrivals and departures, and the contributions of phase assignment and restoration timing.

\subsection{Methodology}
\label{sec:methodology}

\paragraph{Compared systems.}
We compare three configurations: GPU full residency, on-demand host restoration, and \systemname.
Full residency retains the same reference history on the GPU and rejects new sessions beyond a static admission limit determined from the common maximum context and independent calibration.
It uses naturally staggered session clocks and a suitable backend batching configuration.
On-demand restoration uses the same host-copy and partial-eviction implementation as \systemname, but restores missing KV when current work needs it.
This configuration isolates the contribution of advance restoration within the shared implementation.
\systemname combines residency planning, phase assignment, and restoration before the next tick.
Each system uses its own admission limit under the same resource and service constraints; rejected sessions are counted and are not automatically retried.

\paragraph{Workload controls.}
Comparisons fix the model and precision, maximum context, history-retention policy, period, original input content and timestamps, and per-session generation settings.
At equal concurrency, we also check the actual input, generation, and retained history.
Capacity comparisons hold offered work fixed and measure how much each system completes.
Input streams use reproducible content and per-session offsets, avoiding identical streams that could inflate cross-session reuse.
Initial histories and measurement durations are matched, and retained input and generation positions must remain within the context limit.
Backend settings and resource budgets are recorded, including any differences required by the mechanisms.
Each data point starts a fresh worker; independent calibration is separate from the repeated measurement runs.

\paragraph{Completion and latency.}
Let $c(i,k)$ denote completion of model generation associated with update $k$ of session $i$, and let $r(i,k)$ be its planned tick.
An update is on time when $c(i,k)\leq r(i,k+1)$; its periodic completion latency is $c(i,k)-r(i,k)$.
We report on-time, late, and unfinished updates alongside latency distributions and offered, admitted, rejected, and completed sessions.
Rejected sessions are unserved demand, rather than deadline misses among admitted sessions.
Delayed submission does not move the original deadline.
Initial phase-alignment waiting, input backlog, and delivery latency from the original input clock remain visible.
RPC returns and previously buffered output do not establish completion of new model work.
Failed or timed-out runs retain their completed and unfinished work under the common observation interval.

\paragraph{Resources and validation.}
Peak KV occupancy counts physical GPU blocks unavailable to other sessions, including restoration destinations from allocation onward; shared blocks count once.
We also record host-copy storage, H2D and D2H bytes, restoration waits, and actual batch shapes.
Detailed traces at selected points distinguish allocation, copying, and scheduling waits, with profiling overhead checked separately from the main runs.
Before performance measurements, short checks compare KV content and model results across eviction and restoration and verify session termination and resource release.
The checks record controls for nondeterminism and distinguish state correctness from timely completion.

\subsection{Capacity and Service Cost}
\label{sec:eval-main}

The first experiment compares all three systems at five concurrency points spanning low load, the full-residency boundary, and higher offered concurrency, with three independent runs per point.
Each run uses a fixed session population with staggered input clocks and records histories growing toward the common context limit.
The same runs provide equal-concurrency resource comparisons, capacity curves, and measurements of how costs change with context length.
Low-load points expose overheads when little additional capacity is needed.

Long-history initialization can shorten a controlled comparison when its state fits during setup.
It uses the same reconstructible history and excludes initialization output from service measurements.
If the highest concurrency cannot initialize all histories while resident, the entire sweep starts from a common shorter history and grows through real input and generation over a matched duration.
The comparison records actual context lengths and preserves room for subsequent work rather than silently truncating history.

\paragraph{Interpreting capacity.}
\label{sec:eval-capacity-bound}
Near the full-residency limit, joint allocation and execution observations test whether KV capacity prevents additional service while the aggregate periodic work still leaves compute budget.
The additional work completed by \systemname then tests whether that budget remains usable after restoration and changes in batching.
A protected baseline may continue serving admitted sessions promptly while rejecting additional sessions.
A capacity gain requires \systemname to complete additional sessions' work on time, together with a report of the associated latency and resource costs.
We retain the full curves rather than classify configurations using an added deadline-miss tolerance.

\subsection{Dynamic Session Arrivals and Departures}
\label{sec:eval-dynamic}

The second experiment compares full residency and \systemname using the same open-loop session schedule.
Successive session interarrival times are exponentially distributed with rate $\lambda$.
Each session lasts for a fixed duration $\tau$ and replays its assigned input stream at the original rate.
The schedule records each session's arrival, duration, content identifier, and content offset, together with the random seed.
Neither new arrivals nor ongoing input wait for earlier work to complete.
Planned and actual send times expose delays introduced by the load generator.

\paragraph{Natural staggering.}
For a session arriving at time $s_i$, input for its first period becomes available at $s_i+T$, followed by periodic input at $s_i+2T,\ldots$.
These session-relative clocks retain their fractional offsets rather than being rounded to a shared global tick.
Random arrivals therefore produce naturally staggered phases and a mixture of session ages.
\systemname receives the same input segments at the same original times and may buffer them for its assigned phases within the application's timing flexibility.
Its initial alignment wait and input-to-result delay are included in the measurements.
The planner does not receive the generator's future arrivals or departure times.

\paragraph{Load and observation.}
We use three arrival rates covering low load, the full-residency boundary, and higher load, with three independently seeded schedules per rate replayed across both systems.
The product $\lambda\tau$ provides a reference for average offered concurrency after startup, rather than the number actually admitted.
The arrival window spans at least two session lifetimes to include departures and replacement arrivals.
After new arrivals stop, existing sessions continue to their scheduled input end; remaining work is accounted for under the common termination rule.
Draining is reported separately from throughput during offered load, and context-limit termination is distinguished from execution failure.

\subsection{Mechanism Ablations}
\label{sec:eval-ablation}

The third experiment uses one or two representative boundary points from the capacity sweep.
Two additional variants reuse \systemname's implementation: natural phases with advance restoration, and prefetching after input submission with the assigned phases.
Together with the three main systems, these give five configurations in total.
Matched main-system runs are reused where their workloads and controls agree.

\paragraph{Phase assignment.}
The first comparison holds concurrency, history, eviction budgets, host-copy policy, and advance restoration fixed, and compares natural session phases with \systemname's assigned phases.
It measures whether active phase assignment improves peak allocation and periodic completion beyond the staggering already provided by independent session clocks.
Actual batch shapes and execution costs capture the cost of changing those phases.

\paragraph{Restoration timing.}
\label{sec:eval-latency}
The second comparison fixes phases and the other residency settings, and changes only the trigger: current demand, input submission, or advance restoration for the next tick.
For each update, traces associate destination allocation, copy start and completion, tick, execution start, and generation completion.
These events test whether earlier restoration reduces dependent work's wait and how much GPU space it occupies in advance.
