\subsection{Methodology}
\label{sec:methodology}

\paragraph{Workload and comparison controls.}
A residency comparison holds the model, precision, input content, retained history, and generation work fixed.
The controls also match batching limits, scheduling policies, and resource budgets except for the variable under study.
Retention policies are workload parameters; each residency comparison preserves the selected policy and its resulting history.
Workload parameters include the period, session duration, context-length range, and input and output configuration.

\paragraph{Compared systems.}
Full residency establishes capacity and latency without recovery.
On-demand host restoration exposes the cost of putting recovery on the execution path.
Recomputation provides a second way to recover missing state when the required historical inputs are available.
Comparisons with \systemname use the same generation workload and include the phase and restoration ablations described below.

\paragraph{Service capacity.}
The main metric is the largest concurrent session population that satisfies the specified deadline-miss and failure criteria over the observation interval.
Offered, admitted, and completed work are reported separately, so refusing more load cannot appear as a latency improvement.
Deadline violations use $c(i,k)>r(i,k+1)$, and latency distributions use $c(i,k)-r(i,k)$.
The analysis also records initial phase-alignment delay and accumulated backlog.
Progress measurements distinguish legitimate silence from missing generation work, which a timely empty response can conceal.

\paragraph{Resource measurements.}
GPU memory measurements include all KV allocations, particularly destinations whose copies have not completed.
Valid content, evicted bytes, and host-copy storage are recorded separately.
Transfer measurements distinguish waiting for space, queueing for the copy stream, copying, and completion handling.
Compute measurements cover the work required by each micro-turn and its interference with transfers.
These measurements connect a change in session capacity to the resource it consumes.

\subsection{Capacity and Service Latency}
\label{sec:eval-main}

The main comparison varies concurrency and session duration to locate the service limit of each system.
Latency and deadline violations at equal offered load show whether recovery introduces a cost before capacity is exhausted.
At each system's capacity limit, the allocation and execution traces identify whether memory, transfers, computation, or growing backlog prevents further admission.

\paragraph{The full-residency limit.}
\label{sec:eval-capacity-bound}
The motivating measurement varies retained history and concurrency together.
A memory-limited operating point requires evidence that KV allocation prevents additional service while the corresponding computation still fits within the period.
Session-level idle intervals alone do not establish spare compute capacity across the workload.
Near the memory boundary, the measurements report the complete workload's execution time per period and the remaining fraction of the period, rather than inferring slack from a device-utilization counter.
Calibration and validation use separate configurations to test Equation~\ref{eq:memory-before-compute}, including regions where it predicts no slack.
An additional-work experiment tests whether the observed budget can accommodate more session work while preserving the service objective.

\subsection{Mechanism Ablations}
\label{sec:eval-ablation}

The ablations isolate phase assignment from advance restoration.
The first comparison holds the restoration policy fixed and changes aligned releases to uniformly staggered releases.
The second keeps phases fixed and compares three recovery policies: on-demand restoration, prefetching after submission, and restoration planned before the next tick.
Their combination tests whether spreading demand improves the memory and transfer schedule beyond either action alone.

A further comparison holds the phase schedule fixed while varying eviction budgets and restoration lead time.
It tests the coupling in Section~\ref{sec:opportunity}: too little eviction leaves memory occupied, whereas excessive eviction or early allocation can make the schedule infeasible.
Host-copy policy, retained history, and transfer implementation remain fixed within each comparison.

\paragraph{Restoration on the critical path.}
\label{sec:eval-latency}
For each micro-turn, the analysis measures how much restoration finishes before its tick and how much delays computation.
Allocation waiting, copy-stream queueing, transfer time, and post-transfer scheduling are distinguished.
This decomposition tests whether the design removes recovery delay or moves it to an earlier queue.

\subsection{History Growth and Plan Revision}
\label{sec:eval-model}

Admission predictions are compared with execution over configurations and traces not used for calibration.
The comparison covers per-period KV growth, transfer duration, computation time, and peak allocation.
Prediction error is reported against the horizon and scheduling margins used to make the admission decision.

Continuous runs span multiple planning horizons to test service beyond the initial admission decision.
One experiment keeps the session population fixed while histories grow; another introduces departures and new admissions.
Together they distinguish gradual correction from population changes.
The relevant outcomes include revision frequency and cost, service around each revision, and the treatment of sessions when a new feasible plan cannot be found.

\label{sec:eval-correctness}

They exercise state round trips and overlapping demand, restoration, eviction, and plan changes.
For copying, the correctness criterion is preservation of KV content; any recomputation path additionally requires a numerical and output-equivalence criterion.
