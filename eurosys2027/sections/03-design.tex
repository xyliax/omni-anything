\section{System Design}
\label{sec:design}

\systemname turns the idle intervals identified in Section~\ref{sec:problem} into a recurring schedule for sharing GPU KV capacity.
The schedule couples three decisions: when each session's update is released, how much of its KV to evict, and when to restore that state.
Restoration targets the next tick so that the following update can use its period for computation.
Meeting this target removes a source of waiting; meeting the update's soft deadline also requires sufficient execution time after the tick.

\subsection{Architecture and Execution Cycle}
\label{sec:design-overview}

Figure~\ref{fig:design_overview} shows four logical components above the inference backend.
The \emph{residency planner} produces a plan at admission and revises it as resource demands change.
The plan specifies session groups and phases, per-session eviction budgets, and restoration timing.
The \emph{session manager} follows this plan, maintaining periodic progress and coordinating KV preparation with request submission.

The \emph{KV memory manager} carries out residency operations using the backend's allocation and reference state.
It identifies safely reclaimable blocks, obtains restoration destinations, and tracks which GPU and host copies are valid.
The \emph{KV transfer engine} executes the resulting asynchronous copies and reports their outcomes.
The inference backend schedules submitted work and performs model computation, including batch formation when used.
Thus, the planner selects the residency schedule, while the other components enforce it against actual execution and memory state.

Consider a session in group C whose idle KV has been partially evicted.
At the planned restoration time, the session manager requests its missing state.
The memory manager obtains the destination space, and the transfer engine copies the state from host memory.
Once all historical KV required by the next update is valid on the GPU, the memory manager reports readiness.

The session manager submits the update when its tick has arrived, its input is available, and any conflicting prior execution has finished.
During computation, newly retained KV can enter the incremental host-backup path.
After computation, safely backed and unreferenced ranges can be released again, supplying space for later restorations.
This is the cyclic reuse illustrated in Figure~\ref{fig:comparison}(b).

\subsection{Session Groups and Phase Assignment}
\label{sec:design-offsets}

Phase assignment uses the timing flexibility allowed by the application.
For sessions with a common period $T$, \systemname divides the period into $S$ evenly spaced slots.
Session $i$ assigned to slot $j$ has phase $\phi_i=jT/S$, for $j=0,\ldots,S-1$, and ticks
\[
  r(i,k)=t_0+\phi_i+kT,
\]
where $t_0$ is the common time origin and $k$ indexes updates.
Sessions in the same slot form a \emph{session group}; they share a release phase but retain separate histories and eviction budgets.
The group organizes residency scheduling, while the backend selects execution batches from eligible work.
Uniform spacing distributes release times without guaranteeing equal transfer demand or simultaneous execution within a group.

\paragraph{Trading batching efficiency for memory reuse.}
Aligning every session to the same phase makes more work available for batching, but also concentrates demand for resident KV and restoration.
Staggering groups distributes that demand and lets their eviction intervals supply space for one another.
It can reduce batch sizes and increase total execution cost through additional model iterations and weight accesses.
Assigning multiple sessions to each slot retains opportunities for batching.
For $N$ sessions in roughly balanced groups, each phase releases about $N/S$ sessions, although actual batches depend on the backend and current readiness.

The goal is to preserve the service target while reducing peak memory use.
Let $C_{\mathrm{aligned}}$ and $C_{\mathrm{grouped}}$ denote the complete periodic execution costs for the two release patterns at the same history length and workload.
The extra cost $C_{\mathrm{grouped}}-C_{\mathrm{aligned}}$, together with transfer interference and scheduling delays, must fit within the original margin $T-C_{\mathrm{aligned}}$.
The short generation bursts described in Section~\ref{sec:request-classes} motivate this tradeoff; admission must check execution costs under the candidate grouping and each session's deadline.
Initial phase-alignment waiting is recorded separately, and later submission delays do not move the ticks.

\subsection{Joint Residency Planning}
\label{sec:design-planning}

The planner sizes each session's KV demand at the maximum context length configured in the model and backend.
Input and generation must respect that limit, including all positions retained by the reference history policy.
This approach accounts for future state growth when selecting the recurring schedule.
It can admit fewer currently short sessions, but allows the plan to be reused as their histories grow within the limit.

The planner combines this demand with session periods, execution costs under the configured workload and candidate groupings, GPU KV capacity, host capacity, and effective transfer service.
Its output couples group assignments, per-session eviction budgets, and restoration times within the recurring schedule.
Planning at maximum context does not require every session's KV to remain resident simultaneously; runtime copies and allocations cover only existing state.
A candidate must fit the complete workload's compute budget and each session's deadline, as well as the time and space constraints below.
As Equation~\ref{eq:memory-gain} shows, using more transfer bandwidth is useful only if the resulting eviction intervals reduce peak GPU allocation.

\paragraph{Eviction budgets.}
An eviction budget $e_i$ limits the bytes of safely recoverable KV released from session $i$ in a cycle.
It need not cover the entire history.
As Section~\ref{sec:opportunity} shows, full eviction becomes infeasible when the retained state exceeds the available restoration budget.
Partial eviction keeps the excess resident and gives the planner control over each restoration's duration and destination size.
A useful budget must free enough memory to matter while leaving a feasible return path.

\paragraph{Restoration timing and space.}
For the restoration preceding tick $r(i,k+1)$, let $u_i$ be the planned trigger time and $\widehat B_i$ the estimated effective bandwidth available to that restoration.
A budget check takes the form
\[
  u_i+\frac{e_i}{\widehat B_i}+\delta_i\le r(i,k+1),
\]
where $\delta_i$ accounts for queueing, completion handling, and a safety margin.
These estimates must describe a feasible shared transfer schedule: independent estimates that each assume the full link bandwidth are insufficient.
Equation~\ref{eq:transfer-budget} supplies an aggregate necessary condition, while individual recovery windows constrain the order and timing.

Space must be available when a restoration obtains its destination, even though the copy has not finished.
The planner therefore accounts for each entire destination from allocation until release, together with resident history and newly generated KV; shared physical blocks count once.
Total allocation must remain within $G_{\mathrm{KV}}$ throughout the recurring schedule.
An earlier restoration gives the transfer more time but shortens the interval during which its state frees GPU space.
The plan must consequently match releases by preceding groups to allocations for upcoming groups, accounting for state and host-copy storage at the configured context limits.

\subsection{Safe Eviction and Scheduled Restoration}
\label{sec:design-idle}
\label{sec:design-correctness}

Runtime execution enforces the plan without treating predicted availability as permission to access or free a block.
The memory manager distinguishes physical allocation, valid content, and references from computation or copying.
Three steps govern the transition from idle state to the next update.

\paragraph{Backing and releasing state.}
Incremental host backing runs during inference as newly retained blocks become safe to copy.
Each session can accumulate such blocks and issue asynchronous D2H copies without waiting for its entire update to finish.
Completed host copies of unchanged history are reused across cycles, so later backups cover newly retained state rather than repeatedly copying the whole history.
The memory manager extends valid host coverage only after a successful copy.

Backing up KV does not itself reclaim GPU space.
After an update completes, the memory manager checks the ranges selected for eviction against the budget and restoration plan.
A block can be released only if its host copy is valid and all execution, sharing, and transfer references permit reclamation.
If a copy or reference is still outstanding, reclamation waits; only space actually released becomes available for reuse.
These checks preserve the selected history while making its idle GPU allocation available to other sessions.

\paragraph{Allocating and copying.}
\label{sec:design-prefetch}
At the planned restoration time, the memory manager checks which required ranges remain missing and confirms their host coverage.
It allocates the complete missing destination for one session before submitting H2D copying, potentially using space released by another group.
The transfer engine queues H2D copies in the plan's session order; incremental D2H copies may overlap them.
Several sessions can have complete destinations allocated while their copies await execution or completion.
This choice avoids reserving an entire group's destinations before its first session can restore, at the cost of additional allocation decisions and possible waiting between sessions.

If the complete target cannot be allocated, the operation waits without holding a partial destination or reserving space for later sessions.
Resource changes trigger retries; the runtime reports a timing risk when waiting threatens the planned recovery window.
It does not bypass the blocked session under the current plan.
This policy can cause head-of-line blocking, so the planner must check the resulting order and allocation timeline.
Every allocated destination counts toward capacity immediately, including completed restorations waiting for their ticks.

\paragraph{Resuming computation.}
On successful transfer completion, the memory manager validates the operation's identity and publishes the corresponding GPU ranges as valid.
It reports KV readiness only when every historical range required by the update is available.
Readiness is per session: a restored session need not wait for the rest of its group before becoming eligible for submission.
Cancellation, duplicate requests, or plan changes cannot allow an old completion to publish state for a different operation or session.
Readiness checking and acquiring execution references must be coordinated with eviction so that submitted work retains access to its state.

KV readiness and the tick are separate conditions for submission.
An early restoration waits for the tick and the update's other execution conditions; a tick that arrives before restoration finishes leaves dependent computation waiting.
On-demand restoration can recover missing state, but the resulting delay remains part of latency measured from the original tick.
A missed timing target never permits computation to read unfinished KV.

\subsection{Plan Reuse and Revision}
\label{sec:design-revisions}

The planner reuses a plan as histories grow within their configured limits and revises it when sessions arrive or depart.
Context growth alone does not require periodic replanning.
Existing sessions keep their phases and the current slot grid; the revision changes future eviction budgets and restoration timing and places new sessions on that grid.

To activate a candidate, the runtime pauses new restoration allocations and lets operations with allocated H2D targets finish or settle safely.
It then rechecks the candidate against current allocations and references, including the time needed for the transition.
If the check succeeds, it advances the plan version and replaces only operations that have not started.
Computation and D2H backing can continue across the transition, with their references and completion events preserved.
This boundary simplifies switching but can add waiting to the restoration queue.

If a candidate cannot accommodate a new session, admission is rejected and the existing plan remains in use.
Blocked allocations wait for resource events, and copy or execution errors follow the existing error paths.
Updates retain their original ticks, so recovery waits remain visible in the measured completion latency.
