# Reviewer-Facing Audit

## Thirty-Second Test

- [ ] The title names the object and the distinctive idea.
- [ ] Figure 1 makes the failure and opportunity understandable without reading the full paper.
- [ ] The first page states who benefits, why the problem appears now, and why existing control is insufficient.
- [ ] A reviewer can repeat the paper's one-sentence story without naming implementation details.

## Systems Contribution Test

- [ ] The workload assumption is explicit and externally meaningful.
- [ ] The resource bottleneck is demonstrated, not inferred from a queue failure.
- [ ] The system has a unified design principle rather than a list of patches.
- [ ] Mechanisms are independently ablatable.
- [ ] Correctness and fallback behavior are explained.
- [ ] The evaluation crosses the claimed resource regime and exposes where the method stops helping.

## Evidence Test

- [ ] Every headline number resolves to formal evidence.
- [ ] Baseline, offered workload, executed work and scheduling controls are matched.
- [ ] Tail behavior and uncertainty are reported.
- [ ] Costs include GPU memory, host memory, HBM/compute effects and host-device traffic as applicable.
- [ ] Generalization wording matches the hardware and model coverage actually tested.

## Rejection-Risk Test

- [ ] Closest-work novelty is not merely a feature difference.
- [ ] The paper does not overclaim full-duplex audio behavior from a Thinker-only path.
- [ ] Implementation fixes and measurement instrumentation are not presented as mechanisms.
- [ ] The resource model is calibrated and validated before being used for extrapolation.
- [ ] Optional prefetch benefits do not carry the entire paper unless formal evidence supports them.
