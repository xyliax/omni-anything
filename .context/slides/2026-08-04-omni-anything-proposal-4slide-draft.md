# Omni-Anything

## 面向 Agent 双工交互的推理系统

## Slide 2｜项目目标：构建 Agent 的通用交互能力层

### 页面标题

# 从“会完成任务”到“能持续参与真实世界”

### 核心目标

**构建一套与 Agent 智能内核解耦的 Omni Interaction Runtime，将任意 Agent 的推理与工具能力，稳定投射为实时、连续、可中断、可持续的多模态交互。**

### 三项能力目标

#### 1. 通用接入｜Any Agent

- 通过标准适配层连接 jiuwenswarm 及异构 Agent / Tool / API
- 不修改 Agent 的核心推理逻辑，不依赖模型权重训练
- 前台交互模型与后台 Agent 可独立演进、灵活替换

#### 2. 原生双工｜Always Interactive

- 输入与输出并行：边听、边说、边思考、边调用工具
- 以真实播放进度定义上下文，正确处理打断、撤回和结果作废
- 后台任务异步返回后，可在不中断前台交互的情况下回注结果

#### 3. 可部署性能｜Production-Ready

- 支撑长时、多会话、低抖动运行，而非单次 Demo
- 在有限 GPU 容量下保持实时 deadline 和可接受的单路成本
- 形成可迁移到 GPU / 昇腾等平台的 runtime、状态协议和执行机制

### 底部结论条

> **项目交付的不是一个新的语音模型，而是 Agent OS 时代可复用的实时交互基础设施。**

### 版式建议

- 上半页放“一句话目标”；下半页放三张能力卡片：通用接入 / 原生双工 / 可部署性能。
- 三张卡片上方可以画一条能力链：

  `Agent Intelligence → Omni-Anything → Real-Time Interaction`

### 这一页怎么讲

项目把“智能能力”和“交互能力”解耦。Agent 负责想什么、做什么；Omni-Anything 负责何时听见、何时说出、何时撤回、状态如何持续，以及这些行为如何以可接受成本运行。语音双工是第一阶段的可测载体，架构面向更一般的多模态事件流。

## Slide 3｜研究问题：传统推理系统为何支撑不了原生双工 Agent？

### 页面标题

# 从一次性“请求”，到持续存在的“交互过程”

### 场景图

```text
用户 / 环境
   ⇅  连续输入、实时输出、随时打断
前台 Omni 模型  ⇄  Omni Interaction Runtime  ⇄  后台 Agent / Tool / API
   ⇅  固定节拍                         ⇅  异步、长时、结果可作废
```

### 核心研究问题

**如何在不重训 Agent 的前提下，把请求式推理引擎改造成一个满足真实时间因果、承载长期状态、且成本可控的持续交互系统？**

### 三个结构性矛盾

#### ① 长期状态 vs. 有限显存

双工会话没有轮次间隙，模型的会话工作状态（KV Cache）随输入持续增长、每拍都要访问。系统往往不是先把 GPU 算满，而是先被状态塞满。

> 真栈实验中，KV 池满后系统进入饥饿，而 85% 的 GPU 采样仍为 0% SM utilization。

#### ② 微小周期工作 vs. 通用动态引擎

每个交互拍的有效计算很小，却反复支付动态组批、算子发射、内存规划和形状适配成本；通用性开销反而成为主要成本。

#### ③ 并行交互语义 vs. 串行生成接口

用户输入、模型输出和 Agent 结果在真实时间中并行发生；传统引擎却按串行 token 顺序组织状态，既可能让模型“看到尚未播出的内容”，又会重复扫描同一份历史。

### 底部结论条

> **需要共同解决三个瓶颈：状态容量、执行控制、数据移动；任何单点模型优化都不足以构成完整的双工 Agent runtime。**

### 版式建议

- 左侧占 40%：画“用户—前台—runtime—Agent”的闭环图。
- 右侧占 60%：用三条“结构性矛盾”解释为什么传统 serving 不够。
- `KV Cache` 首次出现时加小字解释：“模型为会话历史保留的工作状态”。

### 这一页怎么讲

评审不需要先理解所有底层术语，只需要抓住一个变化：普通聊天服务处理的是短暂请求，Omni-Anything 处理的是持续存在、事件驱动、带物理时间约束的交互过程。持续状态、固定节拍和真实播放因果同时出现后，传统引擎的三项基本假设一起失效。

## 三个研究点：面向agent前台双工交互的推理系统

### 页面标题

# 从“能双工”到“能持续、稳定、高效地双工”

### RP1｜状态容量

## 持续双工会话的 KV 状态虚拟化与请求编排

**问题：** 多路会话的 KV 状态持续增长，GPU 算力远远未满就先撞显存墙；Agent 回注和打断还会制造大量失效状态。

**方法：** 利用交互节拍的可预测性，把尾部 KV 母本放在主机内存，通过相位指派和 deadline-aware DMA 时刻表，在每拍前搬入、算后释放；配合未提交 / 提交 / 作废状态机管理 Agent 结果。

**目标：** 以算力和带宽换显存，将物理 KV 容量 `M` 扩展为等效容量 `M + P`，支撑更长、更高密度且无损的实时会话。

`State Virtualization · KV Conveyor · Transactional Injection`

### RP2｜执行控制

## 面向周期交互的静态执行计划特化

**问题：** 每拍计算很小，却不断落入通用动态路径，反复支付组批、CPU 发射、内存规划和形状适配开销。

**方法：** 由 runtime 主动把拍类型、会话相位和批组成约束成有限签名族，对每类交互拍执行 AOT 图捕获、注意力元数据固化、KV 动作编排和工作区预分配。

**目标：** 把“在线逐步规划”变成“预编译计划重放”，降低每拍延迟和抖动，提升跨 GPU / 昇腾平台的可预测执行能力。

`Interaction Process Compilation · AOT Execution · Finite Signatures`

### RP3｜数据移动

## 面向同请求共享上下文的 Prefill–Decode 融合

**问题：** 同一交互拍内，模型一边读入新信息、一边生成输出，两条路径会重复扫描同一份会话历史；简单串行化还可能破坏真实播放因果。

**方法：** 以播放前沿定义时间对齐掩码，将共享同一历史快照的 Prefill 与 Decode 合并执行，并通过分支 `fork / commit` 生命周期保证打断和回注后的状态正确性。

**目标：** 在不改变模型语义的前提下减少重复 KV 访存，降低同拍关键路径和首字延迟。

`Causality-Aware Fusion · Shared-History Scan · Playback Frontier`

### 三点共同底座

> **双工时间轴协议 + 可撤销 KV 状态机**：统一描述输入何时可见、输出实际播到哪里、Agent 结果何时返回，以及状态何时提交或作废。

```text
RP1：让状态装得下       RP2：让每一拍跑得轻       RP3：让历史少搬一次
      长时多路承载   +        稳定低抖动执行   +        低延迟同拍计算
```

### 版式建议

- 主体使用三列等宽卡片，分别标注 State / Execution / Data Movement。
- 每列严格保留“问题—方法—目标”三行；英文关键词作为小号技术标签。
- 底部用一条横向底座承托三列，写“双工时间轴协议 + 可撤销 KV 状态机”，强调三点属于同一 runtime，而不是三项零散优化。

### 这一页怎么讲

三个研究点对应三个不同层面的系统税：RP1 扩展状态容量，RP2 消除动态控制开销，RP3 消除同一请求内部的重复数据移动。它们共享同一时间轴和状态机，最终共同支撑“任意 Agent 的免训练、可持续、性能可接受的原生双工交互”。

## 全稿统一口径

- 主标题讲 **Agent 的通用实时交互基础设施**，不要讲“语音 serving 优化项目”。
- 语音双工是首期载体；`omni` 表示能力层可连接持续多模态事件，而不是承诺一期覆盖所有模态。
- “免训练”明确指**无需为接入的 Agent 重新训练模型权重**，不等于系统无需配置、标定或适配。
- RP1 的约 20% PCIe5/480ms 容量增益仍是闭式预测，未在这四页中写成已完成结果。
- 对非领域评审，三个记忆点应保持一致：

  1. 不是重新造模型，而是给任意 Agent 补一层交互基础设施；
  2. 双工交互把“请求”变成带真实时间的持续过程；
  3. 三个研究点分别解决状态、执行和数据移动问题。
