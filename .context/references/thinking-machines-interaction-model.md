# Thinking Machines 交互模型：公开测试案例与机制分析

Updated: 2026-08-06

## 核心结论

Thinking Machines Lab 的《Interaction Models: A Scalable Approach to Human-AI Collaboration》展示的不是一组普通语音助手演示，而是一组实时交互测试案例。核心变化是：模型和用户共享同一条时间线。用户说话、停顿、动作、画面变化、模型语音、模型沉默、搜索结果和界面更新，都可能成为下一步动作的条件。

带音轨的 MP4 是分析公开视频的最好载体。它一次保留音频、画面、字幕、界面和相对时间关系，比把音频和视频分开分析更接近这些演示本来的交互形态。本地读回覆盖 10 个 YouTube 演示，以及 Figure 8 中 Example 1 的带音轨合成视频；Figure 8 其他四个标签页官方没有发布公开视频，只能依据音频资源和页面配置分析。

用户输入不能一律看成同一种东西。公开视频里的音视频轨迹可以作为固定回放，用来评价模型在给定观察流上何时该说、该说什么；但部分任务的产品语义是干预型的：真正上线时，模型输出会影响用户后续说话、动作、注意力或界面关注点。区分时要同时看录制回放协议和实时交互语义。

## 交互模型机制

Turn-based 模型把交互压平成一条有序序列：

```text
user turn 1 -> model turn 1 -> user turn 2 -> model turn 2
```

Interaction model 把交互锚定在时间上。输入流和输出流都被切成 micro-turn，每个时间片都可能包含音频、视频、文字、沉默、模型语音或模型沉默：

```text
t0: user A/V/text chunk + model speech/action chunk
t1: user A/V/text chunk + model speech/action chunk
t2: user A/V/text chunk + model speech/action chunk
```

两种界面的区别可以画成这样：

```text
turn-based                                   ||     interaction model
------------------------------------         ||    -------------------------------------
用户说完一整轮                               ||     用户音/视/文持续流入
模型在边界之后才开始                         ||     模型可以等待、说话或插话
模型不输出时感知冻结                         ||     模型说话时仍持续听
工具结果作为下一轮内容返回                   ||     工具结果作为实时事件到达
```

这让模型可以自己判断等待、backchannel、插话、停止说话、边听边说、根据视觉事件主动提醒，并把后台搜索或界面结果带回前台。沉默不再是空白，重叠说话不再只是异常，后台结果也不只是下一轮 prompt 里的附加文本。

这篇博客的关键主张可以概括为：交互能力应该内化到模型的时间上下文里，而不是完全交给外部 VAD、停顿规则、打断按钮、tool-calling scaffolding 或界面层状态机。

```text
   └─ Coach in your ear
```

## 用户输入是否受模型输出影响

判断用户输入是否受模型输出影响，需要分清录制证据和实时交互语义。公开视频本身都是固定轨迹：音频、视频、用户动作和用户后续语音已经录好，可以回放给另一个模型，观察它在同一条输入流上何时该说、该说什么、何时该沉默或插话。实时交互语义则不同：部分例子把模型输出当成干预，模型一旦说错、漏说、晚说或生成不同界面，用户后续说话、动作、注意力或工具上下文就可能改变。

```text
官方视频证据                               ||     实时产品语义
------------------------------------       ||    -------------------------------------
录好的用户音视频                           ||     用户/环境状态持续演化
候选模型据此响应                           ||     模型输出成为干预
后续输入仍按录像走                         ||     后续输入可能依赖输出
评价时机与内容                             ||     评价干预后的轨迹
```

固定回放会出问题的地方，不是模型不能看视频，而是后续输入可能本来是在回应原演示模型。另一个模型说了不同的话、生成了不同界面、搜到了不同结果、没有提醒或提醒延迟时，固定后续用户输入仍然照旧播放，就会变成「用户在回应另一个模型」。

官方例子的实时语义可以按干预强度理解：

| 干预强度 | 官方例子 | 读法 |
|---|---|---|
| 最强 | Coach in your ear | 私密提示直接改变用户公开说法，后续公开对话会成为下一步输入。 |
| 强 | Diet manager | 模型提醒应改变用户拿起、放下或接受的食物，并处理用户纠错。 |
| 工具/界面闭环 | Search、Generative UI、Introducing interaction models 的搜索/界面段 | 模型搜索、追问和界面生成会改变用户后续关注点和问题。 |
| 条件型 | Audio interjection、Visual interjection、Time-awareness | 只测输出时机和内容时可固定回放；若评价用户是否改计划、坐直、停止活动，就进入干预语义。 |
| 较弱 | Dialog management、Simultaneous speech、Figure 8 各例 | 更像跟随、转换、计时或状态报告；用户后续输入主要可视作外生轨迹。 |

如果只想找官方最强反馈环例子，应先看 `Coach in your ear`。它的反馈链最短：私密提示改变用户下一句公开表达，改变后的公开对话又会变成模型后续输入。`Diet manager` 是第二强，但它更依赖物理行为是否真的被模型提醒改变。

## 逐条案例分析

### Introducing Interaction Models

发生了什么：一位用户先让模型在朋友进入画面时说 `Friend`。第一位朋友进入画面后，模型根据视觉线索立即发声。随后朋友用印地语发言，模型几乎同时输出英文同传。第二位朋友加入后询问人类对听觉、视觉、触觉刺激的反应时间，模型边对话边搜索并给出数值。最后用户要求把数据画成柱状图，模型生成可视化时继续回答「为什么听觉反应比视觉快」的追问。

测试点：这是总览演示，把视觉触发、同时说话、搜索、后台任务和 Generative UI 放在一个连续交互里。它展示 interaction model 不是单一能力，而是前台实时对话和后台异步工作共同组成的协作界面。

用户输入影响：混合。`Friend` 触发和同传段可以作为固定轨迹回放；搜索、澄清和生成图表段里，后续用户话语依赖模型问题、搜索结果或界面状态。公开视频展示的是一条交互轨迹，不足以证明每个后续动作都由模型输出驱动。

机制：一个交互过程里同时出现视觉事件、语言输入、模型语音、搜索调用和界面更新。模型需要把它们看成同一条时间流里的事件，而不是多个互相隔离的功能模块。

### Dialog Management

发生了什么：用户要求模型听动物词并立即计数，然后开始讲故事。她中途喝水，模型识别出她还没讲完并保持沉默。后续故事中出现 `deer`、`sheep`、`coyote`、`capybara` 时，模型分别插入 `One`、`Two`、`Three`、`Four`。故事结束后，模型根据上下文判断话轮结束并总结总数。

测试点：模型不能只用静音长度判断 turn boundary。喝水、故事结构、用户语义目标和短插话任务都要同时进入上下文。模型的动作不是简单的「回答」或「不回答」，而是在等待、短计数、继续听和最终总结之间切换。

用户输入影响：弱。用户在模型计数后继续讲故事，没有明显改变故事方向。这个案例更像测试模型输出不破坏用户持续输入，而不是测试模型引导用户改变输入。

机制：沉默也是动作。错误地在喝水停顿时接话是不合适的；在线索出现后低延迟短反馈是合适的；故事结束后的主动总结需要依赖语义上下文，而不是固定的 VAD 规则。

### Visual Interjection

发生了什么：用户告诉模型，如果自己开始驼背就提醒。她在电脑前工作时前倾、歪头、再次驼背，模型每次根据画面主动提醒；用户听到后立刻坐直或摆正头部。模型也会在姿态改善后给出正向反馈。

测试点：视觉流本身能触发模型输出。用户不需要再次说话，模型也不能等到一个文本回合结束后再判断。它测试持续视觉状态跟踪、主动插话时机，以及干预型提示是否在合适时刻出现。

用户输入影响：从固定视频本身不能证明。这个例子可以作为 open-loop replay：用户姿态变化可以预先录好，模型只需在正确时间提醒。若要证明提醒真的让用户坐直，需要真实用户或 user simulator 参与，让后续姿态依赖模型是否提醒、何时提醒、怎么提醒。

机制：这个任务的产品语义是干预型，但公开视频可以退化成固定轨迹测试。合格行为首先要识别姿态并及时提醒；若要评价提醒后的用户反应，还需要 closed-loop 协议。

### Audio Interjection

发生了什么：用户说想带年长父母骑山地车。模型不等用户说完整段计划就插话劝阻，指出危险。用户随后改提更稳定的双人自行车，又提到活火山。模型再次打断，强调活火山危险。用户笑着转向吐槽模型不想让他玩得开心。

测试点：模型要在用户没说完时判断「继续等」还是「现在打断」。触发信号来自语义风险，而不是视觉事件。模型如果等到完整 turn 结束，安全干预就太晚；如果过早打断，又会显得粗鲁。

用户输入影响：语义上是干预型，但固定视频本身不是反事实证明。它可以回放成「模型是否该在危险的 partial utterance 上打断」的 open-loop 测试；若要测用户是否因打断而改计划，需要 closed-loop 用户或 user simulator。

机制：插话判断同时包含语义理解、风险估计和社交时机。模型是在 partial utterance 上行动，不能依赖完整转写之后才知道的内容来决定当时是否应该打断。

### Simultaneous Speech

发生了什么：用户要求模型把他说的话实时改写成人力资源话术。用户持续抱怨同事迟到、影响团队、可能需要睡在办公桌上；模型在用户仍在说话时同时输出积极、专业、委婉的人力资源版本。

测试点：模型输出时感知没有冻结。它一边发声，一边继续听用户后续内容，并把用户持续输入转换成另一种语域。这里的重点不是最终回答质量，而是低延迟、重叠说话、语速匹配和声音分离。

用户输入影响：没有直接证据。用户说话节奏基本稳定，像在按预设脚本连续输入；模型输出并没有明显改变用户后续内容。

机制：同时说话要求模型把「自己正在说什么」和「用户同时在说什么」都放进上下文。滞后太多会失去实时性，提前太多又会因上下文不足而改写错误。

### Time-awareness

发生了什么：三位用户要求模型快速回答 trivia，同时设定 30 秒倒计时，到点说 `Time's up`。他们快速、部分重叠地提问，模型边回答前一个问题边听下一个问题。计时到点时，模型打断当前节奏宣布时间到，三人停止继续问答并笑起来。

测试点：时间本身是状态。模型不是只响应用户话语，还要根据真实经过时间主动发声。这个演示同时测试多说话者、快速问答、重叠输入和定时抢占。

用户输入影响：固定视频本身不能证明。`Time's up` 在任务语义上是活动边界提示，但这段视频可以回放成「模型是否在 30 秒时正确发声」的 open-loop 测试；用户停止提问是否由模型输出造成，需要反事实协议。

机制：内容正确但晚了几秒，在这个任务里仍是失败。交互评价必须同时看说什么和什么时候说。

### Generative UI

发生了什么：用户要求把 Uber 最新财报成本可视化。模型先澄清想看特定季度还是整体趋势，同时屏幕开始生成 `Uber Q1 2026` 指标卡片。用户回答只看整体趋势。旁边用户在图表构建过程中插话，请模型顺便讲今年其他业务表现。模型继续生成柱状图，同时口头回答外卖和出行业务表现。

测试点：界面是并行输出通道。模型不是停下语音去生成网页，也不是等界面完成后再回答；它在同一段交互里维护语音对话、用户插话和可视化生成进度。

用户输入影响：后续语音明显引用模型澄清问题和界面状态，因此比姿态提醒更依赖交互上下文。但如果把整段用户音视频录死，它仍然只是固定轨迹评测，不能验证模型生成不同界面时用户会如何改问。

机制：界面更新也是交互状态的一部分。用户会根据正在生成的界面继续说话，模型也要在界面生成未完成时继续听和回答。

### Search

发生了什么：用户聊 `Devil Wears Prada 2` 的票房和观影感受。模型识别这是需要新信息的时事话题，边对话边搜索，给出票房数值，并反问用户是否喜欢 Andy 回归。用户接着聊 Lady Gaga 客串和结局，然后请求推荐相似且正在上映的电影。模型一边说「我来找推荐」，一边搜索并给出推荐结果。

测试点：搜索不是独立回合，而是实时对话中的后台动作。模型要判断何时需要搜索、搜索结果何时仍相关、是否先用语音保持对话、结果回来后如何自然插入。

用户输入影响：后续话题沿着模型追问和搜索结果展开。固定回放可以测模型是否能处理这条轨迹；真正 closed-loop 评测还要允许模型搜索结果或追问不同，并观察用户如何继续。

机制：tool call 是交互流里的异步事件。模型不能简单停住等待工具，也不能在没有证据时编造；结果回来后还要判断现在是否仍该说、是否应该等用户说完、是否已经过时。

### Diet Manager

发生了什么：用户要求模型帮他避开咖啡因和甜食。桌上有咖啡杯、绿茶、Pocky、水果。模型看到黑色杯子后提醒可能是咖啡，用户随后放下杯子。用户拿起绿茶罐时，模型先警告可能含糖或咖啡因；用户插话解释是无糖绿茶，模型更新判断。旁边用户递出 Pocky，模型立即劝阻；她换成青苹果，模型认可。

测试点：偏好约束来自用户语音，触发信号来自视觉物体和动作，纠错信号来自用户插话。模型要持续把「我正在减肥、避开咖啡因和甜食」这个目标绑定到视频中的物体选择上。

用户输入影响：产品语义是强干预型，因为模型应影响用户拿什么、放下什么、如何纠错。但公开视频仍可被当成固定物体轨迹回放；要评估干预是否真的改变选择，需要让用户或环境按模型输出动态反应。

机制：这个任务的产品语义是物理干预和纠错恢复。固定回放能测识别、提醒时机和误报恢复；closed-loop 协议才测模型输出是否真的改变用户选择。

### Coach in Your Ear

发生了什么：两人面对面聊天。女子说自己喜欢吃 `acai bowls`，但发音错误。模型只通过她的耳机轻声纠正发音，女子立即改口。随后她说 acai 来自 Argentina，模型再次通过耳机提示实际来自 Brazil，女子立刻向对方改口。

测试点：模型输出可以是私密旁路，不一定进入公共对话声道。它要识别发音和事实错误，并在不破坏双人谈话的情况下只提示一个参与者。

用户输入影响：产品语义是强干预型，因为私密提示应改变用户的公开说法。固定录制可以测模型是否在应提示处提示；closed-loop 评测才测提示缺失、提示错误或提示延迟时，用户公开对话会怎样变化。

机制：交互状态需要区分谁知道什么、谁能听到什么。模型动作也有接收者。这个演示的关键不是「大声回答正确答案」，而是只把提示送到合适的人，并让她自然接回对话。

### Figure 8 Example 1

发生了什么：用户面对摄像头说：看我的手，持续报出我伸出的手指数，每次变化都更新。模型确认后，用户依次展示 5、2、10、9、4、2、1、4、5、10 根手指；模型逐次播报 `Five fingers up`、`Two fingers up`、`Ten fingers up` 等。

测试点：这是视觉状态跟踪和事件驱动输出。模型不能每一帧都说话，也不能只看最终帧；它要判断手势何时变化，并在变化后及时发声。

用户输入影响：没有直接证据。用户按自己的节奏改变手势，模型像在线跟踪器一样响应。这个案例更接近单向高频感知和状态报告。

机制：这个例子的难点不是回答「图里有几根手指」，而是持续观察、识别变化边界，并只在变化发生后发出及时、正确的短反馈。

## Figure 8 音频例子

Figure 8 的五个标签页更像 benchmark 风格的定性样例。Example 1 有视频；Examples 2 到 5 只有音频和波形。

### Example 1：视觉状态跟踪

用户要求模型持续看手势，并在手指数量变化时更新。模型先确认，然后依次播报 5、2、10、9、4、2、1、4、5、10。它测试在线视觉状态跟踪、变化检测和及时口头更新。

### Example 2：即时语言插话

用户要求每当自己提到欧元金额时，模型立刻插话报美元换算，并设定 `10 euros = $11`。用户连续讲旅行开销，提到 20、30、100 欧元。模型不等整段结束，分别插入 `$22`、`$33`、`$110`。它测试 cue-triggered overlap，而不是事后总结。

### Example 3：线索触发分类

用户准备营养学考试，要求模型听到某个营养素时判断它是不是脂溶性维生素。用户在长句中抛出维生素 A、C、D、K。模型逐项回答 `Yes`、`No`、`Yes`、`Yes`。它测试模型能否在自然长话流中抓线索并立即短答。

### Example 4：真实时间回答

用户要求模型启动医学模拟秒表，并在被问到当前时间时精确报告已经过时间。用户操作中问当前时间，最后说 finish。模型回答 4 秒和最终 8 秒。它测试时间状态与用户事件绑定，而不是文本内容本身。

### Example 5：定时插话

用户说 30 秒后要离开，要求模型每 10 秒更新一次，并在最后说 `time to leave`，同时用户继续对孩子讲话。模型按节奏插入 `20 seconds left`、`10 seconds left`、`Time to leave`。它测试定时重叠说话：模型需要在用户话流中按真实时间插入短提示。

## Benchmark 解释

页面把这些例子放在交互性 benchmark 讨论附近。明确命名的维度包括 `TimeSpeak`、`CueSpeak`、`RepCount-A`、`ProactiveVideoQA` 和 `Charades`。稳妥理解是：Figure 8 给这些交互式能力提供定性例子，而不是在 HTML 里把五个标签页严格映射到五个 benchmark。

| Benchmark / 任务 | 测试什么 | 为什么重要 |
| --- | --- | --- |
| `TimeSpeak` | 模型能否在用户指定时间点说话，并说出正确内容。 | 内容正确和时间正确必须同时满足。 |
| `CueSpeak` | 模型能否在语义线索出现时说话，包括用户仍在说话的时候。 | 评价线索触发的干预和重叠说话。 |
| `RepCount-A` 改造 | 用户用音频要求模型数重复动作，视频继续流式播放。 | 评价持续视觉跟踪和及时口头输出。 |
| `ProactiveVideoQA` 改造 | 先流式播放问题，再播放视频；模型应等视觉证据出现才回答。 | 评价沉默、证据充分性和回答时机。 |
| `Charades` 改造 | 用户要求模型在动作开始/结束时分别说 start/stop。 | 把时间定位变成在线语音动作。 |

这些 benchmark 可以按主要压力源理解：

```text
benchmark 压力
├─ 何时说话
│  ├─ TimeSpeak
│  ├─ CueSpeak
│  └─ Charades 的 start/stop
├─ 证据是否足够
│  ├─ ProactiveVideoQA
│  └─ RepCount-A
└─ 如何保持因果
   ├─ 不能用未来转写
   ├─ 不能用未来视频帧
   └─ 不能只做离线「只评答案」计分
```

这些 benchmark 只是早期方向，不是完整的交互质量评价。真实交互还需要评价社交打扰、用户是否接受、私密旁路、后台任务陈旧性、跨模态延迟和长期上下文管理。

## 服务形态

Interaction model 的实时循环天然产生频繁的小输入写入和短输出生成。用户音频、视频、文字、模型输出、后台结果都按时间进入同一条会话状态：

```text
打开流式会话
  -> 追加新的前台 chunk
  -> 追加可选的后台结果
  -> 增量更新上下文
  -> 短响应或等待动作
  -> 重复直到关闭或超时
```

前台交互和后台工作不是两条互不相干的链路。后台结果返回后，仍要由 interaction model 决定怎样进入当前对话：

```text
用户流
  |
  v
interaction model ──────────────> 用户可见的语音 / 界面
  |                                    ^
  | 委托上下文                         |
  v                                    |
后台工作 ──── 结果事件 ────────────────┘
```

这种会话形态减少的是整段历史反复重算，不是不再处理新增上下文。新音频、新文字、新视频表示和后台结果仍要进入运行时上下文，只是处理范围是新增 chunk，而不是每个时间片都重新构造完整对话。

它和普通文字聊天的大 prompt 加长回答不同。双向交互更像很多活跃会话频繁执行小输入写入、小段输出、短等待和短插话；目标从单纯生成完整答案，转向保持前台交互低延迟、后台结果不过时、插入时机自然。

## 机制总结

第一，交互状态是按时间展开的共享活动流。只记录最终转写会丢失相对时序：模型说这句话时用户是否还在说话、是否已经改变动作、后台结果是否已经返回。

第二，模型动作不只是生成文本。等待、开始说、停止说、短反馈、插话、同时说话、定向提示、tool call 和界面更新都属于可见行为。

第三，时机是评价对象本身。内容正确但时机错是不同错误：太早会打断用户，太晚会错过安全或纠错窗口，重复输出会制造干扰，过度等待会让系统迟钝。

第四，在线交互需要保留因果可见性。时刻 `t` 的决策只能用 `t` 时刻已经可见的音频、视频、文字和后台结果来判断；用未来转写或未来帧倒推「当时应该插话」，会把在线任务变成离线任务。

第五，用户是否是固定输入源取决于评测协议。使用官方视频做回放时，后续音频、视频和动作都是固定轨迹；在真实交互协议里，模型输出可能改变后续用户输入、物理环境、纠错内容和界面注意力。不能只凭一条公开视频轨迹证明反事实因果。

第六，后台工作不是下一轮答案，而是异步到达的上下文事件。模型还要判断结果是否仍相关、是否应该马上说、是否应该等用户说完、应该用语音还是界面呈现。
