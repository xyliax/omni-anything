# docs 顶层文档的论文式写作审阅建议

## 1. 审阅结论与范围

当前五份顶层文档已经建立了清楚的职责分工：问题定义、系统设计、评估协议、证据解释与论文组织分别维护，原型配置也已集中到复现附录。多数段落能够区分假设、设计要求、实现与观察，并注意到周期可预测不等于偏移可控、调用返回不等于模型完成等关键问题。这些内容应当保留。

主要需要改进的是论证的连续性。部分章节先给出表格、检查项或写作指令，却没有解释这些材料共同支持什么判断；设计说明频繁在目标、候选动作与实现限制之间切换；结果按独立 finding 排列，读者需要自行拼出问题、机制与证据之间的关系。将这些材料转化为有主题句、因果解释和明确承接的段落，能够使文档更接近可用于投稿的研究底稿。

与此同时，部分提纲反映的是真实研究空缺。例如，最终完成事件与达标标准尚待定义，预取与偏移选择规则也未全部确定。这类空缺不能靠扩写补齐。建议把可以直接改写的表达与需要作者决定、实现或测量的内容分别处理。

本报告审阅 2026 年 9 月 10 日工作区中的 [problem.md](problem.md)、[system.md](system.md)、[experiments.md](experiments.md)、[findings.md](findings.md) 和 [PAPER.md](PAPER.md)，未将 `docs/papers/`、`docs/references/` 或论文写作目录纳入内容审阅。本报告也不构成源码审计、证据复算或文献库审查。五份原文在本轮任务开始前已有本地修改，本报告以读取到的本地稿为对象，不以 Git HEAD 的旧稿为对象。

本轮仅新增本文与[论文写作借鉴指南](writing-lessons-2026.md)，没有应用下列建议。本文是编辑建议，不建立新的项目事实入口，不改变实验配置、证据资格或研究范围。

## 2. 修改原则与优先级

这里的“论文风格”指读者能够沿正文理解对象、问题、原因、设计与证据。定义表、对照表、算法步骤和状态图仍然必要：它们适合精确表达并列内容。应优先改写的是承担主要论证、却只有动作词和片段的部分，而不是删除所有列表。

建议采用如下分工：正文解释研究关系，表格比较可并列的信息，复现附录记录影响实验解释的实例，Agent 层保存操作与治理。事实的维护位置仍遵守[根入口](../AGENTS.md)；文章式组织不要求把所有内容复制到一份“完整论文”中。

| 优先级 | 含义 | 审核后的处理方式 |
| --- | --- | --- |
| P1 | 影响读者对研究问题、设计或证据的理解 | 优先补足论证结构；涉及待定内容时先完成作者决策 |
| P2 | 影响可读性、简洁性和段落衔接 | 在不改变含义的条件下进行编辑 |

| 修改类型 | 含义 |
| --- | --- |
| 表达 | 现有含义基本足够，可以直接润色或连接段落 |
| 组织 | 保留材料与锚点，调整段落顺序、分组和正文／附录关系 |
| 研究依赖 | 需要新增定义、明确策略或补证据，不能用确定语气补写 |

下面的示范文字全部是建议稿。设计示例保持候选语气，方法示例保持计划语气；关于诊断证据的例子只使用无数字摘要，并链接现有 finding。它们不是已批准的正文替换。

## 3. 总体修改建议

### EDIT-G01：让每节首先回答一个研究问题（P1，组织）

五份文档的局部信息普遍可用，但部分节标题后直接进入表格或待办，读者尚不知道为什么需要这些材料。建议在每个主要表格前增加一个解释段：提出该节要解决的问题，说明选择这些比较维度的理由。表后增加必要的含义与下一节承接，而不逐行复述表格。

例如，机制表前可以解释“减少驻留、准备恢复和改变释放位置分别影响资源约束的哪一部分”；消融表前可以解释“怎样区分复制成本、逐出效果和提前信息价值”。这一做法借鉴 [Bidaw 与 InferCept 的组织方法](writing-lessons-2026.md)，使多个机制有共同目的。

### EDIT-G02：把连续的纠错句组织成正向定义与后果（P2，表达）

当前稿中的“不能”“不代表”“不保证”大多有必要，尤其用于防止过度主张。但连续出现时，读者先记住许多禁止解释，反而难以形成对象模型。建议先定义对象及其作用，再说明容易混淆的边界。例如，先解释目标分配会消耗空间、传输完成使内容有效、索引发布使内容可查找，再说明三者不能互相替代。

这种修改必须保留实质限制。涉及并发正确性、输入等待、证据资格的约束应留在相关论证附近；可以合并重复说明，但不能把全部限制移到文末，以至于正文看起来已完成验证。

### EDIT-G03：将待补事项写成具体的未决问题（P1，表达／研究依赖）

“待补：规则、算法、指标、实验”能够记录工作量，却不能让作者或读者判断补到什么程度才算完整。建议在相关段落末尾明确缺少哪项决策、它阻止哪一条主张，以及需要什么材料作出决定。例如，“待补预取排序”应进一步说明排序需要协调预计需求、目标空间与传输竞争，并指出当前尚无最终选择规则。

正文保留会改变研究结论的未决条件，文件末尾则用一张简短材料表汇总后续工作。具体运行命令和操作清单继续由原有操作层维护。这避免每个小节同时充当解释、实现日志和任务清单。

## 4. problem.md：保留严谨定义，增强属性到问题的递进

### 已经写得好的部分

[From Model Timing to Periodic Updates](problem.md#from-model-timing-to-periodic-updates) 明确区分规律节奏、信息可见与偏移可控；[Workload Model](problem.md#workload-model) 区分释放、提交、依赖计算与完成事件；[Resource Frontier](problem.md#resource-frontier) 区分物理分配与有效状态。这些内容直接防止错误问题设定，应作为后续润色的约束。

### EDIT-P01：缩短背景中的历史铺陈，突出与 KV 管理相关的属性（P2，组织）

定位：[Interaction Sessions and Their Timing](problem.md#interaction-sessions-and-their-timing)。当前段落从“对话、工具交互与双工体现了不同的交互组织方式”进入 ELIZA、ReAct 和双工模型实例。这些例子有助于纠正应用分类，但名称密度较高，历史 KV 与更新节奏的关系出现得稍晚。

建议保留分类表，将正文重点放在跨请求历史、等待结构与更新规律。ELIZA 可以缩为背景引用或移到现有来源节；ReAct 与双工模型只在其支持的具体属性旁出现。这里不是删除来源，也不是把某种应用排除出研究范围，而是减少与当前资源问题关系较弱的展开。

示范段落：

> 交互会话围绕共同历史持续推进，其状态生命周期可以跨越多次模型请求和外部操作。不同应用以不同方式组织这些更新：对话轮次包含等待用户的间隔，工具调用引入依赖等待，持续输入则要求系统不断跟进新内容。对 KV 管理而言，关键在于历史是否跨更新复用，以及下一次使用是否具有可获得的时间信息。以下比较这些时间属性，再说明哪些条件允许采用周期模型。

该段可以放在现有分类表之前。表后直接引出周期条件，不再重复完整分类。对应学习方法见 [Pensieve 与 SYMPHONY](writing-lessons-2026.md)。

### EDIT-P02：把三种时间条件与研究动作对应起来（P1，表达）

定位：[From Model Timing to Periodic Updates](problem.md#from-model-timing-to-periodic-updates) 与 [Why Timing Information Matters](problem.md#why-timing-information-matters)。当前“三个不同条件”的段落已经准确，但它与后面的预取机会相隔一个容量小节。建议在时间信息小节中用一两句回扣这三个条件，解释它们分别允许哪些动作。

可以写为：

> 当规律更新对服务系统可见时，系统可以据此估计后续状态需求；即使输入释放不可调整，这份信息也可能用于提前准备。只有应用进一步允许改变更新位置时，系统才可以选择释放偏移，以改变多会话需求的重叠结构。因此，评估需要分别检验时间信息本身的价值与控制释放位置的额外作用。

该段是对现有定义的承接，不声称每种条件均已找到代表工作负载。

### EDIT-P03：为资源公式补充物理含义与可行性层次（P1，表达／研究依赖）

定位：[Resource Frontier](problem.md#resource-frontier)。现有物理容量公式正确地约束任意时刻的已分配块集合，但后文主要列出尚需纳入的资源。建议先解释公式如何连接“完整历史”“驻留策略”和“恢复目标分配”，再解释为什么通过容量检查还不足以证明每次更新及时完成。

示范段落：

> GPU 容量约束限制任意时刻的物理分配。将空闲内容逐出能够回收其中一部分空间，而预取会在相关计算开始之前重新占用目标空间，因此峰值分配取决于逐出与恢复的时间安排。即使该峰值未超过容量，恢复仍可能因传输竞争或调度等待而迟到。资源分析需要同时检查空间是否可分配，以及所需内容是否能在使用前就绪。

在该解释之后保留明确待补项：批处理成本、传输服务、主机容量及其可行性条件。本轮不建议补入未经验证的闭式并发上限、均匀偏移最优性或跨设备缩放结论。主目标可以在定义完成后用统一目标函数表达，不能先为版式完整而写公式。

### 建议的章节顺序

可沿用现有大部分标题，按“会话历史与时间属性—周期抽象成立条件—容量矛盾—时间信息的机会与代价—形式化对象与服务目标—资源约束—适用条件”递进。术语表与来源说明保留为查阅部分。该调整主要补充承接，不要求重写整份问题定义。

## 5. system.md：从要求与机制目录推进到设计论证

### 已经写得好的部分

设计目标包含历史、引用、内容就绪和资源记账等要求；逻辑图明确标出候选接口；[Implementation Boundary](system.md#implementation-boundary) 明确当前触发与候选未来节奏预取的差异。这些区分对正在进行的研究很重要。建议保留它们，而不是为了论文语气改成完成式。

### EDIT-S01：在不变量列表前解释整体设计思路（P1，组织）

定位：[Design Goals](system.md#design-goals)、[Logical Architecture](system.md#logical-architecture) 和 [Research Mechanisms](system.md#research-mechanisms)。目前开头简述三项挑战后立即列七项要求，随后展示架构与机制表。材料完整，但读者尚未看到一个状态在周期内怎样被管理。

建议在设计目标后增加一段总览，再给架构图和要求。总览应说明“依据预计需求安排准备，依据有效覆盖和引用决定回收，两者受到同一空间与传输约束”。随后要求列表解释该过程成立的条件。候选机制表保留为对照，不再承担全部设计说明。

示范段落：

> Conveyor 的候选设计将空闲状态回收与后续状态准备联系起来。当前更新结束后，策略依据访问引用和有效主机覆盖判断哪些 GPU 内容可以回收；下一次使用之前，策略结合预计需求与资源压力安排恢复。若应用允许调整更新位置，释放偏移还可以改变多个会话需求的重叠。上述过程需要共同维护内容有效性和空间占用，并在预取未完成时协调正常恢复。

这段应紧接当前边界提示，保持它作为设计总览的性质。它不证明当前代码已经实现统一调度器，也不把组成动作全部升级为贡献。

### EDIT-S02：将状态维度表连接到实际状态转换（P1，组织／研究依赖）

定位：[KV State Model](system.md#kv-state-model)。六个维度有助于防止将会话简化为 GPU／主机二选一，但缺少一个连续例子解释它们怎样影响决策。建议在表后沿一次主机复制、GPU 回收和恢复过程解释状态变化，然后保留待补转换规则。

示范段落：

> GPU 内容仍有效时，建立主机副本会增加一份存储与传输依赖，并不立即释放原有空间。只有副本完成并且相关访问引用允许回收时，策略才能按其恢复规则选择逐出。恢复则先占用目标空间，再使内容就绪并发布可复用状态。因而，分配、内容有效与索引可见分别影响容量检查、读取安全和缓存复用。

如策略允许无副本逐出，必须紧接解释该分支依赖重算，以及为何满足参考历史要求。精确前置条件、共享引用与取消行为仍须补设计；示例不能替代并发证明。

### EDIT-S03：把未决定的策略写成设计空间，而非隐含已存在的算法（P1，研究依赖）

定位：[Release-Offset Scheduling](system.md#release-offset-scheduling)、[Idle-Session Eviction](system.md#idle-session-eviction) 与 [KV Prefetching](system.md#kv-prefetching)。例如，“可以选择只逐出已有确认主机副本的块，也可以允许对无副本范围在以后重算”准确记录了选择空间，但尚未给出选择依据；预取部分同样未确定排序与提前量。

建议每节分成连续的两层：先解释共同约束和候选选择各自代价，再明确“当前采用什么／尚待决定什么”。待定策略集中列出所需输入、决策、裁决材料及受影响主张。不要用“系统自适应选择”等表述替代缺失规则。

| 待决问题 | 需要补充的内容 | 不能提前写出的主张 |
| --- | --- | --- |
| 何时逐出、逐出哪些范围 | 引用条件、有效覆盖、恢复成本与容量压力的选择规则 | 所有被逐出内容都能直接回载 |
| 何时开始预取、如何排序 | 预计使用时刻、成本估计、容量准入与竞争处理 | 恢复总能在下次需求前完成 |
| 怎样选择或调整偏移 | 应用许可、优化目标、异构与会话变化规则 | 均匀偏移普遍最优或没有用户代价 |

### EDIT-S04：保留正确性条件，用因果段落压缩重复限定（P2，表达／组织）

定位：[On-Demand Restoration](system.md#on-demand-restoration)、[Correctness and Failure Analysis](system.md#correctness-and-failure-analysis) 与 [Implementation Boundary](system.md#implementation-boundary)。这些小节多次提示状态就绪、参考历史和回退限制。建议在恢复流程中说明一次主要因果关系，正确性小节以性质和验证覆盖总结；实现边界只保留当前路径对这些性质的具体影响。

例如，当前“回退保持历史语义的前提是……”可以与“恢复可能增加延迟……”连接成一段：先说明缺口如何根据保留历史重建，再说明重建为何可能保持语义但仍错过目标。这样的结构比在多处单列“不能等同”更容易阅读，也不会淡化正确性要求。

初始上下文预加载已经被准确归为评估准备。建议保留简短机制语义与实验附录链接，无须为了让设计章节显得完整而扩写成研究模块。

## 6. experiments.md：将评估提纲推进为可执行方法

### 已经写得好的部分

[Evaluation Questions](experiments.md#evaluation-questions) 同时列出支持和削弱主张的结果，能够防止评价只寻找正例；代表性负载与压力负载已分开；复现附录清楚标明当前实例不是最终矩阵。这些都是论文式评估的基础。表格本身无需改成大段文字。

### EDIT-E01：为实验问题补充连贯的方法段落（P1，组织）

当前问题、矩阵、比较族与消融表彼此相关，但缺少一段解释其推进顺序。建议在研究问题表后先说明：容量扫描建立问题实例，匹配对照衡量服务收益，恢复分解与消融解释原因，留出配置和扰动检验边界。随后为关键实验组写“目的—改变的因素—匹配条件—观测—判定”的方法段落。

示范段落：

> 评估首先联合改变会话规模与上下文条件，检查 KV 分配是否在计算和输入处理之前限制服务。随后在相同参考历史与服务标准下比较不同驻留和恢复方案，确定资源节省是否转化为达标承载能力。机制分析进一步固定非目标条件，分别检查主机复制、逐出和不同预取触发的作用；对于没有获得服务收益的配置，保留其恢复、计算与等待分解，用于解释适用边界。

该段组织现有计划，不新增配置常数或获胜预期。具体实验对象仍须按原文的待选项落实。

### EDIT-E02：优先确定主指标的操作定义（P1，研究依赖）

定位：[Service and Capacity Metrics](experiments.md#service-and-capacity-metrics)。表头明确写的是“定义要求”，并有“待作者填写：主服务指标及完成事件……”。这不是零散句子的问题，而是实验还缺少最终判定。建议将其作为写作前置任务，确定后再改成方法正文。

需要作者确认的内容包括：主完成事件及其可观测映射；延迟采用哪个输入时间基准；目标值与允许违约比例；观察期限、持续落后与会话失败规则。若各输出架构无法使用同一个事件，应说明公共要求与各自映射，而不为统一表格强行等同。

定义落实后，正文应能让独立读者依据同一事件记录得到相同的达标判断。尚未落实时，保留醒目的待定状态，不写“系统满足 SLO”或“已增加最大并发”。这一方法可参考 [JITServe 与 DistServe](writing-lessons-2026.md)。

### EDIT-E03：明确触发对照究竟隔离哪种信息优势（P1，研究依赖／表达）

定位：[Ablation Matrix](experiments.md#ablation-matrix)。表中已区分当前需求、输入提交后和预计未来需求，但“预计未来需求”仍需要映射到具体事件。建议在表后用一个完整段落说明触发可见的信号、信号产生时刻、预计使用对象以及其他条件如何匹配。

示范段落：

> 不同恢复触发组用于区分提前信息与搬运实现的作用。比较时固定参考历史、主机副本和传输路径，并记录触发信号实际产生的时刻及相关计算开始时刻。基于应用节奏的组还需说明时间信息是否在输入提交之前可获得；输入提交后预取则仅使用当时可见的需求。对不可部署的精确信息参照，单独标明其信息优势，使算法效果与额外先验能够区分。

该段不要求所有工作负载都具有精确未来信息。对照的具体事件和实施资格需要完成定义与实现后核验。不要仅按配置名称断言已经完成正交消融。

### EDIT-E04：保留复现附录的结构，把公平性缺口与科学后果连接起来（P2，表达）

定位：[Executed Decode Difference](experiments.md#executed-decode-difference) 与 [Repository Health Gates](experiments.md#repository-health-gates)。这里的参数、字段和运行规则已经放在合理位置。建议保留表格，只增强解释：生成与保留规则差异如何影响状态增长，调度差异如何影响批形状与时长，失败样本如何进入主指标。

诸如 runner 的具体拒绝规则属于当前操作事实；正文只需要能够解释样本资格与结果偏差。若后续压缩附录，操作规则应由现有 owner 承接并保留链接，不能删除唯一记录，也不能因为主文变简洁而把旧运行重新分类为公平比较。

## 7. findings.md：从证据卡片串联为结果论证

### 已经写得好的部分

现有条目普遍包含观察、依据和限制，并保留了稳定 `FINDING-*` 锚点。[Current State](findings.md#current-state) 明确诊断与正式结果的差距；附录也保留统计口径不一致和测量解释问题。建议保留这一透明度，不将尚无正式结果的文件改成确定的性能展示。

### EDIT-F01：按研究问题分组，保留 finding 身份和证据链接（P1，组织）

定位：[Paper-Relevant Findings](findings.md#paper-relevant-findings)。目前容量、偏移、驻留和源码路径各成一张卡，读者需要来回拼接。建议添加叙事分组，并在每组开头解释这些观察共同回答什么问题。组内继续保留现有 ID、锚点和来源；不要合并掉旧身份或改写历史 artifact。

| 建议分组 | 现有条目 | 该组正文应解释什么 |
| --- | --- | --- |
| 容量动机与资源记账 | FINDING-D1、FINDING-D2、FINDING-D5 | 历史观察为何支持继续检验容量问题，以及需要排除哪些混淆 |
| 需求分散与计算取舍 | FINDING-D3、FINDING-H1 | 输入侧变化与驻留／恢复收益之间还缺什么证据 |
| 驻留节省与恢复代价 | FINDING-H4、FINDING-H5 | 状态占用下降为什么尚不能推出达标承载能力提高 |
| 实现可行性与验证缺口 | FINDING-H3、FINDING-H7 | 源码支持哪些路径，尚未证明哪些并发与性能性质 |

最后一组可明确命名为实现可行性依据，避免与端到端性能观察处于同一种结果层次。它仍保留在 Findings 中维护证据解释；设计语义继续由 System 维护。

示范分组导语：

> 现有诊断分别提供了空闲驻留下降和状态准备开销的线索。前者说明回收路径可能释放其他会话可用的 GPU 空间，后者说明重新使用这些状态仍需付出恢复与等待成本。由于相关对照尚未满足统一工作量与服务判定要求，两类观察目前只能支撑后续容量—延迟联合实验，不能组合为正式容量提升结论。具体依据与限制见 [FINDING-H4](findings.md#finding-h4) 和 [FINDING-H5](findings.md#finding-h5)。

### EDIT-F02：以观察为主句，集中重复的证据资格说明（P2，表达）

多个条目在简短观察后立即接“依据……；待补……”，语气接近审核卡片。建议每条正文依次说明观察对象、支持的解释和仍未排除的原因；证据入口与下一步验证可放在段后短行或统一材料表中。共享的来源等级由 Evidence Scope 解释，各条只保留独有的限制。

集中重复限制不意味着删除关键资格。短时程不能支持长期稳定、工作量不匹配不能支持公平提升、源码不能代替并发验证等限制，仍应贴近相应结论。若没有数据支持更强主题句，保持诊断语气。

### EDIT-F03：移除本次编辑过程的叙述，保留稳定的证据说明（P2，表达）

定位：[Evidence Scope](findings.md#evidence-scope)。原句“本次整理只收缩过强表述、保留诊断边界，没有接受新的实验结果”描述编辑动作，会随着下一次维护失去时间含义。建议将编辑过程留在变更说明中，正文改为长期可解释的角色说明。

可替换为：

> 本文按来源和可验证程度解释已有观察。诊断材料用于形成待检验假设，正式性能主张须依据匹配协议下的有效测量；各条目分别列出其可支持的解释与验证缺口。

这是一项表达修正，不改变任何 evidence 的等级。

### EDIT-F04：将测量解释中的重复项串联，保留历史差异（P2，组织）

定位：[Diagnostic Appendix: Fairness and Measurement](findings.md#diagnostic-appendix-fairness-and-measurement)。FINDING-B1、FINDING-B2、FINDING-F7 与 FINDING-H2 从不同角度说明调用、生成、消费和进度的区别；FINDING-C2 与 FINDING-C3 说明比较资格。建议按“事件关联”“公平性”“执行成本诊断”“初始状态”添加附录分组，并用短导语解释关系。

数值不一致、未命中样本和净增长口径问题应保留。将文字改得流畅不能替代复算；本轮不建议择取一个数字、统一历史口径或重新绘制结果。协议定义继续链接 Experiments，finding 只保留实际发现的问题及其证据解释。

## 8. PAPER.md：从写作指令清单改为论证摘要

### 已经写得好的部分

大纲已经有中心问题、候选贡献与证明义务，并在设计、评价、相关工作和讨论中保持证据约束。作为写作规划，它理应包含待补事项。用户希望更接近论文风格，并不意味着现在就应填满摘要、贡献数字和结论。

### EDIT-W01：每小节写一段“本节论证”，将材料清单放在其后（P1，组织／表达）

定位：[Background and Motivation](PAPER.md#2-background-and-motivation)。当前多以“解释……”“给出……”“说明……”开头，例如 2.2 的“解释参考历史、KV 状态大小、物理驻留与恢复”。这能提示写作者任务，但读者还看不到小节自身的论证。

建议采用“论证摘要 + 必需材料”的结构。摘要用连贯语言说明本节为什么存在、前后如何连接；材料表继续记录需要的来源、图或定义。这样保持大纲的用途，同时减少散乱指令。

2.2 可示范为：

> 本节将跨更新历史需求与 GPU 容量约束联系起来。在保持参考历史的条件下，完整驻留需要随上下文与会话规模增加的物理空间，而更新计算是否已经饱和取决于工作负载和资源配置。动机实验据此联合检查状态分配、模型进度和计算，识别容量先成为约束的条件。应用任务中的历史依赖用于说明保留这些状态的价值，并为后续质量与资源取舍提供依据。

段后保留“所需材料：受控动机观察、参考历史定义、代表任务依据”，并链接 owner。本段描述该节应完成的论证，不宣称动机实验已经完成。

### EDIT-W02：用问题、决策和证据连接章节，减少重复提纲（P1，组织）

当前贡献表、Introduction 表、Evaluation 表以及四份 owner 文档会重复出现同一研究问题。这些映射有用，但不应在大纲中再手工维护参数、结果状态或完整实验协议。

建议让 PAPER 重点解释章节间的依赖：背景建立条件，形式化固定对象与目标，设计给出条件下的动作，评价检验动作是否改善目标，讨论解释边界。贡献表保留简洁的证明义务和 owner 链接；具体实验矩阵、缺失结果与配置仍回到相应文档。

### EDIT-W03：近期文献作为比较入口补充，结论留待核验（P1，研究依赖／表达）

定位：[Related Work](PAPER.md#7-related-work) 与 [Writing References](PAPER.md#writing-references)。当前写法已正确说明“下面是检索和比较提纲，不是完成的新颖性结论”。建议审核后将[新阅读指南](writing-lessons-2026.md)中的 2026 年工作作为比较入口：SYMPHONY 对应提前信号，Strata 和 Bidaw 对应缓存感知调度，ECHO 对应模型内部预取与容量问题，JITServe 对应服务目标与不精确信息。

这里建议的是补充阅读与比较维度，并不声称已完成全文比较，也不预设每篇都要成为实测基线。正式相关工作仍应写清现有方法已经处理的部分，以及 Conveyor 需要通过定义和实验检验的剩余条件。

### EDIT-W04：把章节末的待补项收敛成论文材料依赖（P2，组织）

目前多数小节单独重复“待补”。可以在局部保留会影响理解的关键未决条件，将具体产物汇总到末尾，例如目标事件、策略规则、动机图、设计图、正式主结果与资源边界。汇总表应说明它们分别阻止哪一部分写作，不维护运行过程和实现修补任务。

结论与摘要的结果位置继续留空。研究未完成时，一份准确的论文大纲应展示哪些论证已有材料、哪些仍依赖验证，而不使用流畅叙述制造完成感。

## 9. 审核后建议采用的目标结构

| 文档 | 主体应承担的论证 | 保留的结构化材料 | 后置或集中内容 |
| --- | --- | --- | --- |
| Problem | 会话属性如何产生容量与时间约束 | 应用属性比较、符号、容量公式 | 术语表、来源、尚缺的背景材料 |
| System | 如何利用信息作出安全且有资源代价的决策 | 架构图、状态表、转换／算法、正确性覆盖 | 具体实现边界与复现链接 |
| Experiments | 怎样判定问题、收益、原因和适用区间 | 矩阵、基线、指标、消融与运行参数 | 当前实例和操作诊断附录 |
| Findings | 已有观察支持什么、为什么仍有限制 | 稳定 finding、证据入口、当前状态表 | 诊断分组和缺失证据汇总 |
| PAPER | 各节怎样共同建立最终论点 | 段落职责、图表计划、证明义务映射 | 写作来源与材料依赖 |

建议保留全部现有稳定锚点。若只改变标题层级，可用显式 HTML 锚点保持入口；若内容需要跨 owner 调整，应在后续实施中检查引用和维护职责。本轮没有必要为了文字风格新增目录或重组事实域。

## 10. 建议的实施顺序与验收条件

第一步只做已有含义足够明确的编辑：缩短无关背景、增加表前解释与表后承接、将 PAPER 的动作清单改为论证摘要，并清理依赖“本次整理”的措辞。这些修改可逐段审核，不需要新增实验结论。

第二步完成组织调整：为 System 增加整体流程解释，为 Findings 按研究问题分组，集中重复资格说明和材料待办。保持原有 ID、证据链接和附录，避免清理正文时破坏追溯。

第三步由作者确认研究依赖项：应用时间契约与偏移权限、参考历史、主服务事件和达标标准、逐出与预取选择规则。确定后再补写正式方法；实现与测量尚缺的部分继续标注待验证。

最后，随着正式证据到位，将结果段落和论文主张同步更新到对应 owner，再回填 PAPER 的摘要与结论。配置、数字和状态不在多处手工复制。

审核一段改写是否合格，可以检查以下条件：

1. 首句说明该段的对象或判断，后续句子能解释原因，而不是仅列名词。
2. 每张表或图都有正文说明它用于回答什么问题，并有必要的解释与承接。
3. 设计要求、候选策略、实现事实和实验观察仍然可区分，语气没有偷偷增强。
4. 服务事件、资源对象与参考历史使用一致定义；涉及未决选择时保留明确空位。
5. 结论仍能追到原有 finding 与 evidence；短时程、来源缺陷和公平性限制没有消失。
6. 原型模型、模态、输出和平台没有因删改文字而变成未经批准的论文边界。
