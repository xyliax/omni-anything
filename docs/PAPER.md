# Pilarius: EuroSys Paper Outline

这份大纲组织投稿论证。问题定义见 [Problem](problem.md)，设计见 [System](system.md)，评估协议见 [Experiments](experiments.md)，可引用结果见 [Findings](findings.md)。以下贡献、图表和章节是写作目标；未获得证据的内容保留为待补，不写成完成结果。

章节之间的论证依赖是：背景建立会话与时间条件，形式化固定对象与目标，设计给出条件下的动作，评价检验动作是否改善目标，讨论解释边界。本大纲为每章写步骤骨架——每步一两句草稿级主张、递向下一步的过渡句和待补材料，全部锚定 owner 文档；具体实验矩阵、结果状态与配置常数不在此手工维护，一律链接对应 owner。

- **转写不改变证据成熟度。** 待验证命题（如 KV-capacity-bound）不写成事实；diagnostic 观察不写成正式结果；未决策略在正文保留问题形式，不以“自适应调度”“智能协调”等表述替代缺失的规则。
- **关键句标记。** owner 文档中绝不能说错的句子用引用块 `> **【关键 · <性质>】**` 标出，性质四档：`定义`（措辞即语义）、`待验证命题`（有诊断线索、待实验判定）、`待核验定位`（新颖性定位，投稿前须复核文献）、`核心洞察`（论文核心主张）。每份文档标注不超过 5 处；引用块必须是所属论证段结论的精确浓缩；转写进论文时其措辞与限定不得漂移；`待验证命题`与`待核验定位`在获得相应证据前不得改档或转为事实语气。
- **相关工作核验。** §7 条目进入正文前按原文与最新版本重新核验；“尚未解决”必须以核验后的差异为据；投稿前重查同期文献。
- **实现内容的准入。** 实现章节只解释信息在哪里产生、策略何时执行、如何与引擎协调；缓存索引、传输接口、输出缓冲等实现选择仅在解释正确性或开销时进入正文；输出交付只在影响服务目标或公平性时解释。

### 写作流程

按以下顺序把本大纲转写为论文正文。写作顺序纪律：先固定中心问题与候选贡献（本大纲的对应两节），再按各章步骤搭骨架并同步规划 Evaluation，最后逐段扩写；Abstract 与最终 Contributions 写在最后。limitation → key idea → challenge → module → contribution → section 的链条须逐项闭合，任何一环缺失时以待补标记呈现，不得用更强措辞补偿。

1. **按章走步骤。** 每章按其步骤骨架推进：步骤的主张句是该段落主题句的雏形；沿锚点回 owner 文档取完整论证、限定与关键句标记的精确措辞；用过渡句收尾并交给下一步。
2. **空位与未决的处理。** 遇【空位】查[材料依赖](#material-dependencies)，确认它等待哪项作者决策或实验证据；遇未决策略保持问题形式转写，不虚构规则。
3. **图随步骤落位。** 每张图按[图件计划](#figure-plan)在其服务的步骤处引入，正文先给论证句、图带读图句；测量与示意分开标注。
4. **一致性收口。** 全文完成后按三处呼应规则核对 Intro 主张、正文论证与结论判定的范围与语气；关键句标记的措辞与 owner 文档完全一致；挑战—机制—消融三方对齐。
5. **正文写入位置。** LaTeX 正文写入 `eurosys2027/sections/`，遵守该目录 AGENTS.md 的写作规则（double-blind、证据绑定、AI 使用登记）；本大纲不替代 owner，冲突时先改 owner。

### 贯穿规则

- **挑战—机制—实验一一对应。** Motivation 结尾的挑战清单、Design 的小节、Evaluation 的消融必须三方对齐；Sarathi 的 Takeaway→技术→逐技术消融是最清晰范本。
- **三处呼应。** 同一主张在 Intro（一句主张）、正文（完整论证）、Conclusion（带证据判定）出现三处，三处范围与语气一致，不得漂移。
- **过渡句。** 每节结尾留下一个未回答的问题，下一节开头承接；读者应在作者说出研究问题前自己推出它。
- **图的分配。** Intro 一张动机图，Motivation 密集测量图，Design 一张架构图加机制示意，Evaluation 主结果先行、消融置于最后；每张图必须被正文论证句引用并带读图句。
- **附录去处。** 资源/延迟模型推导（DistServe App.A）与 artifact 说明（Sarathi App.A）进附录，正文保持论证密度。

<a id="central-question"></a>
## 中心问题

对于跨更新保留历史、具有规律服务需求的交互会话，能否利用可预测时序减少 GPU KV 驻留，并以可接受的恢复和调度代价提高满足服务目标的承载能力？

本文的候选核心是**时间信息与状态驻留的共同调度**。KV offload、prefix caching、prefetching 和周期偏移已有各自先例。是否形成新的系统贡献，取决于相对于最接近工作的明确差异、可部署的信息条件及可测的收益，不能由机制名称或代码组合推定。该核心的候选形式化是：释放偏移作为传输链路时间、GPU 空间占用时长与批组成三类耦合资源的联合分配变量（→ [资源边界](problem.md#resource-frontier)）；此形式化是待验证的建模假设，其成立程度由 Q5 的标定与留出验证判定。

论证审计用的三问地图（此结构用于自查，正文按论证递进展开，不以问答形式出现）：**研究什么** → [问题陈述](problem.md#problem-statement)；**为什么存在** → [交互会话及其时间结构](problem.md#interaction-sessions-and-their-timing)与[容量矛盾](problem.md#why-historical-kv-state-can-limit-capacity)确立的三个负载性质；**现有方法为何不够** → [现有路线的代价](problem.md#the-gap-in-existing-approaches)。

<a id="abstract-outline"></a>
## 摘要提纲

摘要按句群结构组织为一个紧凑段落（形制对照 AdaServe/Metronome 摘要）；以下描述每个句位承担什么，成品英文句由 `eurosys2027/sections/00-abstract.tex` 持有。铺垫压缩、We-present 提前是既定形制决策；空位纪律不变——不填提升倍数、最优性或普适性表述。

1. **铺垫句群（问题、缺口与关键观察，四句）。** 依次承担：负载时间结构——会话为长期存续的 full-duplex（输入输出重叠，一处同位语定义，为 §2 的双工铺垫设置 anchor），以固定时长 micro-turn 推进，每个 micro-turn 内模型吸收新到输入、决定回应内容与时机、可解码有界输出段（micro-turn=时间片；片内计算不设专名、不用 update，按内容写 prefill、decoding 或 the computation of micro-turn k）；更新之间无模型计算，而保留的 KV 状态跨 micro-turn 持续增长；residency dilemma——全驻留在计算余量仍在时耗尽 GPU 容量（待 Q1 验证），reactive offloading 把恢复放回关键路径；关键观察——更新时刻表是负载预先给定的性质，状态的下一次使用先于需求可知（措辞锚定核心洞察标记）。产品专名不进摘要（摘要无法带引用），移至 §1① 带引用引入；以对象层命题开篇，不用「makes X explicit」式元话语，不用「in this pattern」式模糊指代承担定义。
2. **We-present 句。** supports-X-through-Y 句式，携带 cyclic state restoration，保留「不截断应用保留历史」限定；抽象层次停在决策层，以 Metronome/AdaServe 摘要为准，不点名实现接口。
3. **操作展开与能力句一（合并为一句）。** cyclic state restoration 的操作语义与逐出深度合并：每个 micro-turn 之后逐出可恢复状态、下一个 micro-turn 之前恢复完成；深度以链路在 KV-idle interval 内可回搬量为界（措辞对照 [problem.md 术语表](problem.md#terminology)的词条定义，不得漂移）。
4. **能力句二（相位错峰）。** 接纳时一次指派固定相位，把恢复期限与驻留峰值分散在周期内；机制句停在决策层，容量效果留给结果句。
5. **能力句三（异构与接纳；兼任决策所要求的结尾能力句）。** 异构会话同一 plan 吸收——恢复需求大者多留驻留；接纳归约为寻找空闲 phase。位于结果句之前，摘要以结果收尾（AdaServe 形制）。
6. **结果句。** 与 full-residency（点名）和 the strongest existing baseline（不点名；on-demand restoration 不作为点名对照出现）比较——【空位：匹配对照与统一服务判定下经验证的承载能力结果】（§5②）。

独立 tradeoff 句（Evicting more… 式）撤出摘要，留给 Intro/Design 展开。

**待补：** 经验证的问题实例、与最接近工作的差异、主结果及实验域。当前不填提升倍数、最优性或普适性表述。

## 1. Introduction

Introduction 按六步递进组织。每步给出草稿级主张与递向下一步的过渡句；主张的措辞与限定以 problem.md 对应段落（含其关键句标记）为准，证据未到位的部分保留空位。②③④ 与 §2 共享同一主张，按三处呼应规则分档：Intro 档位为主张摘要（一句摘要加内部引用），Background 档位为完整论证；完整草稿句只在 §2 保留一份。

**① 背景。**

- 主张：交互式 AI 应用的会话跨请求保留历史并持续推进；新兴的模型级双工交互让会话按媒体时钟持续吸收输入、推进状态，以支持自然话轮转换、重叠输入和及时打断（→ [负载现实](problem.md#interaction-sessions-and-their-timing)）。
- 承接：一边是按时钟规律增长、必须跨周期保留的历史状态，一边是有限的 GPU 内存；二者将在某一负载点相交。
- 待补：running example、应用来源、目标事件。running example 当前不设置 provisional default：需在实验矩阵与图 1 的 formal motivating evidence 冻结后由作者确认，并在 Background、Design walkthrough 与 Evaluation 中复用同一实例。

**② 容量矛盾。**

- 主张（主张级摘要，完整主张见 §2.2③）：以全驻留为参照策略，它只可能在容量轴上失败——历史 KV 的驻留需求可能先于更新计算需求触及 GPU 资源上限（待验证命题，[Q1](experiments.md#evaluation-questions) 判定；→ [容量机理](problem.md#why-historical-kv-state-can-limit-capacity)）。
- 承接：参照策略在容量轴上失效后，自然的问题是：改动参照的哪一部分可以化解矛盾，代价是什么。
- 待补：经核验的动机观察及资源分解（图 1 的测量部分）。

**③ 现有路线的代价。**

- 主张（主张级摘要，完整主张见 §2.2④）：驻留维度的已知路线或者把恢复留在关键路径上，或者依赖与周期节奏错配的信号；缩减保留状态属应用侧质量取舍，与驻留管理正交、可组合（→ [现有路线的代价](problem.md#the-gap-in-existing-approaches)）。
- 承接：驻留维度上没有路线做到及时就绪，除非负载本身能向系统提供状态再次使用的时刻。
- 待补：驻留维度的公平能力对比和原始引用；逐项差异按原文核验。

**④ 关键观察。**

- 主张（主张级；核心洞察句逐字引用，措辞锚定 problem.md 的核心洞察标记，不得漂移；三级信息分级等完整论证见 §2.3⑤）：周期负载把下一次使用时刻作为负载性质预先提供给系统：该信息先于需求出现、跨可描述周期反复出现，因而可以驱动空闲期的驻留回收与使用前的状态恢复（→ [时间信息的机会与代价](problem.md#why-timing-information-matters)）。
- 承接：但这一机会有代价，利用它会引入新的约束。
- 待补：所选工作负载对三级时间信息（节奏存在、释放时刻可见、偏移可控）各自满足到哪一级。

**⑤ 挑战。**

- 主张：把时间信息转化为容量收益须同时处理三个挑战——多会话周期需求落在周期的哪个位置（相位对齐使峰值叠加）；空闲期回收多少（语义可重建与深度可判定，而建副本消耗同一链路）；使用前何时恢复（过晚回到关键路径、过早占用空间并竞争传输，执行时刻还受排队扰动）（→ [设计目标与总览](system.md#design-goals)）。
- 承接：Pilarius 的机制逐项回应这三个挑战。
- 待补：挑战—机制一一对应已在 owner 落实（偏移调度↔需求安置、带主机后备的部分逐出↔回收判定、预取↔恢复时机）；转写时核验消融轴同构（Q4：偏移/逐出/预取），保持三方对齐。

**⑥ 系统、贡献与结果。**

- 主张：Pilarius 以释放偏移调度、带主机后备的部分逐出和 KV 预取回应上述挑战（均为待检验机制假设，→ [候选机制](system.md#research-mechanisms)）；结果句留空位——在【匹配对照与统一服务标准】下【经验证的承载能力变化，含代价与适用边界】。
- 承接：无（收尾段，接贡献列表与全文路线图）。
- 待补：正式结果、配置域、统计与边界；真实实现能力；候选贡献按最终证据重新定位。

## 2. Background and Motivation

### 2.1 Interaction Forms and Timing Contracts

**① 请求类别及触发方式。**

- 主张：交互会话跨请求保留历史并持续推进；以目标对话模型利用最新输入作出回应决策的触发方式，区分显式提交的轮次型请求、端点触发的语音请求和按固定 micro-turn 推进的持续双工会话。第二类用 `endpoint-triggered speech request` 命名，不限定组件架构；DuplexCascade 的对话路径按第三类分析。沿用 Thinking Machines 的时间片用法，以 micro-turn 解释双方尚未完成完整话轮时输入、输出及历史如何随时钟推进。每个时间片都提供处理输入、推进状态并选择行为的机会，行为可以是沉默；持续更新不要求每片都生成可播放语音。前端定期检测或输入 KV 增量追加，也不等同于对话模型每片持续作出回应决策。计算节奏、状态增量和空闲须按具体契约核验（→ [交互会话及其时间结构](problem.md#interaction-sessions-and-their-timing)）。
- 承接：持续双工会话的更新节奏与历史保留共同带来两个资源特征。
- 素材：[三类请求的代表模型与工作](references/full-duplex-model-product-serving-landscape-2026-08.md#representative-request-families)逐项记录年份、公开属性与归类依据，并给出优先引用建议。Background 选择直接实例，Related Work 再展开时间建模与服务抽象；固定周期未披露的商业模型和混合执行路径保留证据边界。
- 待补：选定应用的时间契约来源、代表性的时间敏感交互要求与时间事件映射。

**② 持续双工会话的资源特征。**

- 主张：输入按真实时间产生，有限缓冲和新鲜度限制生成领先于实时消费的程度，具体 micro-turn 契约再给出单次更新的工作预算；允许预缓冲时，单周期生成量可以超过单周期播放量。单次更新计算快于周期推进且没有其他 KV 访问时，会反复留下空闲窗口。一次更新结束后会话仍在运行，历史 KV 必须跨过这些间隔保留。完整历史保留且输入与生成保留量稳定时，周期状态增量近似规律；固定预算只能提供增长上界（余量与增量需按模型及配置测量，单会话空闲不代表整机空闲；→ [交互会话及其时间结构](problem.md#interaction-sessions-and-their-timing)及[服务目标](problem.md#service-objective)）。
- 承接：持续增长的历史 KV 可能在每周期计算预算耗尽之前触及有限 GPU KV 容量。
- 待补：容量受限测量图（状态分配逼近容量线而计算仍有余量，图号待排）。

**②a 交互动机与比较口径（素材说明）。**

- 主张：交互价值由三个时间敏感任务建立——任务同时约束回应内容与交付时机，当端点晚于回应窗口或没有新端点时，以发言结束门控的相关决策即使拥有准确的端点预测也无法满足任务要求（→ [时间敏感任务](problem.md#time-sensitive-interaction-tasks)）；背景正文围绕共同论点展开：持续交互的正确性同时取决于内容与交付时机，计算启动条件必须允许模型在任务窗口内使用最新信息。
- 转写取舍（problem.md 不持有的写作决策）：附和与纠正留作说明完整级联系统也能管理交互的能力边界，不再承担主要动机；论文的论证链应由真实交互需求、已采用的 micro-turn 契约递向 KV 成本，不能由周期性便于管理 KV 反推应用必须采用它。
- 划界（原样保留）：增强语义或视觉事件系统也可能满足这些任务，不能从实例推出固定周期的唯一性；级联的模块化、可观测性、工具生态与阶段级 batching 优势同样保留；这些示例不冻结最终评估任务或模态。
- 素材锚点：资源论证的观察对象（以被管理的历史 KV 所属模型为准）、执行路径比较与周期性 KV 管理的判定依据见[固定 micro-turn 交互与端点触发的比较](problem.md#why-model-level-full-duplex-is-worth-studying)；应用来源与实例边界见[代表模型与部署实例](problem.md#representative-models-and-work)；micro-turn 到应用级 update 的映射见[工作负载模型](problem.md#workload-model)；外部数字与比较限制见[一手调研](references/micro-turn-versus-endpoint-interaction.md)。
- 承接：交互动机与观察对象确定后，论证回到资源轴；参照策略下这一容量矛盾如何呈现，下一小节给出。
- 待补：选定应用的时间契约来源与时间事件映射（与 ① 的待补共用维护）。

### 2.2 Historical KV and the Capacity Problem

**③ 参照策略下的容量矛盾。**

- 主张：以全驻留为参照策略——保留语义零损失、准备零延迟，只可能在容量轴上失败；在该参照下，历史 KV 的驻留需求可能先于更新计算需求触及 GPU 资源上限（措辞锚定【关键 · 待验证命题】，[Q1](experiments.md#evaluation-questions) 判定）；矛盾以三个负载性质同时成立为前提：历史跨更新复用、更新按可描述周期推进且留有空闲区间、单周期计算不饱和（措辞锚定【关键 · 定义】；→ [容量矛盾](problem.md#why-historical-kv-state-can-limit-capacity)）。
- 承接：参照策略在容量轴上失效后，自然的问题是：改动参照的哪一部分可以化解矛盾，代价是什么。
- 待补：受控动机观察（Q1）；保留策略作为负载参数交代，不判定其质量取舍。

**④ 现有路线的代价。**

- 主张：已知动作分属两个维度——缩减保留状态（窗口化、压缩、摘要）属应用侧质量取舍，与驻留管理正交、可组合；驻留维度上，offload 加按需恢复把回载与重算留在关键路径上，已有提前信号（队列深度、行为提示、暂停估计、层内预测、步数距离）绑定各自来源与动作域，都不是周期负载预先给定的释放时刻（→ [现有路线的代价](problem.md#the-gap-in-existing-approaches)）。
- 承接：驻留维度上没有路线做到及时就绪，除非负载本身能向系统提供状态再次使用的时刻。
- 待补：逐项系统差异按原文核验（§7 承接）。

### 2.3 Opportunity and Cost

**⑤ 机会与三级时间信息。**

- 主张（核心洞察句，措辞不得改动）：周期负载把下一次使用时刻作为负载性质预先提供给系统：该信息先于需求出现、跨可描述周期反复出现，因而可以驱动空闲期的驻留回收与使用前的状态恢复。该信息分三级——节奏存在可估计需求，释放时刻可见可提前准备，偏移可控才能重排多会话重叠；偏移控制权不能从节奏可见性推出（→ [时间信息的机会与代价](problem.md#why-timing-information-matters)）。
- 承接：机会有代价，提前恢复占用空间、多会话竞争传输、分散更新削弱批处理。要权衡这些代价，"哪个状态、何时使用、多早准备"必须先成为可判定的量：下一小节固定对象、事件与目标。

### 2.4 Problem Formulation

本章固定后文所有论证共用的对象与目标，使评价与设计使用同一个判定。

**① 对象与事件。**

- 主张：会话 `i` 的第 `k` 次更新在 `r(i,k) = t0 + phi_i + k*T` 获得执行资格；释放 `r`、实际提交 `a`、依赖 KV 的计算开始 `s`、完成 `c` 四类事件分开定义——延迟提交的等待计入从 `r` 起算的延迟，切块调整须另用原始输入时间计量（→ [周期性交互会话](problem.md#periodic-interaction-session)）。
- 承接：服务目标必须落在这些事件上才可判定。

**② 服务目标。**

- 主张：软实时目标写为 `c(i,k) - r(i,k) <= D_i`，完成事件定为该更新的生成完成，用户可见交付建模为常数偏移；延迟基准取实际提交 `a`（稳态下与 `r` 重合，首次提交的对齐等待单列），并与更新落后指标成对使用；实时输出下，有限缓冲与新鲜度限制的是累计生成领先于消费的程度——连续 `n` 个周期的累计生成量受契约上界 `R_play * n*T + B_out` 封顶，允许预缓冲时单周期生成量可以超过单周期播放量，不能按单周期断言输出约束（→ [服务目标](problem.md#service-objective)、[测量语义](experiments.md#measurement-semantics)）。
- 承接：目标定义在事件上之后，还差一件事：降驻留的动作可用的时间窗口在哪里。
- 待补：目标值 `D` 与允许违约比例（参数化扫描）、观察期限与会话失败规则。

**③ KV 空闲区间。**

- 主张：同一状态两次使用之间的空闲区间是所有降驻留动作的时间窗口；周期性提供预测依据，但排队、长计算或重叠执行可能缩短甚至消除它，释放偏移只改变多会话重叠、不创造单会话空闲（→ [KV 空闲区间](problem.md#intrinsic-reuse-interval)）。
- 承接：动作还要通过资源约束的另一半检查。

**④ 资源约束与可观测。**

- 主张：物理容量约束 `sum b_p <= G_KV` 限制任意时刻的分配；峰值取决于逐出与恢复的时间安排，且空间可分配不等于内容按时就绪。将链路视为可再生时间资源，可在总量检查之外陈述更强的候选可行性条件——每个会话的周期恢复需求应在其期限之前获得足够的链路时间（待验证的建模假设）；验证需要关联输入、提交、执行、传输与交付事件（→ [资源边界](problem.md#resource-frontier)）。
- 承接：对象、事件、目标与约束全部确定；在这些约束下利用时间信息应该采取什么动作，设计章逐一给出。
- 待补：批处理相关成本函数、传输服务模型、可行性条件；同周期起始模型如何扩展到所选异构场景。

## 3. Design

### 3.1 Overview

**① 总览与不变量。**

- 主张（措辞锚定 system 的【关键 · 定义】）：候选设计将空闲状态回收与后续状态准备联系起来——回收依据访问引用与有效主机覆盖，恢复依据预计需求与资源压力，释放偏移仅在应用允许时于接纳一次指派、此后不再移动；这是设计总览，不是已实现的统一调度器。七项设计要求与三个挑战为各机制划界，未实现接口与当前路径分开呈现（→ [设计目标与总览](system.md#design-goals)）。
- 承接：按状态生命周期逐一展开机制：先安排何时更新，再管理更新之间的状态。
- 待补（设计总览图）：与最终算法一致的设计总览；当前未实现的选项不画成实线执行保证。

### 3.2 Release Offset Scheduling

**② 释放偏移调度。**

- 主张：释放偏移决定多会话需求的重叠结构；它只在应用允许时才是控制量——本文负载中该权限由服务栈入口持有，稳态无用户可见代价、首次提交的对齐等待单列。v1 采用均匀 slot 网格：加入占空闲 slot、无空位拒绝（接纳归约为 slot 可用性）、退出后释放；偏移接纳时一次指派、终身固定，异构上下文由恢复深度吸收——每会话按其偏移窗口的搬运预算决定逐出与恢复的量；偏移指派可在资源层面理解为对传输链路时间容量的分配；在空间维度，错开偏移使各会话驻留曲线相互错开，部分逐出生效时总分配峰值从峰值之和趋向均值之和，收益比例由驻留策略塑造的峰均比决定（待 Q4 消融）（→ [释放偏移调度](system.md#release-offset-scheduling)）。
- 承接：错开只重排需求的重叠，单会话空闲期的状态仍在占用空间；回收这部分驻留是下一组机制的任务。
- 待补：slot 数推导（联立可行性系统，公式留待标定）与迟到处理（[未决设计决策](system.md#open-design-decisions)）。

### 3.3 Host-Backed Partial Eviction

**③ 主机后备与空闲逐出。**

- 主张：主机副本是安全逐出的前提之一，但复制本身不回收 GPU 空间；若空闲区间与逐出深度的假设成立，空闲期回收驻留可成为容量收益的直接来源，其安全性由引用检查与副本确认共同保证，收益上限由保留前缀与共享块决定（→ [空闲会话逐出](system.md#idle-session-eviction)）。
- 承接：逐出制造缺口，缺口必须在下次使用前填补。

**④ 按需恢复。**

- 主张：按需恢复是预取缺席或失败时的正常恢复路径——GPU 连续前缀复用、主机回载缺失范围、缺口后依赖后缀重算；其语义正确与及时完成是两个独立性质，必须分别验证（→ [按需恢复](system.md#on-demand-restoration)）。
- 承接：按需路径语义正确，等待却仍留在关键路径上；将这段等待移出关键路径，需要在需求出现之前开始准备状态。
- 待补：逐出范围与确认覆盖求交的规则未决；状态转换需覆盖双副本与共享引用，不把会话简化为二元驻留。

### 3.4 KV Prefetching

**⑤ KV 预取。**

- 主张：若提前量充足，预取可把状态准备移出关键路径；提前量必须覆盖从提交到再次获得执行机会的完整依赖链，而不只是传输本身。v1 触发为空间门控：前序会话逐出释放目标空间后即可发起，slot 网格下按期限先后排序。容量不足则延后，输入先到则与按需恢复协调，完成后又被逐出则按普通缺失处理（→ [KV 预取](system.md#kv-prefetching)）。
- 承接：偏移、逐出、恢复与预取各自搬运状态，任何一步出错都会破坏参考语义；机制齐备之后，必须整体论证它们共同满足哪些正确性性质。
- 待补：提前量取值留敏感性实验；实现现状的输入 push 触发与设计的空间门控触发须作为不同实验条件区分（[未决设计决策](system.md#open-design-decisions)、[实现边界](system.md#implementation-boundary)）。

### 3.5 Correctness and Fallback

**⑥ 正确性与回退。**

- 主张：内容一致、无过早复用、覆盖缺口可恢复、预取失败可处理、服务状态可解释——五项性质分别论证，运行成功的示例不能替代论证；回退可以保持参考语义但仍可能错过时限，两类保证分开陈述（→ [正确性与故障分析](system.md#correctness-and-failure-analysis)）。
- 承接：这些性质能论证到什么程度取决于实现事实；下一章交代当前实现支持到哪里、什么仍是候选。
- 待补：状态转换前置条件、共享引用与取消协议、可证明的不变量；**待补算法**：策略输入、动作、前置条件和复杂度。

- 待补：最终实现版本、与基线共享部分、尚未支持路径；API 名称不作为机制创新。

## 5. Evaluation

完整实验矩阵由 [Experiments](experiments.md) 持有，正文按问题推进：

**① Setup 与公平性。** 主张：固定模型精度、输入语义、实际生成工作、参考历史、调度模式与各预算口径；端到端比较须匹配工作量与统一服务判定，机制收益主张须控制变量（→ [比较族与公平性](experiments.md#fairness-checklist-for-the-protocol)）。

**② 主结果：达标承载能力。** 主张：在统一服务判定下比较全驻留、按需恢复与 Pilarius 可接纳的达标负载——结果【空位】（Q2；→ [评估问题](experiments.md#evaluation-questions)）。判读：达标承载增加则支持核心主张；驻留降低而达标承载未增，则结论收缩为"节省驻留但无服务收益"。承接：收益从哪里来、付出了什么。

**③ 延迟代价与关键路径。** 主张：输入到结果的分布与恢复关键路径分解（提交、传输、完成上报、再调度分开测量）解释代价——结果【空位】（Q3）。判读：代价可量化且不抵消容量收益则支持；延迟或持续落后违约抵消收益则收缩适用域。承接：整体收益确认后，还要知道每个机制各贡献多少。

**④ 消融：触发对照对应三级信息。** 主张：按需恢复与提交后预取不使用未来时间信息，基于节奏预取使用前两级，偏移对照检验第三级；比较时固定参考历史、主机副本与传输路径——结果【空位】（Q4；→ [消融矩阵](experiments.md#ablation-matrix)）。判读：收益随信息级别递进则支持"时间信息本身有价值"；收益来自未匹配的生成量或执行模式则该组作废重测。

**⑤ 资源模型验证。** 主张：独立标定、留出配置检验瓶颈分类与预测误差，报告模型失效处——结果【空位】（Q5）。判读：留出配置预测正确则资源模型可列为贡献；仅能逐点回拟合则降为分析工具呈现。

**⑥ 正确性。** 主张：状态往返一致性与参考历史保持在相同标准下验证——结果【空位】（Q6）。判读：往返一致则机制对参考执行透明的主张成立；不一致或输入丢失则正确性主张收缩。

**⑦ 边界与失效。** 主张：短会话、迟到、覆盖缺口、带宽与主机压力下的开销与失效区域如实报告，不从主图删除失败区域（Q7）。承接：本文的边界划清之后，剩下的问题是假设放宽时还剩什么。

## 6. Discussion and Limitations

**① 偏移不可控时还剩什么。**

- 主张：偏移控制权是三级时间信息中最强的假设；应用不允许调整时，节奏可见性仍支持需求估计与提前准备，保留的收益比例【待验证】（→ [时间信息的机会与代价](problem.md#why-timing-information-matters)）。

**② 退化条件。**

- 主张：非周期输入、无空闲区间、短会话或主机容量不足时，机制退化为按需路径；退化区域按 Q7 的结果如实展示，保留策略的质量取舍属应用侧参数，同此讨论其对适用域的影响。

**③ 限制分层。**

- 主张：工程限制（当前触发方式、未验证的并发场景、观测开销）与方法固有条件（需要节奏与空闲区间）分开陈述；模型误差与未覆盖维度明确列出，当前原型不替最终研究范围作决定；增加设备的效果由实际拓扑和竞争决定，不作"加卡无用"的一般判断。
- 承接：适用条件划清之后，剩下的问题是本文相对已有工作的定位。

## 7. Related Work

| 双工与实时语音 serving | 会话生命周期、交互/播放感知、每帧 deadline | Metronome（arXiv:2607.02640：周期实时任务框架、窗口化 KV）；LiveServe（arXiv:2606.22983：next-use 感知逐出、speech-onset 预取）；VoxServe（arXiv:2602.00269：请求作用域软 deadline 调度）；vLLM-Omni（arXiv:2602.02204：stage-graph 底座） |

每族的定位步骤（一句"已解决什么／未覆盖什么条件"，全部为待核验草稿，核验后才能落笔）：

- **① 迭代级服务与分页**：解决了请求内的物理 KV 管理与批处理效率；不处理会话级的跨更新状态生命周期。
- **② 会话级 KV 分层与恢复**：解决了暂停期间的分层放置与回载；其恢复触发是队列深度或请求到达事件，不消费周期负载预先给定的释放时刻（待核验）。
- **③ 恢复与重算的混合**：缩短了恢复段在关键路径上的长度；不改变它在关键路径上的位置。
- **④ 下一次使用感知与预取**：证明了提前量有价值；但信号来源（行为提示、层内预测、步数距离）与周期节奏不同源、动作域不同（待核验）。
- **⑤ 双工与实时语音 serving**：最近邻族——Metronome 以窗口化约束保留状态、窗口内全驻留，LiveServe 的 next-use 是观测估计而非负载预先给定的时刻（待核验；单句差异在 closest-work 核验后冻结）。
- **⑥ 服务目标与请求信息**：提供从应用要求推导调度目标的方法参照；其对象是请求级服务而非跨周期会话状态。
- **⑦ 周期任务与 deadline 调度**：提供偏移指派与可调度性的术语和分析工具；不处理状态搬运与恢复时序。
- **⑧ 窗口、压缩与替代状态结构**：改变保留状态的语义与规模，属与驻留管理正交的维度；作为可组合的负载参数与质量—资源取舍讨论，而非对立的基线。
- **⑨ 分层内存、放置与异构执行**：给出改变恢复成本的硬件条件，决定结论的外推方向而非本文的直接对照。

九族定位收束为一句（措辞取自 problem.md 的【关键 · 待核验定位】标记，逐项核验后方可冻结）：尚无已知工作利用周期负载预先给定的下一次使用时刻驱动驻留回收与状态恢复，在不改变应用保留语义的前提下把状态准备移出关键路径。承接：该定位成立的范围就是本文假设成立的范围，其边界已由上一章划定；把经过判定的主张按适用条件重述一遍，就是结论。
