# Conveyor: EuroSys Paper Outline

这份大纲组织投稿论证。问题定义见 [Problem](problem.md)，设计见 [System](system.md)，评估协议见 [Experiments](experiments.md)，可引用结果见 [Findings](findings.md)。以下贡献、图表和章节是写作目标；未获得证据的内容保留为待补，不写成完成结果。

章节之间的论证依赖是：背景建立会话与时间条件，形式化固定对象与目标，设计给出条件下的动作，评价检验动作是否改善目标，讨论解释边界。本大纲为每章写步骤骨架——每步一两句草稿级主张、递向下一步的钩子和待补材料，全部锚定 owner 文档；具体实验矩阵、结果状态与配置常数不在此手工维护，一律链接对应 owner。

- **转写不改变证据成熟度。** 待验证命题（如 KV-capacity-bound）不写成事实；diagnostic 观察不写成正式结果；未决策略在正文保留问题形式，不以“自适应调度”“智能协调”等表述替代缺失的规则。
- **关键句标记。** owner 文档中绝不能说错的句子用引用块 `> **【关键 · <性质>】**` 标出，性质四档：`定义`（措辞即语义）、`待验证命题`（有诊断线索、待实验裁决）、`待核验定位`（新颖性定位，投稿前须复核文献）、`核心洞察`（论文支点主张）。每份文档标注不超过 5 处；引用块必须是所属论证段结论的精确浓缩；转写进论文时其措辞与限定不得漂移；`待验证命题`与`待核验定位`在获得相应证据前不得改档或转为事实语气。
- **相关工作核验。** §7 条目进入正文前按原文与最新版本重新核验；“尚未解决”必须以核验后的差异为据；投稿前重查同期文献。
- **实现内容的准入。** 实现章节只解释信息在哪里产生、策略何时执行、如何与引擎协调；缓存索引、传输接口、输出缓冲等实现选择仅在解释正确性或开销时进入正文；输出交付只在影响服务目标或公平性时解释。

### 写作流程

按以下顺序把本大纲转写为论文正文：

1. **按章走步骤。** 每章按其步骤骨架推进：步骤的主张句是该段落主题句的雏形；沿锚点回 owner 文档取完整论证、限定与关键句标记的精确措辞；用钩子句收尾并交给下一步。
2. **空位与未决的处理。** 遇【空位】查[材料依赖](#material-dependencies)，确认它等待哪项作者决策或实验证据；遇未决策略保持问题形式转写，不虚构规则。
3. **图随步骤落位。** 每张图按[图件计划](#figure-plan)在其服务的步骤处引入，正文先给论证句、图带读图句；测量与示意分开标注。
4. **一致性收口。** 全文完成后按三次讲述规则核对 Intro 承诺、正文论证与结论裁决的范围与语气；关键句标记的措辞与 owner 文档零漂移；挑战—机制—消融三方对齐。
5. **正文落地位置。** LaTeX 正文写入 `eurosys2027/sections/`，遵守该目录 AGENTS.md 的写作规则（double-blind、证据绑定、AI 使用登记）；本大纲不替代 owner，冲突时先改 owner。

### 贯穿规则

- **挑战—机制—实验一一对应。** Motivation 结尾的挑战清单、Design 的小节、Evaluation 的消融必须三方对齐；Sarathi 的 Takeaway→技术→逐技术消融是最清晰范本。
- **三次讲述。** 同一主张在 Intro（一句承诺）、正文（完整论证）、Conclusion（带证据裁决）出现三次，三处范围与语气一致，不得漂移。
- **焊点句。** 每节结尾留下一个未回答的问题，下一节开头承接；读者应在作者说出研究问题前自己推出它。
- **图的经济学。** Intro 一张动机图，Motivation 密集测量图，Design 一张架构图加机制示意，Evaluation 主结果先行、消融殿后；每张图必须被正文论证句引用并带读图句。
- **附录去处。** 资源/延迟模型推导（DistServe App.A）与 artifact 说明（Sarathi App.A）进附录，正文保持论证密度。

<a id="central-question"></a>
## 中心问题

对于跨更新保留历史、具有规律服务需求的交互会话，能否利用可预测时序减少 GPU KV 驻留，并以可接受的恢复和调度代价提高满足服务目标的承载能力？

本文的候选核心是**时间信息与状态驻留的共同调度**。KV offload、prefix caching、prefetching 和周期偏移已有各自先例。是否形成新的系统贡献，取决于相对于最接近工作的明确差异、可部署的信息条件及可测的收益，不能由机制名称或代码组合推定。该核心的候选形式化是：释放偏移作为传输链路时间、GPU 空间占用时长与批组成三类耦合资源的联合分配变量（→ [资源边界](problem.md#resource-frontier)）；此形式化是待验证的建模假设，其成立程度由 Q5 的标定与留出验证裁决。

论证审计用的三问地图（此结构用于自查，正文按叙事漏斗展开，不以问答形式出现）：**研究什么** → [问题陈述](problem.md#problem-statement)；**为什么存在** → [负载画像](problem.md#interaction-sessions-and-their-timing)与[容量张力](problem.md#why-historical-kv-state-can-limit-capacity)确立的三个负载性质；**现有方法为何不够** → [现有路线的交换代价](problem.md#the-gap-in-existing-approaches)。

<a id="abstract-outline"></a>
## 摘要提纲

用一个紧凑段落依次回答五问；每问的草稿级答案取自对应骨架步骤的首句：

1. 什么交互需求使长期状态与响应目标同时重要？——交互会话跨更新保留历史并按媒体时钟持续推进，历史状态与软实时目标同时存在（§1①）。
2. 哪个具体资源矛盾尚未得到充分解决？——全驻留下历史 KV 可能先于计算耗尽 GPU 容量（待 Q1 验证），而现有恢复与信号机制不消费周期负载承诺的下一次使用时刻（§1②③）。
3. Conveyor 利用什么信息、作出什么不同决策？——以负载承诺的下一次使用时刻驱动空闲期的驻留回收与使用前的状态恢复（§1④⑥）。
4. 在什么工作负载、系统对照和服务标准下得到什么结果？——【空位：匹配对照与统一服务判定下的承载能力结果】（§6②）。
5. 结论适用于什么条件，主要代价是什么？——适用于三个负载性质成立的负载域；代价为主机容量、传输竞争与批处理变化，【空位：实测边界】（§8）。

**待补：** 经验证的问题实例、与最接近工作的差异、主结果及实验域。当前不填提升倍数、最优性或普适性表述。

## 1. Introduction

Introduction 按六步漏斗组织。每步给出草稿级主张与递向下一步的钩子；主张的措辞与限定以 problem.md 对应段落（含其关键句标记）为准，证据未到位的部分保留空位。

**① 世界。**

- 主张：交互式 AI 应用的会话跨请求保留历史并持续推进；新兴的模型级双工交互让会话按媒体时钟持续吸收输入、推进状态，以支持自然话轮转换、重叠输入和及时打断（→ [负载现实](problem.md#interaction-sessions-and-their-timing)）。
- 钩子：一边是按时钟规律增长、必须跨周期保留的历史状态，一边是有限的 GPU 内存——这两件事迟早相撞。
- 待补：running example、应用来源、目标事件。

**② 张力。**

- 主张：以全驻留为参照策略——历史语义零损失、准备零延迟，只可能在容量轴上失败；驻留需求随会话数与上下文单调增长，而满足实时输出时单周期计算通常不饱和，KV 容量因此可能先于计算成为约束（待验证命题，[Q1](experiments.md#evaluation-questions) 裁决；→ [容量机理](problem.md#why-historical-kv-state-can-limit-capacity)）。
- 钩子：参照策略撞墙后，自然的问题是——改动参照的哪一部分可以化解矛盾，代价是什么。
- 待补：经核验的动机观察及资源分解（图 1 的测量部分）。

**③ 逃生路线的交换代价。**

- 主张：已知路线各付一种代价——窗口化与压缩放弃完整历史；offload 加按需恢复保住历史，却把回载与重算留在关键路径上；已有提前信号（队列深度、行为提示、暂停估计、层内预测、步数距离）绑定各自的来源与动作域，都不是周期负载承诺的释放时刻（→ [现有路线的交换代价](problem.md#the-gap-in-existing-approaches)）。
- 钩子：没有路线同时保住完整历史与及时就绪——除非负载自己能告诉系统，状态何时会被再次使用。
- 待补：公平的能力对比和原始引用；逐项差异按原文核验。

**④ 关键观察。**

- 主张（措辞锚定 problem.md 的核心洞察标记，不得漂移）：周期负载把下一次使用时刻作为负载性质承诺给系统：该信息先于需求出现、跨可描述周期反复出现，因而可以驱动空闲期的驻留回收与使用前的状态恢复（→ [时间信息的机会与代价](problem.md#why-timing-information-matters)）。
- 钩子：但这份机会不是免费的——利用它会制造新的约束。
- 待补：所选工作负载对三级时间信息（节奏存在、释放时刻可见、偏移可控）各自满足到哪一级。

**⑤ 挑战。**

- 主张：利用时间信息须同时处理三个挑战——下一次需求可预测但执行时刻受排队影响；状态可以分散存储但有效性必须可判定；提前恢复节省关键路径时间却占用其他会话所需的空间（→ [设计目标与总览](system.md#design-goals)）。
- 钩子：Conveyor 的机制逐项回应这三个挑战。
- 待补：挑战表述与最终机制列表的一一对应核验（Motivation 挑战清单、Design 小节、消融三方对齐）。

**⑥ 系统、贡献与结果。**

- 主张：Conveyor 以释放偏移调度、带主机后备的部分逐出和 KV 预取回应上述挑战（均为待检验机制假设，→ [候选机制](system.md#research-mechanisms)）；结果句留空位——在【匹配对照与统一服务标准】下【经验证的承载能力变化，含代价与适用边界】。
- 钩子：无（收尾段，接贡献列表与全文路线图）。
- 待补：正式结果、配置域、统计与边界；真实实现能力；候选贡献按最终证据重新定位。

背景只保留理解问题所需内容。负载画像比较与全双工背景在下一节展开，Introduction 不需要写成应用综述。实现接口和修补过程不作为动机或贡献。

## 2. Background and Motivation

### 2.1 Interaction Forms and Timing Contracts

**① 负载画像。**

- 主张：交互会话跨请求保留历史并持续推进；按更新触发比较三种画像，对服务系统的本质区别在于系统何时知道下一次更新——只有按媒体时钟推进的持续双工会话把下一次更新时间与状态需求提前给出（→ [负载画像](problem.md#interaction-sessions-and-their-timing)）。第二类画像用 `endpoint-triggered cascaded speech pipeline` 命名；"VAD cascade" 只是简称，不能与所有级联系统或半双工交互画等号。
- 钩子：时钟画像因此同时带来两个资源特征。
- 待补：选定应用的时间契约来源与时间事件映射。

**② 时钟画像的资源形状。**

- 主张：单会话每周期的有效计算受墙钟双侧约束——下一次更新的输入要到下一释放时刻才齐备，无法对尚不存在的输入预支计算；提前生成只积累 backlog——余下的空闲不能由该会话自身填充。这与计算门控的文本请求形成结构性对照：后者 decode 未完成始终有工作、完成后状态可整体让位；周期会话每周期计算有界而会话不结束，历史状态必须跨过每一段空闲。完整历史保留下，会话状态每周期近似追加该周期的输入与输出（余量大小需实测，多会话叠加不等于整机空闲；→ [负载画像](problem.md#interaction-sessions-and-their-timing)）。
- 钩子：一边是按时钟规律增长、必须跨周期保留的历史状态，一边是有限的 GPU 内存——这两件事迟早相撞（与 §1① 钩子同句，三次讲述保持一致）。
- 待补：张力测量图（状态分配逼近容量线而计算仍有余量，图号待排）。

对"为何不用级联"的疑问在本小节回答：模型级全双工的目标不是替代 `VAD → ASR → 文本 LLM → TTS`，而是在需要 backchannel、重叠说话、及时 barge-in 或后台工作插回时直接建模连续时间上下文。动机证据以 2026 年的生产部署与决策周期谱系为主——GPT-Live 与 Seeduplex 的生产上线证明该形态的服务需求真实存在（厂商 A/B 为自报），前沿模型的语义级决策周期从 200 ms（TML micro-turn）延伸到 480 ms（DuplexOmni）、800 ms（BayLing-Duplex 决策块）与 1.0 s（MiniCPM-o 4.5），级联全双工的 micro-turn 甜点也在 0.6–1.2 s：周期是设计参数而非亚秒常数。同时注明级联方案在模块化、可观测性、工具调用与阶段级 batching 上的持续优势（→ [模型级全双工与级联流式的比较](problem.md#why-model-level-full-duplex-is-worth-studying)）。

### 2.2 Historical KV and the Capacity Problem

**③ 参照策略下的张力。**

- 主张：以全驻留为参照策略——历史语义零损失、准备零延迟，只可能在容量轴上失败；在该参照下，历史 KV 的驻留需求可能先于更新计算需求触及 GPU 资源上限（措辞锚定【关键 · 待验证命题】，[Q1](experiments.md#evaluation-questions) 裁决）；矛盾以三个负载性质同时成立为前提：历史跨更新复用、更新按可描述周期推进且留有空闲区间、单周期计算不饱和（措辞锚定【关键 · 定义】；→ [容量张力](problem.md#why-historical-kv-state-can-limit-capacity)）。
- 钩子：参照策略撞墙后，自然的问题是——改动参照的哪一部分可以化解矛盾，代价是什么。
- 待补：受控动机观察（Q1）、代表任务的历史价值依据；质量论证不靠人为设定"窗口必败"。

**④ 逃生路线的交换代价。**

- 主张：已知路线按放弃的性质分三类——窗口化与压缩放弃完整历史；offload 加按需恢复保住历史，却把回载与重算留在关键路径上；已有提前信号（队列深度、行为提示、暂停估计、层内预测、步数距离）绑定各自来源与动作域，都不是周期负载承诺的释放时刻（→ [现有路线的交换代价](problem.md#the-gap-in-existing-approaches)）。
- 钩子：没有路线同时保住完整历史与及时就绪——除非负载自己能告诉系统，状态何时会被再次使用。
- 待补：逐项系统差异按原文核验（§7 承接）。

### 2.3 Opportunity and Cost

**⑤ 机会与三级时间信息。**

- 主张（核心洞察句，措辞零漂移）：周期负载把下一次使用时刻作为负载性质承诺给系统：该信息先于需求出现、跨可描述周期反复出现，因而可以驱动空闲期的驻留回收与使用前的状态恢复。该资产分三级——节奏存在可估计需求，释放时刻可见可提前准备，偏移可控才能重排多会话重叠；偏移控制权不能从节奏可见性推出（→ [时间信息的机会与代价](problem.md#why-timing-information-matters)）。
- 钩子：机会不是免费的——提前恢复占用空间、多会话竞争传输、分散更新削弱批处理。要权衡这些代价，"哪个状态、何时使用、多早准备"必须先成为可判定的量：下一章固定对象、事件与目标。
- 待补（**待补图 1**）：共同输入时间轴下的动机实例，区分输入产生、更新释放、KV 需求、恢复和交付；测量与示意分开标注。

## 3. Problem Formulation

本章固定后文所有论证共用的对象与目标，使评价与设计使用同一个判定。

**① 对象与事件。**

- 主张：会话 `i` 的第 `k` 次更新在 `r(i,k) = t0 + phi_i + k*T` 获得执行资格；释放 `r`、实际提交 `a`、依赖 KV 的计算开始 `s`、完成 `c` 四类事件分开定义——延迟提交的等待计入从 `r` 起算的延迟，切块调整须另用原始输入时间计量（→ [周期性交互会话](problem.md#periodic-interaction-session)）。
- 钩子：服务目标必须落在这些事件上才可判定。

**② 服务目标。**

- 主张：软实时目标写为 `c(i,k) - r(i,k) <= D_i`，完成事件定为该更新的生成完成，用户可见交付建模为常数偏移；延迟基准取实际提交 `a`（稳态下与 `r` 重合，首次提交的对齐等待单列），并与更新落后指标成对使用；实时输出下每周期有效输出受 `N_out <= R_play * T` 约束（→ [服务目标](problem.md#service-objective)、[测量语义](experiments.md#measurement-semantics)）。
- 钩子：目标定义在事件上之后，还差一件事——降驻留的动作能用的时间窗口在哪里。
- 待补：目标值 `D` 与允许违约比例（参数化扫描）、观察期限与会话失败规则。

**③ KV 空闲区间。**

- 主张：同一状态两次使用之间的空闲区间是所有降驻留动作的时间窗口；周期性提供预测依据，但排队、长计算或重叠执行可能缩短甚至消除它，释放偏移只改变多会话重叠、不创造单会话空闲（→ [KV 空闲区间](problem.md#intrinsic-reuse-interval)）。
- 钩子：动作还要通过资源约束的另一半检查。

**④ 资源约束与可观测。**

- 主张：物理容量约束 `sum b_p <= G_KV` 限制任意时刻的分配；峰值取决于逐出与恢复的时间安排，且空间可分配不等于内容按时就绪。将链路视为可再生时间资源，可在总量检查之外陈述更强的候选可行性条件——每个会话的周期恢复需求应在其期限之前获得足够的链路时间（待验证的建模假设）；验证需要关联输入、提交、执行、传输与交付事件（→ [资源边界](problem.md#resource-frontier)）。
- 钩子：对象、事件、目标与约束全部就位——在这些约束下利用时间信息应该采取什么动作，设计章逐一给出。
- 待补：批处理相关成本函数、传输服务模型、可行性条件；同周期起始模型如何扩展到所选异构场景。

## 4. Design

### 4.1 Overview and Invariants

**① 总览与不变量。**

- 主张（措辞锚定 system 的【关键 · 定义】）：候选设计将空闲状态回收与后续状态准备联系起来——回收依据访问引用与有效主机覆盖，恢复依据预计需求与资源压力，偏移调整仅在应用允许时纳入；这是设计总览，不是已实现的统一调度器。七项设计要求与三个挑战为各机制划界，未实现接口与当前路径分开呈现（→ [设计目标与总览](system.md#design-goals)）。
- 钩子：按状态生命周期逐一展开机制——先安排何时更新，再管理更新之间的状态。
- 待补（**待补图 2**）：与最终算法一致的设计总览；当前未实现的选项不画成实线执行保证。

### 4.2 Scheduling Update Offsets

**② 释放偏移调度。**

- 主张：释放偏移决定多会话需求的重叠结构；它只在应用允许时才是控制量——本文负载中该权限由服务栈入口持有，稳态无用户可见代价、首次提交的对齐等待单列。v1 采用均匀 slot 网格：加入占空闲 slot、无空位拒绝（接纳归约为 slot 可用性）、退出后释放、不迁移；偏移指派可在资源层面理解为对传输链路时间容量的分配；在空间维度，错开偏移使各会话驻留曲线相互错开，部分逐出生效时总分配峰值从峰值之和趋向均值之和，收益比例由驻留策略塑造的峰均比决定（待 Q4 消融）（→ [释放偏移调度](system.md#release-offset-scheduling)）。
- 待补：slot 数推导公式（联立可行性系统，闭式留空）与进阶偏移目标（[未决设计决策](system.md#open-design-decisions)）。

### 4.3 Managing Idle KV State

**③ 主机后备与空闲逐出。**

- 主张：主机副本是安全逐出的前提之一，但复制本身不回收 GPU 空间；空闲期回收驻留是容量收益的直接来源，其安全性由引用检查与副本确认共同保证，收益上限由保留前缀与共享块决定（→ [空闲会话逐出](system.md#idle-session-eviction)）。
- 钩子：逐出制造缺口，缺口必须在下次使用前填上。

**④ 按需恢复。**

- 主张：按需恢复是预取缺席或失败时的兜底路径——GPU 连续前缀复用、主机回载缺失范围、缺口后依赖后缀重算；其语义正确与及时完成是两个独立性质，必须分别验证（→ [按需恢复](system.md#on-demand-restoration)）。
- 待补：逐出范围与确认覆盖求交的规则未决；状态转换需覆盖双副本与共享引用，不把会话简化为二元驻留。

### 4.4 Preparing State Before Use

**⑤ KV 预取。**

- 主张：预取把状态准备移出关键路径；其提前量必须覆盖从提交到再次获得执行机会的完整依赖链，而不只是传输本身。容量不足则延后，输入先到则与按需恢复协调，完成后又被逐出则按普通缺失处理（→ [KV 预取](system.md#kv-prefetching)）。
- 待补：触发在释放之前还是提交之后、提前量来源、时机估计与多会话排序未决（[未决设计决策](system.md#open-design-decisions)）。

### 4.5 Correctness and Fallback

**⑥ 正确性与回退。**

- 主张：内容一致、无过早复用、覆盖缺口可恢复、预取失败可处理、服务状态可解释——五项性质分别论证，运行成功的示例不能替代论证；回退可以保持参考语义但仍可能错过时限，两类保证分开陈述（→ [正确性与故障分析](system.md#correctness-and-failure-analysis)）。
- 钩子：这些性质能论证到什么程度取决于实现事实——下一章交代当前实现支持到哪里、什么仍是候选。
- 待补：状态转换前置条件、共享引用与取消协议、可证明的不变量；**待补算法**：策略输入、动作、前置条件和复杂度。

## 5. Implementation

**① 集成点与信息流。**

- 主张：实现章只解释信息在哪里产生、策略何时执行、如何与引擎协调；缓存与传输的引用管理、跨层事件关联是影响正确性与测量解读的关键工程（→ [实现边界](system.md#implementation-boundary)）。

**② 当前边界（诚实清单）。**

- 主张：当前预取由输入 push 触发、未把未来释放时间传给策略，不能写成已实现网格提前预取；逐出的固定尾部余量未与确认覆盖求交；绝对目标网格不保证无抖动（→ [实现边界](system.md#implementation-boundary)）。
- 钩子：这些边界决定评估能主张什么、消融的哪些组当前可执行。

**③ 复现指针。**

- 主张：源码入口、命令、环境与兼容修补放复现材料（→ [复现附录](experiments.md#reproducibility-appendix-current-prototype)）。

## 6. Evaluation

完整实验矩阵由 [Experiments](experiments.md) 持有，正文按问题推进：

**① Setup 与公平性。** 主张：固定模型精度、输入语义、实际生成工作、参考历史、调度模式与各预算口径；端到端比较须匹配工作量与统一服务判定，机制收益主张须控制变量（→ [比较族与公平性](experiments.md#fairness-checklist-for-the-protocol)）。

**② 主结果：达标承载能力。** 主张：在统一服务判定下比较全驻留、按需恢复与 Conveyor 可接纳的达标负载——结果【空位】（Q2；→ [评估问题](experiments.md#evaluation-questions)）。判读：达标承载增加则支持核心主张；驻留降低而达标承载未增，则结论收缩为"节省驻留但无服务收益"。钩子：收益从哪里来、付出了什么。

**③ 延迟代价与关键路径。** 主张：输入到结果的分布与恢复关键路径分解（提交、传输、完成上报、再调度分开测量）解释代价——结果【空位】（Q3）。判读：代价可量化且不抵消容量收益则支持；延迟或持续落后违约抵消收益则收缩适用域。钩子：整体收益确认后，还要知道每个机制各贡献多少。

**④ 消融：触发对照对应三级信息。** 主张：按需恢复与提交后预取不使用未来时间信息，基于节奏预取使用前两级，偏移对照检验第三级；比较时固定参考历史、主机副本与传输路径——结果【空位】（Q4；→ [消融矩阵](experiments.md#ablation-matrix)）。判读：收益随信息级别递进则支持"时间信息本身有价值"；收益来自未匹配的生成量或执行模式则该组作废重测。

**⑤ 资源模型验证。** 主张：独立标定、留出配置检验瓶颈分类与预测误差，报告模型失效处——结果【空位】（Q5）。判读：留出配置预测正确则资源模型可列为贡献；仅能逐点回拟合则降为分析工具呈现。

**⑥ 正确性与应用质量。** 主张：状态往返一致性、参考历史保持、代表任务质量与替代策略在相同标准下比较——结果【空位】（Q6）。判读：往返一致且历史有任务价值则支持"值得保历史"的前提；质量收益仅来自偏置任务则动机收缩。

**⑦ 边界与失效。** 主张：短会话、迟到、覆盖缺口、带宽与主机压力下的开销与失效区域如实报告，不从主图删除失败区域（Q7）。钩子：自己的边界画清之后，剩下的问题是本文相对已有工作站在哪里。

| 下一次使用感知与预取 | 信号来源与产生时刻、可靠性、提前量、允许动作 | SYMPHONY（NSDI'26：应用行为提示）；InfiniGen（OSDI'24：层内推测）；ECHO（OSDI'26：模型内部结构）；KVFlow（NeurIPS'25：工作流步数距离）；Learned Prefix Caching（NeurIPS'25） |
| 双工与实时语音 serving | 会话生命周期、交互/播放感知、每帧 deadline | Metronome（arXiv:2607.02640：周期实时任务框架、窗口化 KV）；LiveServe（arXiv:2606.22983：next-use 感知逐出、speech-onset 预取）；VoxServe（arXiv:2602.00269：请求作用域软 deadline 调度）；vLLM-Omni（arXiv:2602.02204：stage-graph 底座） |
| 服务目标与请求信息 | 应用要求到调度目标的推导、已知量与估计量、未达标处理 | JITServe（NSDI'26）；DistServe（OSDI'24）；Sarathi-Serve（OSDI'24）；Clockwork（OSDI'20：可预测性） |
| 周期任务与 deadline 调度 | 偏移指派、可调度性、资源约束 | Liu & Layland（JACM 1973，精确适用模型待核）；Linux SCHED_DEADLINE（术语参照）；Staggered Asynchronous Inference（arXiv:2412.14355：错开启动的复制推理） |
| 窗口、压缩、检索与替代状态结构 | 改变何种历史/数值语义，质量与资源代价 | Metronome 的 sink+window 为已核对实例；其余待按目标应用选代表方案，避免一概视为不可比较 |
| 分层内存、放置与异构执行 | 后备容量、链路竞争、计算放置 | DirectKV（OSDI'26）；FlashGen（ASPLOS'25）；NEO（MLSys'25）；OrbitFlow（PVLDB'26：decode 内逐层驻留规划）；FlexGen（ICML'23：离线吞吐，不同类） |

每族的定位步骤（一句"已解决什么／未覆盖什么条件"，全部为待核验草稿，核验后才能落笔）：

- **① 迭代级服务与分页**：解决了请求内的物理 KV 管理与批处理效率；不处理会话级的跨更新状态生命周期。
- **② 会话级 KV 分层与恢复**：解决了暂停期间的分层放置与回载；其恢复触发是队列深度或请求到达事件，不消费周期负载承诺的释放时刻（待核验）。
- **③ 恢复与重算的混合**：缩短了恢复段在关键路径上的长度；不改变它在关键路径上的位置。
- **④ 下一次使用感知与预取**：证明了提前量有价值；但信号来源（行为提示、层内预测、步数距离）与周期节奏不同源、动作域不同（待核验）。
- **⑤ 双工与实时语音 serving**：最近邻族——Metronome 以窗口化放弃完整历史，LiveServe 的 next-use 是观测估计而非负载承诺的时刻（待核验；单句差异在 closest-work 核验后冻结）。
- **⑥ 服务目标与请求信息**：提供从应用要求推导调度目标的方法参照；其对象是请求级服务而非跨周期会话状态。
- **⑦ 周期任务与 deadline 调度**：提供偏移指派与可调度性的术语和分析工具；不处理状态搬运与恢复时序。
- **⑧ 窗口、压缩与替代状态结构**：以历史语义换有界状态，作为质量—资源取舍的对照方案而非必败基线。
- **⑨ 分层内存、放置与异构执行**：给出改变恢复成本的硬件条件，决定结论的外推方向而非本文的直接对照。

九族定位收束为一句（措辞取自 problem.md 的【关键 · 待核验定位】标记，逐项核验后方可冻结）：尚无已知工作同时保住完整历史与及时就绪，并利用周期负载承诺的下一次使用时刻驱动驻留与恢复决策。钩子：该定位成立的范围就是本文假设成立的范围——假设松动时还剩什么，下一章讨论。

## 8. Discussion and Limitations

**① 偏移不可控时还剩什么。**

- 主张：偏移控制权是三级时间信息中最强的假设；应用不允许调整时，节奏可见性仍支持需求估计与提前准备，保留的收益比例【待验证】（→ [时间信息的机会与代价](problem.md#why-timing-information-matters)）。

**② 退化条件。**

- 主张：非周期输入、无空闲区间、短会话或主机容量不足时，机制退化为按需路径；退化区域按 Q7 的结果如实展示，完整历史的必要性与质量取舍同此讨论。

**③ 限制分层。**

- 主张：工程限制（当前触发方式、未验证的并发场景、观测开销）与方法固有条件（需要节奏与空闲区间）分开陈述；模型误差与未覆盖维度明确列出，当前原型不替最终研究范围作决定；增加设备的效果由实际拓扑和竞争决定，不作"加卡无用"的一般判断。
- 钩子：把经过裁决的主张按适用条件重述一遍，就是结论。

## 9. Conclusion

**① 主轴收束（过去时模板，正式评估后填写）。**

- 主张：本文刻画了周期交互中长期 KV 状态与 GPU 容量的张力【待 Q1 验证】，提出以负载承诺的下一次使用时刻驱动驻留回收与状态恢复的设计，并在【匹配对照与统一服务标准】下验证了【结果空位，含代价与适用边界】；结论适用于三个负载性质成立的负载域。不提前重复候选贡献，无新主张。
