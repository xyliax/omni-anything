论文叙事的定位、论证与计划笔记。自包含、可独立阅读；不是项目事实源。数字标注证据等级（实测 / 诊断级 / 推导 / 外推），与事实层冲突时以事实层为准；本项目自己的工作点数值、平台常量与配置值一律由 [`Experiments`](experiments.md)、[`Findings`](findings.md) 与资源模型持有，本文只保留结构性论证与符号关系，外部文献的数字随引用保留。

## 主张

对周期性交互会话（例如全双工语音与多模态助手等服务形态；最终 running example 待实验矩阵冻结后确认），在不截断上下文的前提下把 GPU KV 驻留变成可调度的量：会话空闲时把中段 KV 逐出到主机，按已知的下一次释放时刻在使用前恢复，并用释放偏移把各会话的驻留窗口与恢复流量确定性地分散到周期内。核心论点：这类负载的释放时钟由服务层掌握，KV 的下一次使用时刻由调度决定而不是预测得到，这使 deadline 驱动的驻留调度成为可能。

可以辩护的贡献表述：

1. 无损保留约束下的容量刻画：在“完整上下文必须保留”的要求下量化周期会话的容量-计算-恢复三资源关系与可利用余量。这是对丢弃路线开放问题的回答，不是对 capacity-before-compute 现象的首次发现。
2. 调度驱动的驻留机制组合：以事先承诺的绝对网格上的未来释放时刻（先于任何到达事件存在）触发恢复、以调度器 idle 转换触发逐出、失败时安全退化到按需回载或重算。与既有 prefetch 触发的区别在信号是否先于到达事件存在、是否精确、是否可事先承诺，不在搬运机制本身；引擎可以从到达时间戳估计周期，但不能承诺释放偏移，也不能决定输入在何时切分。
3. 偏移作为确定性时分复用：释放偏移把相关或依赖服务顺序的驻留与恢复峰值替换为确定性峰值，并把每个会话的输入切分时刻对齐到它的服务槽，使铺开工作不增加从切分到响应的延迟；事先承诺的释放偏移同时是“下一次使用是调度而非预测”得以成立的机制。可跨 GPU 扩展。
4. 周期-deadline 耦合的多资源 roofline：capacity/compute/HBM 逐卡、restore 逐主机的四约束模型；恢复带宽轴与周期 deadline 结构的耦合是既有 break-even 分析未覆盖的组合。

## 负载与问题

Introduction 骨架：

1. 服务栈的既有形状是一次性 request/response；流式交互会话改变形状：请求长期打开、输入小块到达、状态跨更新复用。
2. 上下文与 KV 工作集随每次更新增长；全驻留下 KV 池在每周期计算仍有余量时先满，容量先于计算限制并发。
3. 三个直观选择各有代价：全驻留触及容量上限；整段重算恰好耗掉作为动机的计算余量并威胁 D；按需回载把传输放进到达之后的关键路径，多会话同时恢复还会挤占链路带宽。
4. 请求级接口缺失的是下一次使用时刻；周期负载有这个信息，而且它就在服务层。

周期性是模型自身的推理契约，不是服务层强加的抽象：Moshi 以 12.5 Hz（80 ms/步）为帧时钟，DuplexOmni 用固定 480 ms 切片，MiniCPM-o 4.5 用 1 s 时分复用窗口，SyncLLM 用 160-240 ms 同步块；周期常量在训练时就写进了 token 排布，调度器不能更改。软 deadline 有三种独立表述：DuplexOmni 的 RTF < 1 生成目标、MiniCPM-o 的追赶控制律（TAIL）、OmniInteract 的随时间线性衰减效用评分；所有 deadline 数字锚定在人类对话 200-250 ms 的话轮转换间隙上。这批模型论文没有任何一篇讨论 KV 容量或会话长度维度的服务成本。

形式负载模型：会话 \(i\) 的第 \(k\) 次更新在 \(r_{i,k} = r_{i,0} + kT\) 释放，释放偏移 \(\phi_i = r_{i,0} \bmod T\) 在会话建立时指派并保持稳定；每次更新生成至多 \(M\) 个 token，受每周期软延迟目标 \(D\) 约束；上下文与 KV 工作集每周期净增长。

已确立的前提（引用，不再声称）：周期交互会话是每帧增长且常驻 KV 的周期实时任务；KV 池在每帧计算仍然便宜时先满；崩溃是静默的内存事件，触发前系统看似健康、随后集体停滞；线性池填充模型可预测饱和时刻。以上均为 Metronome（concurrent 预印本）已公开的内容。

分叉点：状态有界化的两条路。丢弃路线（Metronome：sink + 滑动窗口）把窗口外 KV 永久丢弃，其召回探针自己就显示窗口外召回为零，且“驻留是唯一预算兼容选择”的论证依赖一个对抗性 swap 模型（整状态每帧换出换入、数十 GB/s）。保留路线是本文立场：中段 KV 增量后备到主机、按调度恢复；每周期每会话实际搬运一次中段字节，搬运时刻与输入特征提取重叠；对其 swap 成本估算的定量反驳列于评价计划。

作用域限定：VAD 触发的级联服务面是事件驱动的反例；DuplexOmni 的后台思考通道是周期任务旁的 sporadic 伴随任务；deadline 时刻可以由事件决定，不必固定在周期边界。正式表述是“周期释放 + 每周期软 deadline，另伴随一个 sporadic 任务类”。

## 设计骨架

| 机制 | 一句话语义 | 所属层 | 失败退化 |
| --- | --- | --- | --- |
| 释放偏移调度 | 会话建立时在绝对时间网格上指派稳定释放偏移；晚醒只影响当次 firing，不重新锚定网格 | gateway | 不启用即同步释放 |
| 带主机后备的部分逐出 | 完成块增量复制到主机；会话 idle 后逐出中段，保留 GPU 前缀与未后备尾部 | engine | 无主机副本的块在恢复时重算 |
| KV 预取 | 释放时把 host-backed 块拷回 GPU prefix cache，与输入特征提取同期进行 | worker + engine | 拒绝、迟到或被 LRU 逐出时退回按需回载或重算 |

单会话一个周期的流水线：释放并快照未交付输出，特征提取与预取拷贝同期，准入与前缀匹配，补缺按需回载，prefill 与 decode（至多 \(M\)），新完成块推进主机后备前沿，idle 后逐出中段。

Design 章的两条纪律：正确性不依赖预取，预取只改时序，所有失败路径收敛到按需回载或重算；设计章只写上表三机制，no-wait `Step`、同步调度约束等按实现选择披露，不进贡献列表。

## 偏移调度的结论

三种策略的比较（对应下图的 S1/S2/S3 标注）：同步整批，所有会话同一瞬间释放、一批服务；同步流水线，释放仍同步，引擎内部把各会话的恢复与服务错开排列；释放偏移（本文方案），各会话在自己的释放偏移上切分输入并立即被服务。核心事实：同步流水线与偏移的资源占用曲线完全相同，分歧只在输入切分与服务之间的距离；逐项差异由图注与下方量化对照持有。

```text
one period T, four sessions; each needs restore (host link) then compute (GPU)

S1  synchronized release, one big batch
          ▼ all four release at t0
    link  █████.█████.█████.█████  r1 r2 r3 r4 serialized
    GPU   ........................████████████  one batched compute
    pool  all 4 full contexts resident together -> no capacity gain
    time  every reply due by t0+D: all work crams into D, rest of T unused

S2  synchronized release, engine pipelines internally
          ▼ all four release at t0
    link  █████.█████.█████.█████
    GPU   ......█████.█████.█████.█████
    pool  ~2 full contexts at a time + prefixes -> capacity gain
    but   all four inputs were captured at t0; s4 is served three slots
          later, so it answers OLD input, and latency varies by slot

S3  release offsets (ours)
          ▼ s1             ▼ s2             ▼ s3             ▼ s4
    link  █████............█████............█████............█████
    GPU   ......█████............█████............█████............█████
    pool  ~1-2 full contexts at a time + prefixes -> same gain as S2
    and   each session is served right after ITS OWN capture boundary:
          uniform latency, zero added staleness

（S3 的不重叠画法只在 N 不超过 T/单会话服务时长时成立；更大的 N 下相邻
窗口自然重叠，continuous batching 重新合并，见下方 slot 参数条目。）
```

关键认识：

- 陈旧不是延迟之外的第二种伤害：它就是队列位置带来的每会话固定延迟偏斜，量级至多一个周期。因此论证强度随 T 增大而增强：秒级周期下偏斜可达一整个周期，对 200-250 ms 话轮转换间隙是实质伤害；Moshi 级 80 ms 周期下可忽略。
- 抖动这一反对意见不成立：稳定服务顺序的内部流水线没有抖动。但稳定顺序本身就是一种内部释放偏移指派，这等于承认了同一种结构，也消除了这项伤害。
- 让内部方案零陈旧的唯一办法是把每会话的输入切分时刻推迟到它的服务槽，而这正是释放偏移。释放偏移若由引擎服务顺序涌现，会随负载漂移，下一次使用退化为预测事件，“调度而非预测”的全文命题随之不成立；在绝对网格上事先承诺释放偏移才保得住它。
- 引擎“不知道周期”是错的（从到达时间戳两三个周期即可估计）；正确表述是引擎不能承诺释放偏移、不能决定输入在何时切分。
- slot 参数（把 N 个会话分到 S 个释放槽）只在 S 不超过 T 与单会话 decode 时长之比（记为 S*，由工作点标定）时有意义；更大的 S 下相邻槽 decode 自然重叠、continuous batching 重新合并，瞬时批量稳定在约 N/S*，权重读膨胀有界（约 S* 倍，与 N 无关，推导）且必须在 HBM 余量内核算。
- 上界不变：总恢复流量与释放偏移无关；每周期恢复预算由链路带宽与 T 决定（推导，数值由资源模型给出），等上下文容量乘数被恢复预算/池容量与计算强制重叠共同封顶；随机释放偏移对独立到达已有统计复用，指派相对随机只再多带来常数因子，N× 级差距只在相关到达下出现。

三种策略的定性对照（工作点数值——恢复窗口分位数、峰值占用、权重读带宽、偏斜量——由 [`Experiments`](experiments.md) 与资源模型在实验矩阵冻结后给出）：

| 账目 | 同步整批 | 同步流水线 | 释放偏移 |
| --- | --- | --- | --- |
| 恢复传输 | 全部串行挤进 deadline 窗口 D | 每槽一次，隐藏在其他会话的计算之下 | 同流水线 |
| 峰值 KV 池 | 全部上下文同时驻留，等于全驻留，逐出无收益 | 少数全量上下文，加其余会话的保留前缀 | 同流水线 |
| 权重读 | 每周期迭代次数最少 | 瞬时批量变小、迭代次数增加，须在 HBM 带宽余量内核算 | 同流水线 |
| 新增延迟与陈旧 | 恢复串行可能超出 D，所有会话都违约 | 第 k 个会话多等 k·T/N，队尾偏斜近一个周期，回复对应旧输入 | 零 |

整表的结论：同步整批省下的权重读不是本工作点的瓶颈资源，它付出的容量与 deadline 恰恰是瓶颈。

等待位置的对照（候选论文图）：

```text
the wait exists in both spreading designs; what differs is where it sits

S2  wait AFTER capture (engine queue):
    capture s4 input at t0 ──► wait 3 service slots ──► serve ──► reply
    user-visible harm: the reply is late, and it is about old input

S3  wait BEFORE capture (phase assignment):
    one-time phase shift ──► capture s4 input at phi4 ──► serve ──► reply
    at session admission     user-invisible: fresh input, on-time reply

making S2 staleness-free = delaying each session's capture boundary to
its service slot = assigning it a release offset. The fix IS the design.
```

可写进论文的表述：确定化峰值、切分对齐与事先承诺三点已由主张 3 持有；需补充的只有两点：偏移不创造容量、带宽或重叠；它相对引擎内流水线的额外价值只出现在 D 紧于 T、到达相关或需要 schedulability 分析的场合，并随周期长度增强。

关于“偏移是为了让搬运与计算重叠”：重叠是流水线的属性而非偏移的属性。单会话的预取本就与其特征提取重叠，跨会话重叠引擎内流水线同样能做；偏移独有的是先于到达事件的确定 deadline 与 D 紧于 T 时受控的恢复并发。其核心价值在于：稳态下偏移让“传输隐藏在其他会话的计算之下”成为默认结构，而不需要引擎另行安排。

必做证伪实验：同 N、上下文、逐出配置下，指派偏移、随机偏移、完全同步三种配置对照，测峰值占用、deadline 违约与从输入切分到输出交付的延迟。

## 设计骨架内的改进计划

上节确定的是释放偏移指派这一层：同质周期会话在网格上均匀铺开释放点已是周期任务偏移指派的标准最优解，骨架不需要更换。骨架内部还有一批决策没有用到已承诺的释放时刻，或没有由约束推导：逐出的时机与对象、预取的发起时刻、恢复传输的次序、保留前缀 K 与槽数 S 的取值。以下各项按依赖排序，第 1 项的结果决定其余各项的取舍方向；全部改动都保持这三项机制与失败退化路径不变。

1. **回载窗口分解（其余各项的前提）。** 即评价计划的前置分解检查。它的两种结果指向相反的后续：固定开销可归因并消除，则继续按本节细化调度；固定开销是传输链路或引擎的串行占用，则重心转向传输合并（第 7 项）与主机侧压缩（设计空间表的 KV 压缩行），偏移把恢复拆散成时间上分离的小传输这一点反而成为代价。引擎源码的结构支持前一种组成：窗口大头是引擎步边界的等待而非链路占用（机制与打点方案见前置分解检查条目），此时错开不受固定成本惩罚，且缩短关键路径的修复落在提交与上报粒度上，改动很小；分解 run 用来证实这一点并给出各段实测占比。
2. **网格触发预取。** 当前预取在输入块到达 worker 时发起，与该块的特征提取同期，实际提前量只有一次特征提取窗口；会话从上次服务结束到下次释放之间的空闲段（占周期的绝大部分，见 [`problem.md`](problem.md#intrinsic-reuse-interval)）完全没有用于恢复。改为 gateway 在 r − Δ 时刻通知 worker 发起预取，Δ 取实测回载时长加裕量，现行触发方式保留为退化路径。收益：主张 2 的“先于到达事件触发恢复”从设计陈述变成实现事实，恢复流量可以分散到整个空闲段；同一实验直接给出 scheduled 与 arrival-triggered 的对照，即风险节 InferCept 条目所要求的数字。代价：提前 Δ 的额外驻留约为恢复字节的 Δ/T；gateway 与 worker 之间新增一条控制路径。验证：同配置下两种触发方式对照，测输入切分到首 token 交付的分位数与准入时的前缀命中率。
3. **保护已预取的块。** 预取完成到准入之间，块仍可被引擎按 LRU 逐出。对截止期落在一个回载窗口之内的块加保护，容量不足时改为拒绝更远会话的预取。这是预取净延迟收益可以被测出的前提。验证：高占用点统计预取完成后、准入前被逐出的比例。
4. **水位驱动的逐出。** 现行策略在会话进入 idle 时无条件逐出到 K，与池占用无关；诊断级数据显示逐出后池占用进入远低于满池的锯齿稳态，而对照接近满池（见 [`FINDING-H4`](findings.md#finding-h4)），同时每次回载都有实测的非零窗口成本：池仍有大量空闲时，系统在为此刻不需要的容量支付回载。改为池占用超过水位线才逐出，被逐出者按下次释放时刻由远及近选择；高占用时行为与现行策略一致。这同时让释放网格第一次作用于逐出方向。验证：低 N 点对照回载次数与占用轨迹，机制在不需要时应为零开销。
5. **逐出集合先裁剪到已后备块。** 现行逐出不检查主机覆盖，无主机副本的块被逐出后在下次恢复处退化为整段重算（机制文档已记录的实现限制）。逐出前与主机后备前沿求交即可，最坏情形与现行为相同。验证：恢复事件中由覆盖缺口引起的重算应归零。
6. **K 与 S 由约束反解。** 当前 K 与 S 都是配置常量（具体值见 [`Experiments`](experiments.md)），不来自任何推导。K 的约束是每周期恢复字节不超过恢复预算：诊断工作点只用掉预算的一小部分（推导），反解出的 K 是实现下限；K > 0 只在 N 与上下文之积逼近恢复预算时才有作用（推导给出该边界的表达式，数值随工作点定）。S 的约束来自两头：计算面有效上界 S*（见偏移一节），而特征提取与传输发起需要更细的偏移分辨率，内点最优要由扫描裁定。验证：Q4 的 K 扫描加上覆盖 1、S* 与 N 的 S 正交扫描，同时报告占用峰值、每周期传输字节、GPU 忙时与迭代次数。
7. **恢复传输的排序与合并。** 现行预取由各会话独立发起，容量不足即推迟重试，多会话同槽时形成传输突发；改为按下次释放时刻排序的单一恢复队列，按需回载可抢占预取。若第 1 项显示固定开销主导，同槽多会话的恢复应合并为一次大传输；错开与合并在固定开销下方向相反，这也是分解检查必须在前的原因。验证：相关到达的压力配置下测瞬时传输带宽分布与恢复迟到率。
8. **恢复与重算的双向填充。** 中段缺口目前的退化路径是串行回载，或从缺口起整段重算。改为计算从保留前缀向右重算、传输从中段末端向左装载、在中间会合，即把恢复与重算前沿的分割点思想（设计空间表 Cake 行）用在"前缀与尾部在卡上、缺中段"的形状上，用计算余量补恢复带宽。代价：消耗的正是动机论证里的计算余量，高并发下要重新记账。两点限定：重算每 token 的成本由固定的线性投影部分与随位置增长的注意力部分组成，短上下文处注意力只占小头（推导，占比随上下文增长），两端的成本不对称要到长上下文才显著，短上下文点收益有限；同轴变体是存每层 hidden state 代替存 KV（HCache 式，字节减半，重建只需线性投影、与上下文无关），做此项时应一并比较。验证：人为制造覆盖缺口，对比纯回载、纯重算与双向填充的就绪时刻。
9. **失败路径的三处收紧。** 其一，gateway 在发起 Step 之前清空会话的输入缓冲，调用失败时该次 firing 各会话的一整周期输入被静默丢弃，与完整上下文不变量冲突；改为确认成功后清空，或显式记录丢弃事件。其二，gateway 的释放循环同步等待 Step 返回，配置的超时长达数个周期，一次阻塞挡住其后所有槽的释放；释放与 Step 解耦后，单个会话的超时只影响它自己的那次 firing。其三，主机后备池是固定配置常量，而按配置上限推导的需求可能超过它（推导，数值见 [`Experiments`](experiments.md)），超出后主机侧逐出会把恢复静默变成重算；应按配置上限计算池容量，并把主机容量列入资源模型的第五条约束。验证：注入 Step 失败与长时程高并发，检查网格记录的完整性与主机池的逐出事件。

两项在当前问题设定之外，仅作记录。其一，负载模型只约束每周期输出量 m ≤ M，过载时下调 m 是唯一能减慢容量消耗速度的调节量，但须先验证模型契约允许。其二，异构上下文或会话进出的场景需要按恢复代价加权的释放偏移指派与有界的重新指派；在当前同构负载下轮转指派本身就是最优解，这也意味着释放偏移指派层的贡献在同构实验里测不出来，评价计划若要展示这一层需要引入异构负载。

约束集：完整上下文全保真可用（a）、不重训（b）、每周期 deadline D（c）、单卡基线（d）。每个替代族至少松弛其一：

| KV 压缩（量化、低秩、跨层） | KIVI、KVQuant、CacheGen | a 的保真度 | 一句话：常数乘子，延迟而非消除耗尽；与本设计可组合，可选一个量化组合配置 |

## 评价计划

六个 reviewer 问题：容量是否先于计算限制并发；恢复多少并发；容量扩展的延迟代价；逐机制正交消融（含 offsets-only 配置与引擎内恢复流水线对照）；roofline 是否可泛化（含以播放速率为参照的输出率配置点）；开销与失效边界。

证据现状（无数字摘要）：偏移对输入处理突发的缓解有诊断级支持，恢复带宽平滑未测；部分逐出对实测点驻留降低有诊断级支持，容量前沿待统一 decode 上限后重扫；预取语义已确认、净延迟收益尚未验证；跨系统正式对比因 decode 上限不一致而无法进行。

针对知道 Metronome 的 reviewer 的补充要求：

- 三个基线：无界全驻留（触及 KV 容量上限）、窗口化 KV（稳定但丢失窗口外历史）、本系统（稳定且全上下文），外加应用层重算对照。
- 一个窗口化必败的召回负载（会话后期询问会话早期内容）；常规探针上窗口化无损，不设此负载则无优势可显。
- swap 代价的定量反驳：实测每周期每会话 H2D 字节、恢复 deadline 裕量、恢复链路成为瓶颈时的行为。
- 容量记账：每会话驻留平台值、有无主机后备下的外推会话上限、每个 N 下最先成为瓶颈的资源。
- 恢复正确性：逐出-预取往返后块级一致与注意力输出等价。
- 测量纪律：每数据点新起 worker、释放偏移错开的独立输入流、时程长到足以显现容量趋势、重复运行并报告触及容量上限的运行比例、引擎内占用轨迹（失败是静默的，从延迟读不出）。
- 前置分解检查：诊断级回载窗口远大于按链路带宽推导的纯拷贝时间（推导；两者数值由 evidence 与资源模型持有）；先分解拷贝与固定开销，若固定开销主导，恢复轴被实现开销掩盖，一切带宽外推都要先通过这项检查。两种结果的后果相反：若固定开销是传输链路或引擎的串行占用，按实测窗口折算的有效恢复速率可能低于按池占用反解的需求（推导），容量乘数上限降到 1 以下，恢复路线在该平台不成立；若固定开销可与其他会话的计算重叠，按链路带宽推导的恢复预算与对应容量乘数成立。引擎源码的时序结构支持后一种：装载在每步模型执行之后的连接器收尾处才提交给拷贝线程，完成也只在同一处按步轮询上报，会话要到下一次调度才恢复，窗口因此按引擎步长量化，量级为两三个引擎步、与字节数基本无关（推导）；拷贝本身是锁页主机内存上的批量 DMA，走低优先级 CUDA 流。分解按三段打点：准入到拷贝提交、拷贝本身（CUDA event 计时）、完成上报到重新被调度。若证实等待主导，恢复轴不受固定成本惩罚，缩短关键路径的对应改动是准入当步提交拷贝、完成后立即恢复，属实现修改而非调度修改。
- CPU 注意力的带宽账：中段留在主机上算注意力时，每个新 token 都要重读全部历史 KV，每周期主存读取约为 N × 每周期新 token 数 × 上下文长度 × 单 token KV 字节 / T，随 N 与上下文继续增长，在诊断工作点即已逼近低带宽主机主存的上限（推导）；而把中段每周期搬回 GPU 一次的流量低若干个数量级（推导）。低带宽主机上该替代不可行；高带宽多通道服务器主存或稀疏注意力会改变结论，论文声明须按主机平台限定，服务器域内仍需把 NEO 式方案升级为基线。
- 输入到交付的对应度量：当前交付路径没有输入-输出对应关系，同步流水线与偏移之间的陈旧与延迟偏斜主张在补上该度量前只能标注为推导结论。

## 多 GPU 扩展

结构性论点：KV 容量与每周期计算随 GPU 数 G 线性扩展，恢复带宽是唯一次线性的轴——共享上行链路的收敛交换拓扑在很小的 G 就以上行链路为瓶颈，直连拓扑随后受主存或跨 socket 链路限制（均为外推，具体拐点按标定计划实测）。“多买卡”不解决问题：加卡不加恢复带宽。这使恢复带宽轴成为动机论证的核心依据，而不只是 roofline 的一轴。

四约束 roofline：capacity、compute、HBM 逐卡，restore 逐主机（唯一对 GPU 求和的约束）。跨卡偏移的精确主张：不抬高 roofline 的上限，而是消除让系统无法逼近上限的峰均比损失，上界 min(T/W, N·G)（W 为回载窗口宽度，比值由标定给出）。

正面写出的边界条件：直连高带宽拓扑是论证最弱情形；小 G 单 socket 有主存余量；对等 HBM 分层（AQUA）与多路聚合（MultiPath）都需要空闲邻卡，同质周期负载下不存在空闲邻卡；恢复 vs 重算交叉点随共享路径拥挤向重算移动，这是模型的输出而非弱点。

标定：每主机 profile 测五个原语（单卡锁页 H2D 带宽、并发 H2D 拐点、拓扑与 NUMA 与主存背景负载、恢复-重算交叉、双向传输干扰）。模型无拟合参数：拐点位置错一以上即拒绝模型而非调参；瓶颈轴判定要求全部配置正确。按拓扑分辨的“并发 H2D 带宽 vs 活跃 GPU 数”受控扫描在现有文献中不存在，是一张低成本的、填补文献空白的测量图。

## 风险

- 新颖性空间狭窄：问题框架属于 Metronome，机制组件属于会话 offload 文献；叙事必须始终立足于调度结构、无损约束与周期 deadline 耦合，任何把机制组件说成贡献的句子都会成为拒稿理由。
- 精确性的价值未量化：InferCept 的 oracle 差距（见相关工作定位表）要求用 scheduled 与 arrival-triggered 的直接对照数字回应。
- 提前量的实现差距：信号坐标图描述的是网格信号的可用范围，当前实现只用其中一次特征提取窗口；在网格触发预取（设计骨架内的改进计划第 2 项）实现之前，与到达后触发系统的区分在实现层不成立，审稿人读代码或追问细节即可发现。
- 时钟归属的循环论证质疑：释放网格是服务层施加的抽象；辩护依赖“周期是模型自身训练契约”的负载事实，须在背景节先立住。
- 瓶颈资源的作用域：encoder 计算可能在某些模型与硬件点先于 KV 成为瓶颈（此前诊断在其他硬件点观察到过这种情形）；必须在实验工作点用容量记账证明 KV 先成为瓶颈，并区分突发容量与长时程容量。
- 偏移收益的可测性：当前路径无播放链、无输入-输出关联；在评价计划的输入到交付对应度量补上前，偏斜与确定性主张只是推导结论，没有实测支持。
- 周期长度作用域：偏移主张随周期长度增强（推导见偏移一节），论文声明需限定在大周期负载类。
