2026-08-11 库存漂移修复验证（conveyor，trace，N=8，seed=4096，park=64，120s）：**库存漂移修复 + 卸载可视化**。起因是项目负责人读 whitebox 时间线时的四个观察，全部坐实为真问题：①「只见回载不见卸载」——eager 镜像无任何可视证据，补 park.log `S` 行（镜像前沿推进量/会话/步，本 run 1701 条）+ Perfetto KV offload instant；②「启动期 batch 同步」——实测 8×4096 seed prefill 在引擎串行排队（各 ~0.87s、合计 ~7s ≈ 3.5 周期），首批音频片压后挤出，槽轮节奏随后自愈；定性为 warm-start 固有瞬态，测量协议应剔除启动 ~15s；③「tick 与 prefill/decode 错位」——根因是**库存漂移**：上一轮把每段 max_tokens 定为 tpt+8，+8/段在取现货库存里无限囤积（whitebox 第 55 帧交付的 token 对应 ~13 周期前的音频，双工语义静默破坏而交付指标全绿）；修为 tpt 精确值，本 run 完成余量恒 ~1.0s 全程平直、`inv_backlog` 监控恒定不增；④「驻留 counter 像累计值」——每 park 单采样只画出上包络，改为释放前/后双采样的真锯齿。副产品：max_tokens=tpt 使 slice 更快，park 拒绝从 297 次降到 43 次（成功率 ~90%）。**残留一个待裁决项**：seed 泄洪期为部分会话留下恒定 ~4 slice 的库存疤痕（生成速率=消耗速率，永不消化），交付内容比设计滞后多 ~4 周期——排空策略（超量交付 vs 丢弃陈旧 token vs 接受疤痕并剔除 warmup）是语义选择，上桌待定。miss=1.46%/TTFA 4004ms 维持启动瞬态口径，run 照纪律判 failed。

2026-08-11 库存漂移修复验证 附录 + keep-K 定时版验证 + auto-park-on-stop 验证（conveyor，trace，N=8，seed=4096，120s）：**驻留策略从固定尾块进化到「随批驻留」**，由项目负责人两轮读图观察驱动。①观察「offload 次数过多」坐实为仪器 bug：C1 修复把 store 游标归零导致每 chunk 重扫全上下文、S 行把重扫计成卸载（每会话 sum ~24,600 块 vs 诚实值 ~545）；改为用 CPU 覆盖度定位游标（不归零），S 行回归真实拷贝量。②观察「会话驻留单调递增」坐实为策略缺陷：固定 evict-64 下闲置底座 = L−64 随上下文增长，池需求无上界；新增 **keep-K 配额模式**（`park_keep_blocks`：逐出 K 之外全部尾块，闲置底座钉死）。③观察「全驻留会话数 ≈ batch size、必须瞬间释放」→ **auto-park-on-stop**：park 从 worker 的 push+1.2s 定时 RPC 移到调度器 `_handle_stopped_request` 内联（段配额打满转入闲置态的那一行 = decode 刚结束的精确定义），零延迟零 RPC、天然串行；留 2 块尾部余量避开 store 发出竞态。**量化结果**（keepquota 定时版 → onstop 版，K=128）：稳态池占用 0.377 → **0.296**（全驻留假设 0.860，**66% 驻留换到主机**）；同时全驻留会话数 3/4 各半 → **3 个占 79%、2 个占 14%**（逼近批驻留下界 = slice 时长 × N/周期）；回载窗口 p50=70ms/max=115ms（415 块 ≈364MB 尾巴仍藏进 FE 窗）；被逐尾块 CPU 覆盖率 p50=100%；交付零恶化（miss=1.46% 恒为 seed 启动瞬态，[starve]=7 同基线）。带宽换显存主张首次有端到端量化证据；进一步压低全驻留数已是物理边界（slice 时长），属 decode 中渐进释放的未来工作。

2026-08-12 warm-start 屏障验证（conveyor，trace，N=8，seed=4096，K=128，120s）：**warm-start 屏障 + 首个全绿 park run**（state=success、miss=0.00%、TTFA p50=2003ms、零 starve、481 次 park）。项目负责人裁定 warm-start 的正确语义：seed 模拟「请求自带上下文」，引擎应在**全部会话 seed prefill 完成后**才开始接收 tick——seed 与 tick 抢跑（旧行为）正是 seed 泄洪瞬态的根源。实现为结构性屏障：worker 预建 sid 1..N 会话、跑完全部 seed（实测 8 会话 8.7s）后才写 ready 文件，gateway/client 在 ready 之后才启动，首个 tick 物理上不可能早于最后一个 seed（依赖 gateway 按到达序分配 sid 1..N 的确定性，越界 sid 回退惰性 seed 并告警）。两轮修正：①r1 暴露 **seed token 泄漏**——seed 的 1 个输出 token 留在取现货库存，首 tick 交付它导致 TTFA 假读 3ms、烧掉首交付豁免（12 次假饥饿）；修：屏障完成时消费指针跳过 seed 产出（seed 是上下文不是回应）。②r2 暴露 **starve 口径毛边**——首段爬坡的部分交付被稳态口径记饥饿（miss 0.63%）；修：饥饿计数从会话**首次足额交付（≥tpt）**起算（gateway `fdFull` 标志），TTFA 保持首个非零 token 语义，两个口径正式分离。同批落地：kv.log 采样周期可配（`OMNI_STATLOG_PERIOD_S`，conveyor 默认 0.2s = 每 tick 10 采样，1Hz 太粗看不清 park 锯齿间的连续曲线；本 run 568 行 @200ms）。**残留待裁决**：inv_backlog 稳在 64（~2.5 slice）——爬坡期堆积的库存在生成=消耗的精确配平下永不消化，交付内容比设计的 1-slice 滞后多 ~1.5 周期；排空策略（超量交付 / 丢弃陈旧 / 接受）仍上桌。
